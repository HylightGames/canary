# `v0.0.6` Roadmap: Rendering Bootstrap (RHI + `canary-render-vulkan`)

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
the RHI trait and its first concrete implementation, per
[ADR 0004](../decisions/architecture-decision-records/0004-rendering-abstraction-strategy.md)
(the RHI/render-graph split) and
[ADR 0016](../decisions/architecture-decision-records/0016-native-rendering-backends.md)
(native per-graphics-API backends, superseding the earlier `wgpu`-bootstrap
plan). See both for the full reasoning; this is what's actually in scope
for the release that makes the RHI trait real rather than aspirational.

## Why rendering, and why bounded this way

Rendering was the natural next subsystem before `v0.0.5` redirected to
localization, and the redirect's own reasoning ("a founding constraint
gets cheaper the earlier it's load-bearing") doesn't apply here the same
way — rendering isn't a constraint on other subsystems' correctness the
way "no hardcoded text" is, it's simply the next large, real piece of
engine surface. Physics, `CanaryUI`'s concrete backend, and `canary-state`
remain genuinely unsequenced beyond this release — see `status.md`'s
updated `v0.0.4`+ list. Networking is deliberately pushed toward the end
of that sequence, per direct project direction, rather than raced to.

**Building even a minimal native Vulkan backend is real, substantial
engineering** — instance/device setup, memory allocation, pipeline and
descriptor management, synchronization — likely more so than any prior
`0.0.x` release's single-focus scope. This roadmap bounds `v0.0.6`
deliberately narrowly (an offscreen "hello triangle," not a render graph
or a live window) for the same reason `v0.0.3` shipped a first-cut data
ABI with a deliberately small value-type set rather than general foreign
reflection: a real, working, narrow slice beats a broad, half-finished
one, and widening later is straightforward while walking back an
over-general first cut is not.

## Not blocked on `v0.0.4` (real windowing) landing first

`v0.0.4` (winit-backed windowing) remains scoped but unimplemented — see
`status.md`. Rather than wait on it, `v0.0.6` proves the RHI trait and
the Vulkan backend correct **offscreen**: a headless Vulkan instance
rendering into a GPU-side render-target image, with correctness checked
by reading that image back and asserting on its pixels, not by a human
looking at a window. This is the same pattern `v0.0.5` used for
`CanaryUI`/`canary-assets` not existing yet, and `v0.0.3` used for
proving Tier A capability enforcement without a real plugin ecosystem to
exercise it: **prove the subsystem correct in isolation, wire it to
siblings whenever they're actually ready.** Swapchain-to-window
presentation is real, near-term follow-on work once `v0.0.4` lands, not
part of this release's definition of done.

## Scope

1. **The RHI trait itself** (`canary-render`, or a `canary-render-core`
   split if the implementation makes that separation worth it): devices,
   buffers, textures, pipelines, and command encoding, modeled on modern
   explicit graphics APIs per `rendering.md`. Minimal enough to prove the
   concept end to end for this release's actual milestone (below), not a
   complete abstraction over everything Vulkan/Metal/DX12 can do —
   widening this trait as later backends need more of it is expected,
   not a sign the first cut was wrong.
2. **`canary-render-vulkan`**, via [`ash`](https://github.com/ash-rs/ash)
   (compiles clean against this project's rustc-1.75 floor with zero
   pins — see "Verified, not assumed" in ADR 0016). Implements exactly
   as much of the RHI trait as milestone 4 below needs: instance and
   (software, via `llvmpipe`, for sandbox testing — see below) device
   creation, a single GPU buffer upload, a minimal graphics pipeline
   (one vertex shader, one fragment shader, no blending/depth-testing
   complexity), and command buffer recording for one draw call into an
   offscreen color target.
3. **WGSL authoring, `naga`-cross-compiled to SPIR-V for this backend**
   (see ADR 0016's "Verified, not assumed" for the exact confirmed pin
   set: `naga = "=22.1.0"`, `indexmap = "=2.11.4"`). A materials *system*
   is explicitly out of scope (below) — this release needs one shader
   compiled once, not a general material/variant pipeline.
4. **The actual milestone: a real, automated "hello triangle" test.**
   Render a single hard-coded triangle (position + vertex color, no
   textures) to an offscreen render target at a fixed resolution, copy
   the rendered image back to host memory, and assert on its pixels —
   e.g., the triangle's known color appears at its known interior
   coordinates and the background clear color appears outside it. This
   is the equivalent proof-of-correctness rigor `v0.0.3`'s
   real-compiled-plugin tests and `v0.0.5`'s real-`.ftl`-resolution tests
   already established: exercise the real thing, not a mock, and check a
   concrete, specific, automatable assertion — not "it compiled" or "it
   didn't panic."
5. **Feature-gating proven, not just described.** `canary-render`'s
   `vulkan` Cargo feature must be genuinely optional: a build with it
   disabled must not pull in `ash` at all. This is the first real test
   of the "backend crates are opt-in, unused ones aren't in the build"
   claim ADR 0016 makes — worth checking mechanically (e.g.
   `cargo tree` without the feature enabled shows no `ash`), not just
   asserted in prose.
6. **`docs/architecture/rendering.md` and the relevant ADRs' status
   updated** once this lands, the same discipline every prior release
   has followed.

## Explicitly not in scope

- **The render graph.** Pass declaration, resource-dependency tracking,
  transient resource pooling, and the ECS extract step (`rendering.md`'s
  "Render graph responsibilities") are all real, described, future work —
  this release proves the RHI layer beneath them works, not the layer
  itself.
- **A materials/shader-variant system.** One hard-coded shader, compiled
  once, for the hello-triangle proof. Data-driven materials are
  render-graph-era work.
- **Live window presentation (swapchain-to-window).** Deliberately
  deferred until `v0.0.4` real windowing actually lands — see "Not
  blocked on `v0.0.4`" above. The RHI trait's device/buffer/pipeline
  surface is designed so adding swapchain presentation later doesn't
  require redesigning what this release builds.
- **`canary-render-metal`, `canary-render-dx12`, `canary-render-gl`.**
  Real, intended, explicitly unsequenced — see ADR 0016's "Alternatives
  considered" for the reasoning behind Vulkan going first, and
  `future-roadmap.md` for why the rest aren't pinned to release numbers
  yet.
- **2D-specific rendering (sprite batching, orthographic-camera
  configuration).** `rendering.md`'s "2D is a specialization, not a
  separate architecture" still holds; there's no render graph yet for
  2D to be a configuration *of*.
- **Textures, depth testing, blending, multiple draw calls, or any
  multi-pass rendering.** One triangle, one pass, one target — anything
  past that is render-graph-era scope, not RHI-bootstrap scope.
- **Real GPU hardware validation.** This release's automated test target
  is `llvmpipe` (software, sandbox-testable — see below); validating
  against real Vulkan drivers on real GPU hardware is real, necessary,
  separate work whenever that hardware is available, not blocked from
  starting without it.

## Verified, not assumed

Carried over from ADR 0016 (full detail there), restated here since it's
exactly the kind of groundwork a roadmap should confirm rather than
re-assert:

- **`ash = "0.38"` compiles clean under rustc 1.75 with zero pins** — the
  cleanest dependency check of any subsystem scoped so far.
- **A real Vulkan device is enumerable in this sandbox.** Installing
  `mesa-vulkan-drivers` (the `llvmpipe`/`lavapipe` software Vulkan ICD)
  and running `vulkaninfo --summary` confirmed a real
  `PHYSICAL_DEVICE_TYPE_CPU` device (`llvmpipe`, Vulkan API version
  1.4.318, Mesa 25.2.8) — meaning milestone 4's offscreen render-and-
  readback test is genuinely automatable in CI-like environments without
  real GPU hardware, not a "should work, untested" assumption. Enabling
  a display surface for a *windowed* test would additionally need Xvfb
  (already confirmed available per `platform-abstraction.md`), but
  milestone 4 doesn't need a display surface at all — offscreen
  rendering only.
- **`naga = "=22.1.0"` + `indexmap = "=2.11.4"` is the minimal pin set**
  for standalone `naga` (no `wgpu`) under rustc 1.75 — confirmed from a
  clean `Cargo.lock`, not carried forward from an intermediate,
  over-pinned debugging state. A real functional test (not just a
  compile check) cross-compiled one real WGSL vertex+fragment shader to
  actual SPIR-V, MSL, HLSL, and GLSL output — see ADR 0016.

All of the above should be re-verified at implementation time in case
the ecosystem has moved again, the same caveat every toolchain pin in
this project carries per
[`build-system.md`](../development/build-system.md#the-rustc-175-sandbox-validation-floor).

## Definition of done

- [ ] `canary-render`'s RHI trait exists, covering exactly what
      milestone 4 needs (device, buffer, minimal pipeline, command
      encoding) — not a speculatively complete GPU abstraction.
- [ ] `canary-render-vulkan` implements that trait via `ash`, with no
      `ash` (or other Vulkan) types leaking past the trait boundary into
      `canary-render`'s public API.
- [ ] A real WGSL shader is cross-compiled to SPIR-V via standalone
      `naga` and loaded by the Vulkan backend.
- [ ] The offscreen hello-triangle test renders a real triangle to a
      real (software, `llvmpipe`-backed) Vulkan device, reads the result
      back, and asserts on specific pixel values — automated, not
      manually eyeballed.
- [ ] `canary-render` builds with the `vulkan` feature disabled and
      pulls in no Vulkan-specific dependency when it is — checked
      mechanically (e.g. `cargo tree`), not just claimed.
- [ ] `docs/architecture/rendering.md`'s status, and ADR 0004/0016's
      status lines, updated to match what's actually implemented.
- [ ] `cargo build`/`fmt --check`/`test`/`doc` clean; `clippy` verified
      if this sandbox can reach it this time, honestly flagged if not.

## Status

Not started. Scoped and ready to begin — including the toolchain and
sandbox-capability verification most releases have needed as a first
step, already done (see "Verified, not assumed").
