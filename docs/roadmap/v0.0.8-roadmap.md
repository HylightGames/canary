# `v0.0.8` Roadmap: ECS Scheduler (`canary-scheduler`)

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
the scheduler `v0.0.7`'s access-model work was explicitly the
prerequisite for. See
[`docs/architecture/execution-model.md`](../architecture/execution-model.md#the-scheduler)
for the full design.

## Why this, and why bounded this way

`v0.0.7` added multi-component queries and typed resources specifically
because two external reviews converged on "the ECS needs a real
data-access declaration before a scheduler can be built on it." That
prerequisite is done; the scheduler is its direct, intended payoff, not
a new direction. Picked over the render graph/physics/`CanaryUI`/
`canary-state` options `status.md` left open after `v0.0.7`, since
letting the access-model work sit unused for a release would waste the
exact thing it was built for.

Bounded deliberately narrow, for a reason discovered during
implementation rather than assumed going in: genuinely running two
*write* systems concurrently, even when `SystemAccess` can prove their
writes are disjoint, requires handing each system its own
provably-disjoint view of `World` rather than an exclusive `&mut
World` — a substantially larger `unsafe` undertaking than anything this
project has built so far (closer to Bevy's `UnsafeWorldCell`/
`SystemParam` machinery than to `query2_mut`'s narrow column-pair
split). Attempting that in the same release as the scheduler's first
cut would have meant either rushing a much bigger safety-critical
design or not shipping a working scheduler at all this release. Instead:
ship a scheduler that's *correct* now (every write runs alone,
sequentially) and *measurably* parallel where it's actually safe to be
(read-only systems run concurrently, proven by a real timing test, not
asserted) — and name the write-concurrency gap precisely, rather than
either hiding it or blocking the whole release on closing it.

## Scope

- **New crate, `canary-scheduler`**, depending only on `canary-ecs`'s
  public API (no privileged access to `World`'s internals).
- **`SystemAccess`**: a system's declared reads/writes, component and
  resource types tracked separately, built as an explicit chainable
  declaration.
- **`Schedule`**: greedily batches systems, in registration order, into
  stages — one or more read-only systems, or exactly one system that
  writes anything — and runs each stage, joining any spawned threads
  before the next stage starts.
- Real multi-threaded execution for read-only stages via
  `std::thread::scope` — no external thread-pool dependency needed for
  this first cut.

## Explicitly not in scope

- Concurrent execution of two write systems, even with provably-disjoint
  access — the reason this release is bounded the way it is; see above.
- Automatic access inference from a system function's signature (a
  `SystemParam`-style framework) — `SystemAccess` is declared
  explicitly, matching this project's existing "manual before macro"
  precedent (ADR 0010).
- Wiring `Schedule` into `canary-core`'s `App`/`Subsystem` tick loop —
  `Schedule` is usable standalone; integrating it as `App`'s actual
  per-tick execution path is real next work once a second real
  subsystem beyond the ECS has systems worth scheduling this way.
- A persistent work-stealing thread pool — threads are spawned fresh per
  parallel stage for this first cut; real overhead, documented, not
  optimized against without evidence it matters yet.
- Command buffers and events — still correctly deferred per
  `execution-model.md`: this scheduler's specific design (concurrent
  systems are always all-read, writes always run alone) means there's
  still no live race either would need to prevent.

## Verified, not assumed

- **Read-only systems actually run concurrently, not just "should"
  according to the algorithm.** Tested with a real timing measurement
  (two 120ms sleeping systems; asserts the whole schedule completes in
  well under their sum) and a real concurrency counter (asserts both
  were simultaneously in flight at some point) — not inferred from
  `compute_stages`' logic alone.
- **A write system never overlaps with a concurrently-running read
  system.** Tested with a real shared atomic flag a genuine overlap
  would have caught, not just asserted from the scheduling algorithm's
  intent.
- **Stage computation matches the documented rules exactly**, checked
  directly against `compute_stages`' output: independent read-only
  systems batch into one stage; a write system always gets its own
  solo stage; a read that depends on an earlier conflicting write is
  never merged into or ahead of that write's stage; an unrelated read
  still can't join a write's stage either (no exceptions to "a write
  always runs alone").
- **A system correctly observes an earlier, order-dependent system's
  effect** — tested end-to-end through the public API (`Schedule::run`
  against a real `World`), not just at the stage-computation level.
- Full workspace `build`/`clippy -D warnings`/`test`/`fmt --check` clean
  across the full workspace, with and without `winit-backend`, after
  adding the new crate.

## Definition of done

- [x] `canary-scheduler` exists as a new workspace member, depending
      only on `canary-ecs`.
- [x] `SystemAccess` supports declaring component and resource
      reads/writes separately, with `is_read_only`/`conflicts_with`
      covered by unit tests (including the "resource access doesn't
      conflict with component access of the same type" edge case).
- [x] `Schedule::add_read_system`/`add_write_system`/`run` exist;
      `add_read_system` panics if given an access declaration that
      isn't actually read-only, rather than silently trusting a
      mismatch between declaration and registration method.
- [x] `Schedule::compute_stages` is covered by direct unit tests for
      every stage-boundary rule named in `execution-model.md`.
- [x] Real concurrent execution of a multi-system read-only stage is
      proven by a timing-based test, not just exercised.
- [x] `docs/architecture/execution-model.md` updated in place ("The
      scheduler" section) rather than a new document, per its own
      stated intent from `v0.0.7`.
- [x] `cargo build`/`clippy -D warnings`/`test`/`fmt --check` clean
      across the full workspace, with and without `winit-backend`.

## Status

Implemented. `SystemAccess` and `Schedule` both exist in the new
`canary-scheduler` crate, with 15 passing tests covering access-conflict
logic, stage computation, end-to-end scheduling correctness, and real
measured concurrency. Concurrent disjoint writes, automatic access
inference, `App`/`Subsystem` integration, and a persistent thread pool
all remain real, intended future work — see "Explicitly not in scope"
above.
