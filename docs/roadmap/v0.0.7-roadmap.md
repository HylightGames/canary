# `v0.0.7` Roadmap: ECS Execution Model (Queries, Resources, `Tick` width)

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
the data-access architecture the ECS needs before a scheduler can be
built on top of it, decided by the September 2026 external architecture
review triage
([`docs/reviews/triage/2026-09-review-triage.md`](../reviews/triage/2026-09-review-triage.md))
rather than picked from the previously-open render-graph/physics/UI/state
options. See
[`docs/architecture/execution-model.md`](../architecture/execution-model.md)
for the full design this release implements a first cut of.

## Why this, and why bounded this way

Two independent external architecture reviews converged on the same
finding `core-runtime.md`'s own "Threading & the job system" section had
already implied but never made load-bearing: `canary-ecs` has archetype
storage but not yet the data-access architecture (multi-component
queries, typed resources, a formal access model) a scheduler needs, and
building the next layer of systems around it before fixing that risks a
redesign later instead of a decision now. That's specific and
well-evidenced enough to resolve what was, as of `v0.0.6`, a genuinely
open "what comes next" question.

Bounded deliberately narrow, per both reviews' own closing arguments
("lock the important contracts, implement only what the next milestone
needs" / "design for it, don't build it yet"): this release adds
multi-component queries and typed resources as concrete, hand-written,
tested primitives — not a fully generic `Query<D>` trait over arbitrary
tuples, not the scheduler itself, not command buffers or events (nothing
parallel exists yet to need either from). See
`execution-model.md`'s "What's still deliberately not here" for the
complete list of what this release intentionally does not include.

## Scope

- **`Tick(u32)` → `Tick(u64)`.** A plain `PartialOrd`/`Ord`-derived
  `tick > since` comparison (see `World::query_changed_since`) is only
  correct if `Tick` never wraps during a `World`'s lifetime; at `u32`, a
  long-lived server advancing the tick once per frame at 60Hz wraps in
  about 2.3 years of continuous uptime. Mirrors the same reasoning
  already applied to `Entity::generation`.
- **Typed resource storage**: `World::insert_resource`/`resource`/
  `resource_mut`/`remove_resource`/`contains_resource`/
  `resource_changed_since`, addressed by type rather than by entity, with
  the same `Tick`-based change detection every component column already
  has.
- **Multi-component queries**: `World::query2`/`query3` (read-only,
  archetype-set intersection across 2 and 3 component types) and
  `World::query2_mut` (one mutable, one shared — the "update `A` based
  on `B`" shape).
- **`docs/architecture/execution-model.md`**: the design document these
  implement a first cut of, including the "five invariants" (Ownership,
  Access, Time, Identity, Side-effects) adopted from the second review's
  closing argument.

## Explicitly not in scope

- The scheduler/job-stealing system itself — the entire point of this
  release is the prerequisite, not the thing itself.
- Command buffers (deferred writes) and events
  (`EventWriter`/`EventReader`) — both real, both accepted in the review
  triage, both deferred until something actually runs concurrently or
  needs a cross-system signal to justify their API shape.
- First-class time types (`WallClock`/`FrameTime`/`SimulationTime`) —
  accepted, deferred until there's a frame loop sophisticated enough to
  need them.
- A fully generic `Query<D>` trait over arbitrary-arity, arbitrary
  read/write tuples, or query-composed filters (`Without<T>`,
  `Added<T>`) — `query2`/`query3`/`query2_mut` are the narrow, real
  second consumer this crate's own established pattern (see ADR 0010's
  manual-impl-before-derive-macro precedent) says should exist before
  generalizing, not a substitute for eventually building it.
- Mechanical enforcement of the five invariants (a `cargo-deny`-style
  dependency-direction check, review #2's item 15/16) — real, accepted,
  scoped as its own future CI/xtask work, not bundled here.
- Mixed-mutability query shapes beyond `query2_mut`'s one-mutable-one-shared
  (`query3_mut`, two-mutable-one-shared, etc.).

## Verified, not assumed

- `World::query<T>()` was confirmed, by reading the actual code rather
  than trusting the reviews' description of it, to be single-component
  only before this release — no multi-component join existed.
- `Tick`'s wraparound risk was confirmed directly: `#[derive(...,
  PartialOrd, Ord)]` plus a plain `tick > since` comparison in
  `query_changed_since`, with no wraparound guard anywhere.
- Zero `Resource`-style storage and zero ECS command-buffer abstraction
  existed anywhere in the workspace prior to this release (checked via
  direct source search, not assumed from the reviews' framing).
- `query2_mut`'s `unsafe` column-pair split (in
  `Archetype::column_pair_mut`) was reasoned through explicitly rather
  than reached for by default — canary-ecs had zero `unsafe` code before
  this release, and
  [`docs/development/coding-standards.md`](../development/coding-standards.md#unsafe-code)
  names it as one of only two expected boundaries for `unsafe`, neither
  of which is `canary-ecs`. See `execution-model.md`'s "On `unsafe`" for
  the full argument for why this specific, narrow case is sound and
  necessary, and why the alternative (restructuring `Archetype`'s
  column storage to a `Vec` + index, enabling safe slice-splitting
  instead) was considered and deferred as a larger, riskier change than
  this release's scope justifies.
- Full workspace `build`/`clippy -D warnings`/`test`, with and without
  `winit-backend`, all clean after every change in this release —
  re-verified against the actual sandbox toolchain (`rustc`/`cargo`
  1.91, this sandbox's best current proxy for real CI's `rustup`-managed
  `stable` — see
  [`build-system.md`](../development/build-system.md#the-rustc-175-sandbox-validation-floor)),
  not assumed to still hold after each edit.

## Definition of done

- [x] `Tick` is a `u64`; all 25 pre-existing `canary-ecs` tests still
      pass unchanged.
- [x] `World::insert_resource`/`resource`/`resource_mut`/
      `remove_resource`/`contains_resource`/`resource_changed_since`
      exist, with tests covering insert/get/overwrite/remove, distinct
      resource types not interfering, and change detection.
- [x] `World::query2`/`query3` correctly compute an archetype-set
      intersection (not union), with tests confirming an entity missing
      any one of the queried types is never yielded, and that type
      order in the query doesn't matter.
- [x] `World::query2_mut` writes through the mutable component, leaves
      the shared component untouched, correctly marks only the mutable
      component's change tick (not the shared one's), and spans
      multiple archetypes correctly (an entity with extra components
      beyond the two queried for is still matched).
- [x] `Archetype::column_pair_mut`'s `unsafe` block carries a
      `// SAFETY:` comment stating the actual invariant, per
      `coding-standards.md`'s requirement.
- [x] `docs/architecture/execution-model.md` exists, covering the five
      invariants, what's implemented, and what's deliberately deferred.
- [x] `cargo build`/`clippy -D warnings`/`test`/`fmt --check` clean
      across the full workspace, with and without `winit-backend`.

## Status

Implemented. `Tick(u64)`, resource storage, and `query2`/`query3`/
`query2_mut` all exist in `canary-ecs` with passing tests; the
execution-model document is written. The scheduler itself, command
buffers, events, first-class time types, and a fully generic `Query<D>`
trait remain real, intended future work — see "Explicitly not in scope"
above.
