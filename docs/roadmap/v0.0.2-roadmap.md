# v0.0.2 Roadmap

Per the release cadence recorded in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete),
`v0.0.2` has **one** primary focus: the archetype-based ECS migration.
Tier A (WASM) plugin loading, real windowing, and rendering are
deliberately *not* in this release — each gets its own `0.0.x` release
later, per that same cadence policy — see
[`future-roadmap.md`](future-roadmap.md) for the current ordering.

## Why the ECS migration is the right first `v0.0.2` focus

Of the items deferred out of `v0.0.1`
(see [`v0.0.1-roadmap.md`](v0.0.1-roadmap.md#definition-of-done-for-the-unqualified-v001--revised)),
the archetype ECS migration is the one nearly everything else in the
engine's near-term future depends on, directly or indirectly:

- [ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md)
  (component identity across the language boundary) is explicitly
  supposed to be prototyped *alongside* this migration, not after it —
  doing them together, once, is cheaper than doing the ECS migration and
  then reopening it later for identity concerns.
- Change-detection query filters — needed by both future networking
  replication and editor hot-reload — depend on the storage layout this
  migration establishes.
- The near-term scope of [`state-and-versioning.md`](../architecture/state-and-versioning.md)
  (persistent identity, distinct from runtime `Entity` identity) is
  cleanest to design against the *final* ECS storage shape, not the
  `v0.0.1` placeholder that's about to be replaced.

Tier A WASM plugin loading, by contrast, is comparatively independent —
it depends on Tier B (already shipped) and benefits from, but doesn't
strictly require, the archetype migration to land first. It's next
(`v0.0.3`), not concurrent, specifically to honor "one focused subsystem
per release" rather than parallelizing two big, independent efforts and
diluting attention on both.

## Scope

1. **Archetype-based component storage.** Entities with the same
   component set stored contiguously (an archetype table), replacing the
   `v0.0.1` placeholder's `HashMap<TypeId, HashMap<u32, Box<dyn Any + Send
   + Sync>>>` per-type storage. See
   [`core-runtime.md`](../architecture/core-runtime.md#ecs-architecture)
   for the target design this implements.
2. **Cached queries** over archetype tables, replacing the placeholder's
   linear scan.
3. **Change-detection query filters** (has this component been written
   since system Y last ran) — designed and implemented as part of this
   migration, not bolted on after, per
   [`core-runtime.md`](../architecture/core-runtime.md#known-limitations)
   and risk register R-13.
4. **A first cut at stable component schema identity**, per
   [ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md) —
   enough to validate the "string+version identity, `TypeId` stays a
   host-internal fast-path lookup" direction that ADR proposes, informed
   by actually building the archetype storage rather than decided from a
   desk review. This is expected to be the part of this release with the
   most design uncertainty going in; scope may narrow once prototyping
   starts, and that's an acceptable, expected outcome — not scope creep,
   the opposite of it.

**Explicitly not in `v0.0.2`**: the parallel job-stealing scheduler
(depends on this migration existing first, and is its own significant
effort — a candidate for `v0.0.2`'s immediate follow-up rather than
bundled in with it, to be scoped when this release is closer to done);
Tier A WASM plugin loading; real windowing; rendering; physics;
networking; the UI toolkit implementation; anything from
[`state-and-versioning.md`](../architecture/state-and-versioning.md)
beyond the persistent-identity groundwork implied by item 4 above.

## Definition of done

- `canary-ecs`'s public API (`spawn`, `insert`, `get`, `query`, ...)
  is backed by archetype storage, with existing tests
  (`engine/canary-ecs/src/world.rs`) passing against the new
  implementation with minimal call-site changes — per
  [`core-runtime.md`](../architecture/core-runtime.md#ecs-architecture),
  some churn at call sites is expected and acceptable; a full rewrite of
  every test would suggest the public API wasn't as insulated from the
  storage change as intended.
- Change-detection query filters exist and are tested.
- [ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md)
  is updated — to `Accepted` if the proposed direction holds up, or
  superseded by a new ADR if prototyping reveals a better one — not left
  `Proposed` indefinitely once there's implementation experience to
  ground it in.
- `docs/architecture/core-runtime.md`'s "Known limitations" section is
  updated to reflect what's now resolved, the same discipline applied
  when `v0.0.1` closed out its own known limitations.
- All existing tests continue to pass; `cargo fmt`, `cargo test`, and
  (per [ADR 0009](../decisions/architecture-decision-records/0009-plugin-abi-versioning-and-extensibility.md)-style
  rigor) any new invariant this migration introduces gets a real test,
  not just a passing build.
