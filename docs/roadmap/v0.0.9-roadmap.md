# `v0.0.9` Roadmap: Real-Time Loop + `Transform` + ECS-Driven Rendering

Single focus, per [`docs/roadmap/v0.1.0-plan.md`](v0.1.0-plan.md#v009--real-time-loop--transform--ecs-driven-rendering):
the foundational release nothing above it is buildable without. Three
parts, in dependency order: a real-timed `App`/`Subsystem` loop, the
`Transform` primitive everything spatial depends on, and rendering that
draws actual `World` state instead of a hand-fed vertex buffer.

## Why this, and why bounded this way

`v0.1.0`'s bar is "a competent developer could write a real, small game
directly against Canary's runtime" — and none of that is expressible
without these three. Physics needs a timed loop and something to move;
rendering needs spatial state to draw; audio and UI need both. The
through-line, per the plan, is that **`Transform` is the single most
load-bearing new primitive**: rendering, physics sync, audio
spatialization, and UI anchoring all read or write it, so building it
once, early, and correctly is exactly the "if physics needs pieces of
the runtime or transforms first, build those first" instruction.

Bounded deliberately short of a real game loop: no swapchain/window
presentation (offscreen readback verifies every pixel assertion this
release needs — see below), no textures/materials/depth (the RHI stays
exactly at its `v0.0.6` scope), no App-level scheduler (the
ECS-owning subsystem holds the one canonical `Schedule`; promoting it
into `App` is real `v0.0.10`+ work). Each deferral is a named,
verifiable- later decision, not an oversight.

## Scope

### Part 1 — Real delta-time + wall-clock `App::run`

- `Subsystem::tick` gains a real delta-time parameter
  (`std::time::Duration`) — a breaking API change, made now rather
  than retrofitted once physics/audio timing depend on it being right.
- `App` gains a real wall-clock-timed loop (`App::run`, using actual
  elapsed time as `dt` each iteration until a caller-supplied
  `should_continue` says stop — what a running game uses) alongside
  the deterministic fixed-`dt` `App::run_for` (what tests use).
- Proven with a real sleep-based test (recorded `dt`s reflect actual
  elapsed wall-clock time, not the loop's own intent) plus ordering
  and shutdown-safety tests carried over and extended.

### Part 2 — `canary-transform`: `Transform`, `GlobalTransform`, hierarchy

- New crate `canary-transform`: `Transform { translation: glam::Vec3,
  rotation: glam::Quat, scale: glam::Vec3 }` — one always-3D
  representation for 2D and 3D alike (see
  [`docs/architecture/transform.md`](../architecture/transform.md) and
  [ADR 0017](../decisions/architecture-decision-records/0017-unified-transform-representation.md);
  no `Transform2D`/`Transform3D` split), `GlobalTransform(glam::Mat4)`
  caching the composed world-space matrix, `Parent(Entity)` /
  `Children(Vec<Entity>)` hierarchy components with sync-keeping
  `set_parent`/`remove_parent` helpers.
- `glam` becomes the project's math crate for graphics-facing types
  (pure-math, `no_std`-capable, zero transitive dependencies —
  verified via `cargo tree`, no pin needed).
- Hierarchy propagation is a system registered through
  `canary-scheduler` (`reads Transform/Parent`, `writes
  GlobalTransform`), parent-before-child via depth ordering each run —
  the scheduler's first proof against a real gameplay-shaped system,
  not just its own test doubles. Stale parents fall back to local
  transforms; write-time rejects self/cyclic parents loudly
  (`EcsError::HierarchyCycle`) while propagation itself still
  terminates on forged cycles.

### Part 3 — ECS-driven rendering via `canary-render-ecs`

- New bridge crate `canary-render-ecs` (above `canary-ecs` +
  `canary-render`, so `canary-render` keeps its verified zero
  dependencies): minimal `Renderable { vertices, color }` component,
  `extract_scene` (`World::query2::<GlobalTransform, Renderable>`),
  CPU-bake to NDC (Y-flip, painter-sort, fixed camera constants
  reused from the example), and `draw_baked_frame` through the
  unchanged RHI — reusing `hello_triangle`'s proven shader
  byte-verbatim. Zero RHI churn, zero new RHI-adjacent API.
- Schedule wiring: the ECS-owning subsystem holds `{ world,
  schedule }`, registering propagation FIRST then a bake system that
  writes a `BakedFrame` resource; the GPU draw happens explicitly
  after `schedule.run()` — the GPU never enters `Schedule`, per
  `rendering.md`'s extract-don't-query doctrine.
- `examples/spinning-cube` rewritten on the bridge (same 36-frame GIF
  output, no duplicated bake/sort code, no `unsafe`).
- Real-pixel proof: `#[ignore]`-gated readback tests (distinct colors
  per entity, moved-entity redraw through the full
  propagation→bake→draw chain, empty-scene clear) run live on GPU
  hardware and in CI's new `render-ecs-integration` job.

## Explicitly not in scope

- Swapchain / window presentation — offscreen readback verifies
  everything this release asserts; live presentation is scheduled for
  `v0.0.13` (see `v0.1.0-plan.md`), when interactive UI needs a real
  screen.
- Textures, materials, depth testing, blending, culling, index
  buffers, instancing, buffer updates, push constants / uniform
  buffers — the RHI surface is byte-for-byte its `v0.0.6` self; these
  are the named `v0.0.10` RHI work package.
- A camera component (fixed constants), a mesh asset type (flat
  per-entity color only — real meshes arrive with `v0.0.10` assets),
  App-level scheduler promotion, concurrent disjoint writes.
- Concave / interpenetrating scenes render with painter-sort
  artifacts by design (convex-only correctness, documented in both
  code and `rendering.md`) — a depth buffer fixes it properly later.

## Verified, not assumed

- **Wall-clock honesty.** `App::run`'s `dt`s are proven to measure
  real sleeps, not replays of a fixed value; `should_continue` is
  checked before the first tick (an already-closed window never
  ticks).
- **Propagation correctness.** Multi-level chains compose
  translations down the hierarchy; moving a parent updates
  descendants on the next run; rotation composes onto the parent;
  detach restores local-as-global; despawned parents fall back
  without panic. Write-back is read-before-write (exact-equality on
  deterministic recomposition), so idle ticks mark nothing changed —
  proven by a rerun test shown to fail on the old blind-write code.
- **Ordering proof.** The bake-after-propagation test fails with
  reversed registration and passes with propagation first; the
  access declarations make any other staging impossible under the
  solo-write rule.
- **Real pixels, twice.** The bridge's readback suite passes on real
  GPU hardware (3/3) and the rewritten example's GIF was decoded and
  inspected (480×360, 36 frames, three-faces-visible frame 0).
- Full workspace `build`/`clippy -D warnings`/`test`/`fmt --check`
  clean, plus `cargo doc` zero warnings and the `wasm32-wasip2`
  check; CI green on all platforms including the new
  `render-ecs-integration` job.
