# v0.0.1 Roadmap

This document defines what the **entire `v0.0.1` milestone** contains —
spanning every `-preN` release up through the unqualified `v0.0.1` — per the
versioning scheme in
[ADR 0006](../decisions/architecture-decision-records/0006-versioning-scheme.md).
It also states, explicitly, what this founding session actually delivered
versus what remains for later `-preN` releases within this same milestone.

## Why this scope, and not more

The founding brief for this project listed candidate areas for the first
milestone: repository, build system, engine core, plugin loader, logging,
memory foundation, platform abstraction, basic ECS, testing framework,
documentation standards — and asked for the actual scope to be decided
rather than assumed. The scope below was chosen using one filter: **can it
be built and validated headless**, with no display server, no GPU driver,
and no network dependency, in the environment this foundation was actually
built in? Everything that passes that filter is in `v0.0.1`. Windowing,
rendering, real plugin sandboxing (Wasmtime), physics, and networking all
fail that filter for different reasons (no display/GPU stack available to
validate against; WASM runtime integration is substantial scope on its own)
and are explicitly pushed to later milestones — see
[`future-roadmap.md`](future-roadmap.md).

## v0.0.1 scope (the whole milestone)

1. **Repository & governance** — license, contribution guidelines, code of
   conduct, security policy, issue/PR templates, CI.
2. **Documentation architecture** — the vision/architecture/decisions/
   roadmap/development/ui/research structure itself, populated with target
   designs even where implementation is later.
3. **Build system** — Cargo workspace + `xtask` orchestration (see
   [ADR 0005](../decisions/architecture-decision-records/0005-build-system-and-tooling.md)).
4. **Engine core (`canary-core`)** — the `App`/subsystem bootstrap,
   structured logging, and error-handling conventions.
5. **Logging & memory foundation** — structured logging via `tracing`
   conventions; documented (not yet specialized) memory management policy.
6. **Platform abstraction (`canary-platform`)** — trait definitions
   (`Window`, `InputSource`) plus a headless/null implementation. Real
   windowing backend deferred (see
   [`docs/architecture/platform-abstraction.md`](../architecture/platform-abstraction.md)).
7. **Basic ECS (`canary-ecs`)** — a deliberately minimal, generational-index
   World with per-type component storage and synchronous system execution.
   The archetype/parallel-scheduler design is documented as the target in
   [`docs/architecture/core-runtime.md`](../architecture/core-runtime.md)
   but not implemented yet.
8. **Plugin loader interface (`canary-plugin-api`)** — the `Plugin` trait
   and capability-declaration types, plus a working **native (Tier B)**
   loader. The **sandboxed WASM (Tier A)** loader is designed
   (see [`docs/architecture/plugin-system.md`](../architecture/plugin-system.md))
   but not implemented.
9. **Testing framework** — `cargo test` wiring across all crates, with at
   least one meaningful test per crate; `proptest` added as a dependency for
   property-based testing of `canary-ecs`'s core invariants.
10. **Documentation standards** — doc-comment conventions and the ADR
    process itself (see
    [`docs/development/coding-standards.md`](../development/coding-standards.md)).

## What this founding session delivered (v0.0.1-pre1)

Everything in the scope list above, at a **minimal-but-real** level: the
workspace compiles, `cargo test --workspace` passes, and `canary-runtime`
runs as a headless boot harness that initializes logging, spins up an ECS
`World`, spawns a few entities to prove the API, attempts to load plugins
from a directory (logging "none found" when empty, since no plugins exist
yet), and shuts down cleanly. See
[`milestones.md`](milestones.md) for the exact, dated record of this.

## What's explicitly deferred to `v0.0.1-pre2` and beyond (still within this milestone)

- Wasmtime-backed Tier A (WASM component) plugin loading.
- A real windowing backend (`winit`) behind the `canary-platform` traits,
  once there's an environment to build and test it against.
- Archetype-based ECS storage and the parallel job-stealing scheduler.
- Change-detection query filters (needed by both the editor's future
  hot-reload story and by networking's future replication, per
  [ADR 0007](../decisions/architecture-decision-records/0007-networking-and-multiplayer-model.md)).
- Expanding `xtask` beyond basic orchestration into asset-cooking and
  packaging commands, once there's an asset pipeline to cook for.

None of the above blocks calling `v0.0.1-pre1` real, working progress — it
blocks calling it the *complete* `v0.0.1` milestone, which is exactly the
distinction the `-preN` scheme exists to make explicit.

## Definition of done for the unqualified `v0.0.1`

The milestone graduates from `-preN` to the unqualified `v0.0.1` when all
ten scope items above are implemented (not just designed) and the project
judges the result "stable enough for public use" per
[ADR 0006](../decisions/architecture-decision-records/0006-versioning-scheme.md) —
notably, this still does **not** require rendering, physics, or networking;
those remain later milestones (`v0.0.2`+ or `v0.1.0`, to be scoped in their
own roadmap updates when this milestone nears completion).
