# v0.0.1 Roadmap

This document defines what the **entire `v0.0.1` milestone** contains —
spanning every `-preN` release up through the unqualified `v0.0.1` — per the
versioning scheme in
[ADR 0006](../decisions/architecture-decision-records/0006-versioning-scheme.md).

## Why this scope, and not more

The founding brief for this project listed candidate areas for the first
milestone: repository, build system, engine core, plugin loader, logging,
memory foundation, platform abstraction, basic ECS, testing framework,
documentation standards — and asked for the actual scope to be decided
rather than assumed. The scope below was chosen using one filter: **can it
be built and validated headless**, with no display server, no GPU driver,
and no network dependency, in the environment this foundation was actually
built in? Everything that passes that filter is in `v0.0.1`. Windowing,
rendering, real plugin sandboxing (Wasmtime), physics, and networking all
fail that filter for different reasons and are pushed to later milestones —
see [`future-roadmap.md`](future-roadmap.md).

## v0.0.1 scope (the whole milestone)

1. **Repository & governance** — license, contribution guidelines, code of
   conduct, security policy, issue/PR templates, CI, and (added while
   completing this milestone) a governance/succession document and a
   living architectural risk register.
2. **Documentation architecture** — the vision/architecture/decisions/
   roadmap/development/ui/research/reviews structure itself, populated
   with target designs even where implementation is later, and kept
   synchronized with what's actually implemented.
3. **Build system** — Cargo workspace + `xtask` orchestration (see
   [ADR 0005](../decisions/architecture-decision-records/0005-build-system-and-tooling.md)),
   with CI and local tooling actually agreeing on what passes.
4. **Engine core (`canary-core`)** — the `App`/subsystem bootstrap,
   structured logging, and error-handling conventions.
5. **Logging & memory foundation** — structured logging via `tracing`
   conventions; documented (not yet specialized) memory management policy.
6. **Platform abstraction (`canary-platform`)** — trait definitions
   (`Window`, `InputSource`) plus a headless/null implementation.
7. **Basic ECS (`canary-ecs`)** — a deliberately minimal, generational-index
   `World` with per-type component storage and synchronous system
   execution, hardened (not expanded) for release: `Send + Sync`-bounded
   component storage and a widened 64-bit generation counter, both closing
   real correctness gaps identified by the August 2026 architecture review
   before they could become breaking changes later.
8. **Plugin loader interface (`canary-plugin-api`)** — the `Plugin` trait
   and capability-declaration types, plus a working, **versioned** native
   (Tier B) loader — the vtable ABI itself hardened with an explicit
   version field and forward-extension hook (see
   [ADR 0009](../decisions/architecture-decision-records/0009-plugin-abi-versioning-and-extensibility.md))
   before any plugin exists in the wild to be broken by a later change.
9. **Testing framework** — `cargo test` wiring across all crates, with
   meaningful tests per crate, `proptest` for ECS invariants, and a real
   cross-language integration test (a C plugin, compiled at test time,
   loaded through the actual native ABI).
10. **Documentation standards** — doc-comment conventions and the ADR
    process itself, including keeping ADRs and architecture docs
    synchronized with what's actually built (audited as part of
    completing this milestone).

## Definition of done for the unqualified `v0.0.1` — revised

**This supersedes this document's original "definition of done," which
required all ten scope items above to include the *target* designs
(archetype ECS storage, the parallel job-stealing scheduler, the
Wasmtime-backed Tier A loader, a real `winit` windowing backend) before
`v0.0.1` could ship unqualified.** On review, holding a foundation-laying
release to a bar that includes several genuinely large, independent
engineering efforts was scope creep against this project's own stated
versioning philosophy — `v0.0.1` is defined as "the first foundational
development milestone," not "the first feature-complete milestone," and
a release that keeps growing its own definition of done every time a
harder subsystem gets designed is a release that never ships. This
revision is itself an exercise of the judgment
[ADR 0001](../decisions/architecture-decision-records/0001-record-format.md)
asks every load-bearing decision to receive: stated plainly, with the
alternative (the original, larger bar) named rather than silently dropped.

**The unqualified `v0.0.1` is the ten scope items above, each real and
correct at the depth described, with every architectural risk found in
[the August 2026 review](../reviews/2026-08-senior-architecture-review.md)
that was cheap to fix now either fixed or explicitly, permanently
deferred with a stated reason** — not every possible future capability of
each subsystem. Concretely, `v0.0.1` does **not** include, and these are
now formally `v0.0.2`+ scope (see [`future-roadmap.md`](future-roadmap.md)
for the dependency graph among them):

- Archetype-based ECS storage and the parallel job-stealing scheduler.
- The Wasmtime-backed Tier A (sandboxed WASM) plugin loader.
- A real windowing backend (`winit`) behind the `canary-platform` traits.
- Change-detection query filters (depend on the archetype migration).
- Rendering, physics, networking, and the editor — never in scope for
  `v0.0.1` under any version of this document.

None of this is a lowering of quality — it's a narrowing of surface area.
Everything that *is* in `v0.0.1` is held to a high bar: correct, tested,
documented accurately, and free of known-cheap-to-fix architectural risk.
See [`docs/reviews/RELEASE_CHECKLIST.md`](../reviews/RELEASE_CHECKLIST.md)
for the specific, checked-off verification this claim rests on.

## What actually shipped, across both sessions that produced `v0.0.1`

- **Foundation session (`v0.0.1-pre1`)**: repository, governance,
  documentation architecture, seven ADRs, and a compiling, tested
  workspace implementing the ten scope items at a minimal-but-real level.
- **Architecture review**: a critical self-audit producing three more
  ADRs, a governance document, a risk register, and several config/docs
  fixes (no program logic changed).
- **This session (`v0.0.1`)**: the highest-priority risks the review
  flagged as cheap-now/expensive-later were fixed (ABI versioning, ECS
  `Send + Sync` bounds, the generation-width correctness gap, local/CI
  tooling parity); every ADR and architecture doc was audited against the
  actual implementation and corrected where they'd drifted; the
  milestone's own definition of done was revised for the reasons above;
  and the release was prepared (CHANGELOG, release notes, version bump).

See [`milestones.md`](milestones.md) for the full dated record.
