# `v0.2.0` roadmap — from integration proof to a broadly useful platform

> **Status: proposed (2026-10-24), pending maintainer approval.** Written during the
> [`v0.1.0` final review](../reviews/2026-10-24-v0.1.0-final-review.md) against audited
> commit `ebc8f7f4103de6a8adfa3ae8f7bc25f778ed97c5`. Nothing here is implemented
> because it is planned. ADR-level items are *proposals* until accepted. The
> governing rules are in
> [`capability-roadmap-principles.md`](capability-roadmap-principles.md); the longer
> arc is in [`future-roadmap.md`](future-roadmap.md) and
> [`../vision/long-term-roadmap.md`](../vision/long-term-roadmap.md).

## Purpose

`v0.1.0` proves that Canary's subsystems compose into one small game. `v0.2.0` has
a different job: make **several kinds of games practical** without each one
re-implementing the same missing fundamentals, and make building them fast
enough that developers can iterate. It is the first major *breadth* expansion:
gameplay, physics, rendering, assets, animation foundations, audio, UI, input,
world composition and developer workflow all advance together, and the
production-readiness work (performance budgets, security, compatibility, failure
behavior) lands in the same release as the capability it protects.

## What `v0.1.0` does and does not give a developer

Every answer below is backed by evidence from the review; "example-owned" means
a consumer must copy or rewrite code that lives in `examples/`, not in an engine crate.

| Question | Answer at `v0.1.0` | Evidence |
|----------|--------------------|----------|
| Can a developer build and run one complete small game? | **Yes** | `examples/collectathon`: headless proof, windowed run, replicated session and shared edit, all green in CI at the audited commit |
| ...without writing renderer or loop glue? | **No** | Sample owns a 500-line `ScenePipeline` (`scene.rs`), WGSL compile via `naga` (`shader.rs`), a 192-line HUD painter, a 505-line windowed `main`, and a hand-written fixed-step accumulator (`MAX_STEPS_PER_FRAME = 4`); `ui-game` duplicates the pipeline. There is no facade crate (documented) |
| A meaningful 2D game with physics gameplay? | **Partly** | `canary-physics` (Rapier2D) steps bodies, but the public surface has no collision events, queries, sensors, joints or character controller; the sample detects pickups with a radius check (`COLLECT_RADIUS_PX`) |
| A basic 3D game with camera, materials, lighting, collisions, character movement? | **No** | Perspective path uses a fixed virtual camera (`CAMERA_DISTANCE`); the RHI has no depth attachment (`docs/architecture/rendering.md`; the bridge sorts triangles on the CPU), no mip chain, one texture binding, no engine-owned materials or lights; physics is 2D only |
| Compose reusable worlds and objects instead of hardcoding? | **Partly** | Authored documents with one-level prefab inheritance (`canary-state`); no scenes, nested prefabs or spawn API |
| Import, validate, iterate on content without rebuilding? | **No** | Budgeted loaders for PNG, GLB and WAV exist; hot reload, cooking, dependency tracking and async loading are explicitly deferred (`canary-assets` crate docs) |
| Meaningfully different genres without the same missing fundamentals? | **No** | Every example is a variation of one top-down demo |
| Inspect and profile runtime behavior? | **No** | `tracing` logs only; no inspector, profiler or replay |
| Input beyond keyboard and mouse? | **No** | No gamepad code (`gilrs` or equivalent) anywhere in the tree |
| Multiplayer beyond one machine? | **No** | QUIC server binds loopback only (`ensure_loopback_bind`); client authentication is not built (documented in ADR 0027) |
| Add features without destabilizing consumers? | **Partly** | ADR-governed crates and a versioned plugin ABI; no API-stability policy, no semver checking, git-or-path dependency only |

## The `v0.2.0` success statement

> A developer can choose one of three genres: a **2D action game**, a **basic 3D
> third-person game**, or a **2 to 4 player co-op game over a LAN**. They build it
> from the facade crate with game code only (a `main` of roughly 200 lines or
> fewer), iterate on content with hot reload, inspect and profile it while it
> runs, test its logic headlessly in `cargo test`, and produce a packaged build,
> without writing a renderer pipeline, input plumbing, physics event plumbing or
> a network authentication scheme.

## Delivery shape: a dependency-ordered train

Follow the established `0.0.x` practice: each slice below is a milestone with its
own release notes, cut as `v0.2.0-preN` when its acceptance evidence exists, and
`v0.2.0` is cut when the [exit criteria](#exit-criteria-for-v020) are met. Remediation
of the review's findings ships first (workstream W0) as `v0.1.x` patch releases,
because `v0.2.0` must not start on top of known foundational gaps.

Effort is relative, not calendar time. **S** is a fraction of a `0.0.x` milestone,
**M** is about one, **L** is two to four. Uncertainty is stated because several
items (3D, networking, asset pipeline) have unknowns that only a first
implementation resolves.

## Slices at a glance

| Slice | Games it makes practical | Initiatives |
|-------|--------------------------|-------------|
| **S0 Remediation** | (prerequisite) | `V2-00` |
| **S1 Write a game, not an engine** | every genre: removes about 1,200 lines of per-game glue | `V2-01`, `V2-02` |
| **S2 2D action game** | arcade, top-down, platformer, shoot-em-up | `V2-03`, `V2-04`, `V2-05`, `V2-06`, `V2-07` |
| **S3 Basic 3D game** | third-person collect, obstacle course, walking simulator | `V2-08`, `V2-09` |
| **S4 Iterate fast** | all genres: edit, reload, inspect, profile, test | `V2-10`, `V2-11` |
| **S5 Play together** | LAN co-op and versus | `V2-12` |
| **S6 Scale and safety foundations** | enables budgets, parallelism, plugins and platforms | `V2-13`, `V2-14`, `V2-15` |

## Dependency order

```
V2-00 remediation ─┬─► V2-01 app runner/facade ─┬─► V2-03 2D renderer ──► V2-05 animation
                   │                            ├─► V2-11 diagnostics   └─► V2-08 3D renderer ─► V2-09 3D physics
                   ├─► V2-13 ECS events/order ──┼─► V2-04 physics gameplay surface ─► V2-12 networking v2
                   │                            └─► V2-07 scenes/prefabs/registry ─► V2-10 asset pipeline/hot reload
                   └─► V2-02 packaging/gates         V2-06 input/audio/UI (parallel after V2-01)
                       V2-14 Tier A, V2-15 platforms (parallel, gate the release)
```

Reasons for the order:

1. `V2-00` first: the review found items that change how later work is built
   (load budgets, decode depth limits, release mechanics).
2. `V2-01` and `V2-13` before feature slices: a facade and an event/ordering
   model are needed by every later capability's integration story.
3. `V2-07` (component registry) before `V2-10` and `V2-11`: hot reload of
   authored data, the inspector and prefab spawning all need the same
   type-registry boundary.
4. `V2-03` before `V2-08`: GPU instancing, descriptor sets and a pipeline
   abstraction are prerequisites shared by 2D and 3D rendering.
5. `V2-04` before `V2-12`: prediction needs deterministic, queryable gameplay
   physics.

## Design boundaries to settle now (proposed ADRs)

These are written as **Proposed** ADRs during `v0.2.0` so that later releases do
not need rewrites. None of them requires building the full system early.

| Proposed ADR | Boundary | Why now | Needed by |
|--------------|----------|---------|-----------|
| Frame/render graph | Pass declarations, resource lifetimes, per-pass attachments | The sample hardcodes a scene pass plus a UI pass; 3D, shadows and post-processing all need passes | `V2-03`, `V2-08`; shadows, post-processing later |
| Asset identity and cooking | Stable IDs, dependency edges, import settings, versioned cooked formats | Hot reload, atlases, streaming and platform builds all hang off identity | `V2-10`; streaming and large worlds later |
| Component registry (reflection-lite) | Type registration with serialization, inspection and editing hooks | Prefabs, inspector, replication schemas and hot reload otherwise each invent one | `V2-07`, `V2-10`, `V2-11`, `V2-12` |
| Ordering and parallelism | System sets, explicit before/after, access-conflict validation, change detection | Registration order is currently the only ordering mechanism | `V2-13`; parallel execution later |
| Animation data model | Skeleton, clip, graph, sampler as assets | Sprite animation must not paint skeletal animation into a corner | `V2-05`; skeletal and IK later |
| Telemetry | Spans, counters, GPU timestamps, exporters | Profiling must not be retrofitted per subsystem | `V2-11`; production profiling later |
| World streaming | Origin rebasing, chunked scenes, spatial index | Large worlds change coordinate and loading assumptions | design only in `v0.2.0` |
| Network security | Authentication, binding policy, resource limits | Any non-loopback bind is a security change | `V2-12` |
| API stability | `0.x` semver policy, deprecation, plugin ABI compatibility | A facade crate creates a consumer contract | `V2-01`, `V2-02` |
| Platform tiers | Supported OS and GPU matrix, per-tier evidence | Prevents unverifiable platform claims | `V2-15` |

## Initiatives

Priorities: **P0** blocks the slice or the release; **P1** is expected in `v0.2.0`;
**P2** is valuable and may slip with a recorded reason. Finding IDs refer to the
[review's findings register](../reviews/2026-10-24-v0.1.0-final-review-findings.md).

### V2-00 Audit remediation (workstream W0)

- **Problem:** the review found items that change how later work is built.
- **Pillar:** 7 (also 1 and 6). **Today:** Integrated CI, no confirmed Blocker, three High findings.
- **End state:** every High and Medium finding is fixed or explicitly accepted with a
  recorded justification; every fix lands with its regression test.
- **Needs:** maintainer decisions on stable promotion (`CANARY-REL-001`) and version bump
  procedure (`CANARY-REL-002`).
- **Acceptance:** `v0.1.0` gates re-run on the exact tagged commit; decode depth bounded
  (`003`); load budgets everywhere (`009`); Tier A aggregate budgets (`008`); the
  localization gate checks the shipped files (`010`); the proposed tests in the review
  bundle are merged and green.
- **Proof:** the proposed test bundle plus CI evidence on the final commit.
- **Effort:** M, low uncertainty. **Priority:** P0.
- **Defers:** the Low and Informational findings may follow as they touch the same files.

### V2-01 Engine-owned game loop and the `canary` facade crate

- **Problem:** a developer hand-writes window, presenter, color target, resize, UI frame,
  accumulator and schedule wiring (about 1,200 lines in the sample).
- **Pillar:** 1 (with 7). **Today:** Integrated pieces (`Runtime::drive_frame`,
  `FrameDriver`, `SimPasses`, `WinitWindow`, `VulkanPresenter`); loop and glue are example-owned.
- **End state:** `canary` facade crate with an `App` runner: engine-owned fixed-step
  accumulator (step, catch-up clamp, interpolation alpha), window and presenter lifecycle
  (resize, minimize, close, device loss), default scene and UI passes, documented stage
  conventions, headless mode, per-subsystem feature flags and a prelude.
  Workflow: `cargo new`, add one dependency, write a short `main`.
- **Needs:** `V2-13` (stage and event conventions), the API-stability ADR; `V2-03` for
  the default render passes (initially wrapping the current pipeline).
- **Acceptance:** `collectathon` rewritten on the facade with a `main` of 200 lines or
  fewer and no example-owned pipeline or loop code; the window, headless, resize and
  teardown proofs still pass through the facade; a "first game" tutorial is compiled
  by CI.
- **Requirements:** no new `unsafe`; typed lifecycle errors (closes ADR 0024 item 6);
  loop overhead measured and budgeted.
- **Proof:** the proposed frame-sequence chaos test pointed at the engine-owned
  accumulator (including clamp and alpha); the existing ignored window tests via the facade.
- **Effort:** M, medium uncertainty (API shape). **Priority:** P0: it removes the largest
  per-game cost and every later initiative integrates through it.
- **Risks and alternatives:** premature API freeze (mitigate with the `0.x` policy);
  shipping only a cookbook was rejected because it leaves the gap in place.
- **Defers:** editor play-mode, mobile pause/resume. **Enables:** all samples, plugins, the editor.

### V2-02 Packaging, templates, API policy and release gates

- **Problem:** consumers use git or path dependencies, there is no template, and the
  release workflow publishes on a tag without an approval or evidence gate
  (`CANARY-REL-006`, `007`).
- **Pillar:** 7. **Today:** Exists (CI is strong; the publish path has never produced a release).
- **End state:** a project template (`cargo xtask new-game` or equivalent); verified
  `cargo package` (not `--no-verify`) or a documented reason; `cargo-semver-checks`
  informational on public crates; a `0.x` stability and deprecation ADR; release workflow
  with environment approval and a machine-checked evidence record (tree hash, CI run on the
  exact SHA, manual-evidence record); a `workflow_dispatch` dry-run; a promotion procedure
  that works under the repository rulesets; an explicit crates.io decision.
- **Acceptance:** dry run on a throwaway pre-release tag yields a draft release artifact;
  promotion rehearsed on a scratch repository; the template builds in CI; the evidence
  validator fails on SHA or tree mismatch.
- **Effort:** M, low-medium uncertainty. **Priority:** P0 for gates and promotion
  (needed to tag `v0.1.0` safely), P1 for crates.io readiness.
- **Alternatives:** stay git-only through `v0.3.0` (acceptable while the API moves).

### V2-03 GPU-driven 2D renderer: sprites, atlases, cameras, text, debug draw

- **Problem:** 2D is the commonest path and today needs an example-owned pipeline plus
  CPU-baked vertices.
- **Pillar:** 2. **Today:** Exists (`bake_*` CPU baking, `OrthoView`, textured and blended
  pipelines tested; one texture binding; no instancing).
- **End state:** `Sprite`, sprite sheets and atlases, `Camera2D` (zoom, follow, pixel
  snapping, viewports), layers, tint and flip, batched instanced draws, a basic tilemap,
  text via a font atlas, runtime-toggled debug draw, engine-owned shaders and pipelines,
  render graph v0 (scene pass, UI pass), RHI growth (descriptor sets, uniform buffers,
  instancing, mip chains).
- **Needs:** `V2-01`; asset identity from `V2-10` for atlases; the render-graph ADR.
- **Acceptance:** 10,000 animated sprites at 60 FPS on the reference GPU (llvmpipe numbers
  are regression signals only); the 2D sample has zero example-owned pipeline code;
  pixel-exact readback tests for blending, atlas lookup and camera transforms; validation
  layers clean.
- **Requirements:** no steady-state per-frame heap allocation (allocation-counter test);
  device-lost and out-of-memory are typed errors; a missing asset renders a placeholder and logs.
- **Proof:** ignored GPU tests under llvmpipe in CI; CodSpeed benchmarks for batching.
- **Effort:** L, medium-high uncertainty (RHI growth). **Priority:** P0.
- **Alternatives:** adopting `wgpu` was a different decision (ADR 0016 chose Vulkan via
  `ash`); revisit only through a new ADR.
- **Defers:** particles, 2D lighting, post-processing. **Enables:** `V2-05`, `V2-08`, debug draw.

### V2-04 Physics gameplay surface (2D)

- **Problem:** gameplay needs events, queries, filtering and a controller; the sample uses
  radius checks.
- **Pillar:** 3. **Today:** Integrated for stepping and structural reconciliation
  (`canary-physics` over Rapier2D; rebuild-on-change tests); no events, queries, joints
  or controller in the public surface.
- **End state:** contact events (enter, stay, exit) delivered as ECS events, sensors,
  collision groups and masks, queries (raycast, overlap, shape-cast, point), joints
  (fixed, revolute, prismatic, distance), a kinematic character controller, physics debug
  draw, documented determinism limits, backend capability flags on `PhysicsBackend`.
- **Needs:** `V2-13` events.
- **Acceptance:** the sample's pickups use sensor events; a platformer demo (moving
  platforms, slopes) runs headless with identical snapshot hashes across runs; event order
  is deterministic and tested; queries match a brute-force oracle in property tests; random
  stacks produce no panic or NaN.
- **Requirements:** budget 2,000 dynamic bodies per step at or under 4 ms (provisional).
- **Effort:** L (M for events and queries alone), medium uncertainty.
  **Priority:** P0 for events, queries, controller; P1 for joints.
- **Risks:** Rapier API churn; cross-CPU float determinism is documented, not promised.
- **Enables:** `V2-09`, `V2-12` prediction.

### V2-05 Animation foundations

- **Problem:** there is no animation; every game needs flipbooks, tweens and state machines.
- **Pillar:** 3. **Today:** Not present (no engine-owned implementation).
- **End state:** animation clip assets (sprite frames, property curves), an `Animator`
  component with a state machine (parameters, transitions, events), a tween and easing
  library, animation events delivered as ECS events, a versioned asset format, and an
  accepted data-model ADR that also covers skeletons, clips and graphs.
- **Needs:** `V2-03` atlases, `V2-13` events.
- **Acceptance:** a sprite character with idle, run, jump and attack states driven by the
  state machine in the 2D sample; an animation event triggers audio; playback is
  deterministic under the fixed step and replay; animator state is in snapshots.
- **Effort:** M, low-medium uncertainty. **Priority:** P1.
- **Defers:** skeletal animation, blend trees, IK (planned for `v0.3.0` and `v0.4.0`, designed now).

### V2-06 Input, audio and UI completeness

- **Problem:** no gamepad, no audio mixing or spatialization, no menu navigation or settings kit.
- **Pillar:** 6. **Today:** Integrated (actions and capture routing; rodio triggers; egui HUD).
- **End state:** gamepad support behind the platform trait (hotplug, dead zones, optional
  rumble); rebinding with persisted user config; text input; an audio mixer with buses
  (master, music, sfx, ui), volume, pitch, pan, 2D and 3D attenuation and streamed music;
  a menu stack with keyboard and gamepad focus navigation, a settings kit, HUD data
  binding, dynamic localization (arguments, plurals), and accessibility basics
  (UI scale, contrast, assistive-technology hooks where the UI backend supports them).
- **Acceptance:** the sample is fully playable with a gamepad only; rebinding persists
  across runs (temp config directory test); a bus volume change is verified on the headless
  audio capture; scripted menu-navigation test; plural-aware text in `en`, `de` and one
  language with more plural categories.
- **Requirements:** budget 64 voices mixed in under 1 ms per 10 ms buffer (provisional).
- **Effort:** M-L, medium uncertainty (gamepad CI needs injected events plus manual evidence).
  **Priority:** P1.

### V2-07 World composition: scenes, nested prefabs, spawn API, save slots, component registry

- **Problem:** worlds are hardcoded or one-level prefab documents; save and load are by hand.
- **Pillar:** 1. **Today:** Exists (authored documents) and Integrated (snapshots).
- **End state:** a component registry (type registration with serialization, inspection
  and replication hooks; ADR); scene documents with hierarchy, names and tags; nested
  prefabs with overrides and variants; a spawn and despawn API with deferred commands;
  additive scene load and unload; a save-slot API with metadata and versioned migration;
  bounded decode (depth and size).
- **Acceptance:** the sample's levels come from scene files with nested prefabs; authored
  to world to authored round-trip property tests; a schema-migration fixture test;
  load and unload returns entity counts to baseline (leak test).
- **Effort:** L, medium uncertainty. **Priority:** P0: the registry is needed by `V2-10`,
  `V2-11` and `V2-12`.
- **Risks:** reflection scope creep; start with explicit registration functions.

### V2-08 3D rendering v1

- **Problem:** a basic 3D game is not possible (fixed camera, no depth attachment,
  no materials or lights).
- **Pillar:** 2. **Today:** Exists (perspective bake with a fixed virtual camera and CPU
  triangle sorting; GLB mesh loader).
- **End state:** depth attachments in the RHI; `Camera3D` (perspective or orthographic,
  FOV, planes, viewport); mesh renderer with `Material` assets (unlit and a lit model with
  base color, metallic-roughness and normal maps); a directional light plus ambient;
  instanced meshes; frustum culling; glTF scene import producing entity hierarchies with
  materials; a shader and pipeline cache; mip chains and sampler state.
- **Needs:** `V2-03` (descriptor sets, instancing, render graph v0), `V2-10` (materials and shaders as assets).
- **Acceptance:** a third-person sample renders a glTF level with correct occlusion and
  lighting; pixel-readback tests for depth order, light direction and material tint; 1,000
  instanced meshes inside the budget; validation layers clean.
- **Effort:** L, high uncertainty. **Priority:** P1 (P0 for depth and camera).
- **Alternatives:** unlit plus vertex lighting only in `v0.2.0`, PBR in `v0.3.0`.
- **Defers:** shadow maps (stretch, P2), point-light clustering, post-processing, skeletal rendering.

### V2-09 3D physics v1 and 3D character controller

- **Problem:** a basic 3D game needs collisions and character movement.
- **Pillar:** 3. **Today:** Not present (2D only).
- **End state:** a 3D backend (Rapier3D) behind the extended `PhysicsBackend` (today
  `PhysicsDimension` has only `TwoD`); the same component vocabulary; events and queries at parity with 2D; a kinematic 3D controller;
  debug draw.
- **Acceptance:** the third-person character walks a mesh-collider level with slopes and
  steps; parity tests against `V2-04`; deterministic hash test; 500 dynamic bodies per step
  at or under 4 ms (provisional).
- **Effort:** L, medium-high uncertainty. **Priority:** P1.
- **Defers:** joints and ragdolls beyond the 2D set, vehicles, soft bodies.

### V2-10 Asset pipeline v1 and hot reload

- **Problem:** the edit, rebuild, relaunch loop is slow, and nothing validates content.
- **Pillar:** 4. **Today:** Integrated loaders with budgets and root confinement; hot
  reload, importers, async loading and caching are listed as deferred in the crate docs.
- **End state:** stable asset identities and a dependency graph; importers (PNG, GLB,
  audio, WGSL with reflection, FTL, scenes and prefabs) with import settings;
  `xtask assets cook|validate|list` producing a versioned manifest; runtime loading from
  loose files in development and cooked packs for shipping; file-watch hot reload with
  stable handles and keep-previous-on-error; async loading with budgets and priorities;
  memory budgets and eviction.
- **Needs:** `V2-07` registry (for authored data), the asset-identity ADR.
- **Acceptance:** a running sample reloads a changed texture, shader, locale file and
  prefab within 500 ms (provisional) without restart, proven by an integration test; a
  corrupt asset on reload keeps the previous asset live and logs a typed error; cooking is
  byte-deterministic; each importer has a bounded fuzz target in CI; every file read has
  a budget (resolves `009`).
- **Effort:** L, medium-high uncertainty (cross-platform file watching, shader reload mid-frame).
  **Priority:** P0 for validation and hot reload, P1 for packs and streaming.

### V2-11 Diagnostics: inspector, profiler, crash reports, replay, game test harness

- **Problem:** a running game cannot be inspected, profiled or tested beyond bespoke harnesses.
- **Pillar:** 5. **Today:** Exists (`tracing` logs only).
- **End state:** an inspector overlay (entity tree, component view and edit through the
  registry, resources, per-system timings); a profiler (CPU scopes plus GPU timestamps,
  Chrome-trace or Tracy export); a crash reporter (backtrace, version, last snapshot
  hash, recent logs, platform); deterministic input recording and replay with snapshot
  checkpoints; a `canary-test` crate for headless gameplay tests in `cargo test`.
- **Needs:** `V2-01`, `V2-07`, the telemetry ADR.
- **Acceptance:** live component edit visible in the next frame; an exported trace shows
  per-system and GPU spans; replaying a 60-second recorded session reproduces identical
  checkpoint hashes; a sample gameplay test runs under `cargo test` in under 2 seconds;
  an injected panic produces a crash report; profiler-disabled overhead is under 1% of
  frame time (benchmark).
- **Effort:** L, medium uncertainty. **Priority:** P0 for profiler and test harness,
  P1 for editing and replay.

### V2-12 Networking v2: play together

- **Problem:** the server is loopback-only and unauthenticated, and clients cannot hide latency.
- **Pillar:** 6. **Today:** Integrated over loopback (QUIC, replication, removal history,
  frame-tagged input, documented limits in ADR 0027).
- **End state:** an explicit opt-in non-loopback bind with authenticated clients (token,
  pre-shared key or client certificates, per the network-security ADR and a threat
  model); connection lifecycle (reconnect, resume, kick, timeouts); per-client bandwidth
  caps; interest-lite filtering; client-side prediction with server reconciliation for the
  local player; snapshot interpolation for remote entities; a test-only loss, latency and
  jitter transport wrapper; RTT, loss and bandwidth metrics in the profiler and inspector.
- **Needs:** `V2-04` (deterministic, queryable gameplay physics), `V2-07` registry, the network-security ADR.
- **Acceptance:** four clients on separate processes over a non-loopback interface play
  the co-op sample; an unauthenticated client is rejected; the proposed garbage-datagram
  and decoder-fuzz tests run in CI and the server stays responsive; with 100 ms RTT and 5%
  loss a prediction-smoothness metric stays inside a stated bound; server memory and CPU
  stay bounded at 16 clients.
- **Requirements:** server network work at 60 Hz with 16 clients at or under 2 ms (provisional).
- **Effort:** L, high uncertainty (prediction correctness). **Priority:** P1.
- **Defers:** rollback netcode, lag compensation, dedicated-server orchestration, NAT traversal.

### V2-13 ECS and scheduler foundations

- **Problem:** registration order is the only ordering mechanism; there are no typed
  events; change tracking exists only as a world-level tick baseline
  (`World::query_changed_since`, ADR 0014, used by replication) without per-system
  `Added` or `Changed` filters; scale is measured at 1,000 and 10,000 entities but has no budget.
- **Pillar:** 1. **Today:** Integrated (single-threaded stage scheduler with access declarations).
- **End state:** typed events with tick semantics; ergonomic change detection (`Added`,
  `Changed` filters and per-system last-run ticks) on top of the existing tick baseline;
  a command buffer for deferred structural changes; system sets with explicit before and
  after and cycle detection; access-conflict validation at registration; scaling
  benchmarks and budgets (the review measured the mutable two-component query at about
  6 times the cost of the read-only one and super-linear in entity count, and propagation of
  10,000 moving transforms at about 5.6 ms); the parallel-execution boundary designed (read
  and write sets already exist); per-system timings exposed to the profiler.
- **Acceptance:** events consumed by `V2-04` and `V2-05`; ordering-error tests (cycle,
  ambiguity); benchmark budgets (provisional: 100,000-entity three-component query at or
  under 1 ms, 100,000 spawns at or under 20 ms); the ECS chaos test still passes;
  migration notes for any breaking change.
- **Effort:** L, medium uncertainty. **Priority:** P0 for events and ordering, P1 for
  change detection, P2 for actual parallel execution (design only in `v0.2.0`).
- **Alternatives:** adopting an existing ECS crate would need an ADR and would replace the
  public `Entity` and `World` types; not recommended.

### V2-14 Plugin Tier A hardening and host API v2

- **Problem:** the guest resource budget is incomplete and the host API is too small to be useful.
- **Pillar:** 7 (and 1). **Today:** Exists (fuel per call, per-memory limit; no table or
  aggregate limits, `CANARY-REL-008`).
- **End state:** store-wide memory accounting, table-element and instance limits, epoch
  interruption for wall-clock bounds, bounded host-call arguments, trap-isolation tests,
  a host API for events, spawn, log, time and queries, a plugin SDK and template, a WIT
  versioning policy with compatibility tests.
- **Acceptance:** the proposed budget tests pass; a malicious-guest corpus (memory bomb,
  table bomb, infinite loop, deep recursion, giant allocation, trap storm) is contained
  with typed errors inside a time bound.
- **Effort:** M, low-medium uncertainty. **Priority:** P1 (the budget fix itself is P0 in `V2-00`).

### V2-15 Platform support tiers and evidence

- **Problem:** evidence is Linux-centric: CI proves Vulkan only on llvmpipe, Windows and
  macOS run unit tests, and live-device proof is a manual record from one machine.
- **Pillar:** 7. **Today:** Exists and Integrated for one OS family.
- **End state:** documented support tiers with evidence per tier; software-Vulkan windowed
  tests on Windows in CI; validation layers in CI; high-DPI and scale-factor handling;
  fullscreen and multi-monitor; device-loss recovery tests; Wayland teardown order verified.
- **Acceptance:** a tier table linking each claim to a CI job or a dated manual record;
  validation-layer job green (resolves `014`); device-lost injection passes; no "supported"

- **Effort:** M, medium uncertainty. **Priority:** P1.

## Exit criteria for `v0.2.0`

"All initiatives merged" is not an exit criterion. `v0.2.0` is cut when every item
below is demonstrated with evidence recorded in the release notes.

1. **Three genres from game code only.** A 2D action game, a basic 3D third-person
   game, and the 2D game as a 2 to 4 player co-op session are built from the facade
   crate with a `main` of roughly 200 lines or fewer and no example-owned renderer
   pipeline, loop, input plumbing or network-authentication code. CI builds all three and
   runs headless proofs; one windowed run of each is recorded as live evidence.
2. **A real iteration loop.** Hot reload of a texture, shader, locale file and prefab
   inside a running sample is proven by an automated test within the stated latency;
   the inspector and a profiler trace export are demonstrated; at least ten gameplay
   tests in the samples run through `canary-test` under `cargo test`.
3. **Real networking.** Four clients on separate processes over a non-loopback
   interface, authenticated; the garbage-datagram, decoder-fuzz and loss and latency
   tests pass in CI; an unauthenticated client is refused.
4. **Budgets, not anecdotes.** The provisional performance budgets below are replaced by
   measured budgets on a declared reference machine, and the named benchmarks block CI on
   regression while the rest stay informational.
5. **Hostile-input robustness.** Every untrusted-input decoder has a bounded fuzz or
   mutation test in CI; every file and network read has a size budget; every recursive
   wire or file type has a depth bound; the Tier A containment corpus passes; the threat
   model documents are current.
6. **Compatibility is stated and tested.** The `0.x` stability policy is accepted;
   snapshot, scene and asset formats carry versions with migration tests; plugin WIT
   versions have compatibility tests.
7. **Platform claims have evidence.** A support-tier table links each claim to a CI job
   or a dated manual record; validation-layer jobs are green.
8. **The release process works.** A dry run on a throwaway pre-release tag produced a
   draft release; the approval gate and the evidence validator were exercised; the stable
   promotion procedure was rehearsed under the repository rulesets.
9. **Documentation is checkable.** The first-game tutorial compiles in CI; a docs lint
   (links and index coverage) runs in CI; the ten proposed ADRs are accepted or deferred
   with a reason.
10. **Maturity is honest.** The [maturity snapshot](capability-roadmap-principles.md#maturity-snapshot-at-the-v010-candidate)
    is updated from evidence; no capability is listed above the level its evidence supports.

## Cross-cutting requirements

These apply to every initiative and are part of its definition of done.

- **Untrusted input:** bounded size, bounded depth, bounded allocation, a typed error, and
  a bounded fuzz or mutation test in CI. The review's proposed tests are the template.
- **Network:** no non-loopback bind without authentication; per-peer and per-server
  resource limits; flood and garbage tests.
- **Plugins:** no ambient authority; aggregate resource accounting; containment tests.
- **Failure behavior:** device loss, asset errors, disconnects and decode failures are
  typed, recoverable where possible, and covered by fault injection.
- **Compatibility:** every persisted or exchanged format is versioned and has a migration
  or rejection test; public API changes follow the `0.x` policy.
- **Performance:** each initiative names its budget (see below) and ships a benchmark.
- **Evidence:** claims are recorded as CI jobs or dated manual records; nothing is
  "supported" or "production-capable" without them.

## Program risks

| Risk | Effect | Mitigation |
|------|--------|------------|
| Breadth outruns depth | Shallow features counted as capabilities | The maturity rule: placeholders do not count; slice exit evidence |
| Renderer scope growth (`V2-03`, `V2-08`) | Slips every graphical slice | Render graph v0 only; shadows, post-processing and particles explicitly deferred |
| Single-maintainer capacity | Review and bus-factor risk | ADRs and tests as institutional memory; `GOVERNANCE.md` succession plan stays current |
| Third-party churn (Rapier, winit, egui, wasmtime, quinn) | Surprise breakage | Pin and test upgrades in dedicated PRs; keep Canary-owned trait boundaries |
| Determinism over-promised | Prediction and replay bugs | Scope claims to same binary and same OS; hash tests; document limits |
| Evidence environment (no real GPUs in CI) | Unverified platform claims | Dated manual-evidence records with a schema; software-Vulkan jobs for regressions |

## Non-goals for `v0.2.0` (and where they go)

Non-goals mark scope boundaries; they are not indefinite deferrals.

- **Editor and visual scripting:** design continues; `v0.3.0` builds editor foundations
  on the registry (`V2-07`), collaboration operations and the inspector (`V2-11`).
- **Skeletal animation, blend trees, IK:** data-model ADR now (`V2-05`); implementation in
  `v0.3.0` and `v0.4.0`.
- **Shadows beyond a single directional map, post-processing, GPU-driven culling:** stretch
  in `V2-08`; `v0.3.0` and `v0.4.0` via the render graph.
- **Rollback netcode and lag compensation:** after prediction proves out (`v0.3.0`).
- **Web and mobile targets:** a tier decision only in `V2-15`.
- **VR and large-world streaming implementation:** boundaries designed now (ADRs), built
  in later releases.

## What `v0.2.0` enables

- `v0.3.0`: editor foundations, skeletal animation and blending, PBR and shadows, async
  streaming, parallel scheduling, 3D joints, crates.io publication if the API has settled.
- `v0.4.0`: render-graph-driven GPU culling, large-world techniques, IK, production asset
  workflows, advanced networking.
- Later: studio workflows, cinematics and VR on top of the same registry, asset identity,
  telemetry and render-graph boundaries.
