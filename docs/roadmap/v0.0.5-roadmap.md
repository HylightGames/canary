# `v0.0.5` Roadmap: Localization (`canary-loc`)

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
a working, independently-tested `canary-loc` crate implementing the
`LocKey`/Fluent design in
[`docs/architecture/localization.md`](../architecture/localization.md)
and [ADR 0015](../decisions/architecture-decision-records/0015-localization-format-and-key-mechanism.md).

## Why this replaces what was pencilled in as `v0.0.5`

`status.md`'s `v0.0.4`+ sequencing named rendering as the release after
real windowing. That's overridden here, deliberately: localization is a
founding constraint ("no user-facing text is hardcoded, anywhere") that
gets cheaper the earlier it's load-bearing and more expensive the longer
call sites accumulate around its absence — the same "cheap now, expensive
later" logic `localization.md` already applies to project state and
versioning. Rendering remains real, scoped work; it simply isn't next.

## The two blockers this roadmap works around, not waits on

Two subsystems `localization.md` names as the natural long-term
consumers of `canary-loc` don't exist yet, and won't for a while:

- **`CanaryUI` doesn't exist.** Zero code; gated behind rendering and the
  editor (Era 5). `v0.0.5` cannot validate the `LocKey`-not-`&str`
  constraint against a real widget API, because there is no widget API.
- **`canary-assets` doesn't exist.** No real asset pipeline to load
  `.ftl` resource files through.

Neither blocks `canary-loc`'s *core* correctness from being proven now.
The plan is the same one `v0.0.3` used for proving Tier A capability
enforcement without a real plugin ecosystem yet existing to exercise it:
**direct, real tests against the crate itself**, not a UI or an asset
pipeline standing in as an integration harness it doesn't need to have.
Concretely:

- `LocKey` construction, key resolution, pluralization, and
  interpolation are tested by loading real `.ftl` strings and asserting
  on the resolved output — see "Verified, not assumed" below for what
  this has already confirmed empirically.
- Asset loading for `v0.0.5` is a **deliberate, visibly temporary**
  direct `std::fs::read_to_string` against a fixed `locales/<locale>/`
  directory layout — not a second, competing asset-loading mechanism
  that `canary-assets` will need to reconcile with later. Whoever builds
  `canary-assets` should expect to delete and replace this one function,
  not discover an accidental parallel system.

## Scope

1. **A new `engine/canary-loc` workspace crate**, with `fluent` and
   `fluent-bundle` as its load-bearing dependency (plus their pinned
   transitive dependencies — see "Verified, not assumed"). Per
   [ADR 0015](../decisions/architecture-decision-records/0015-localization-format-and-key-mechanism.md),
   `fluent-templates`, `fluent-fallback`, and `i18n-embed` are
   *deliberately not* dependencies of this first cut — see that ADR's
   "Alternatives considered" for the concrete, tested reasons (a real
   limitation in `i18n-embed 0.15.4`'s asset-loading, and
   `fluent-fallback`'s own documentation admitting its API isn't
   ergonomic yet).
2. **A `LocKey` newtype** (`canary_loc::LocKey`) wrapping a validated key
   string, plus a `loc::key!("some-key")` macro as the only ergonomic
   construction path. The macro validates key syntax (a non-empty
   string matching Fluent's identifier grammar) at compile time.
   **Not in scope for this macro**: validating that the key actually
   resolves against any particular locale's loaded `.ftl` files at
   compile time — a real, desirable win, deferred per ADR 0015 to
   whichever future release has `canary-assets`/`xtask` tooling to hang
   a build-time `.ftl`-reading step on.
3. **A `LocaleBundle` (naming to be finalized during implementation)**
   wrapping a `fluent::FluentBundle`, exposing `resolve(&LocKey, args:
   Option<&FluentArgs>) -> String` plus a way to report — via
   `tracing`, developer-facing only, per `localization.md`'s
   developer/player text distinction — when a key falls back to the
   default locale or fails to resolve at all, rather than silently
   returning a blank string.
4. **Locale-fallback-chain resolution via `fluent-langneg`** (already a
   transitive dependency of `fluent`), not `fluent-fallback`'s
   `Localization` abstraction — see ADR 0015. A requested locale that's
   unavailable falls back through a configured chain (typically ending
   at the locale development happens in), matching
   `localization.md`'s existing fallback design.
5. **The placeholder file-loading function** described above, clearly
   doc-commented as temporary and pointing at the future
   `canary-assets` replacement.
6. **Direct tests, no UI needed**, mirroring the rigor `v0.0.3`'s Tier A
   tests and `v0.0.4`'s windowing test established (test against the
   real thing, not a mock):
   - Round-trip a real `.ftl` resource string through `LocKey`
     resolution for a simple message, a pluralized message across
     multiple `$count` values, and a message with string interpolation.
   - A missing key resolves to a reported, developer-facing fallback
     event, not a panic and not a silent blank string.
   - A locale missing from the fallback chain correctly falls back to
     the configured default rather than erroring.
7. **`docs/architecture/localization.md`'s "Status in this foundation"
   section rewritten** for what's actually implemented after this
   release, replacing the "entirely architectural, nothing exists yet"
   framing that's now stale.

## Verified, not assumed

Building `fluent`/`fluent-bundle` and the wider ecosystem named in
`localization.md` against this sandbox's `rustc` 1.75 floor took more
pins than initially guessed, confirmed one real build error at a time in
a scratch crate rather than assumed from a prior session's partial
notes (which turned out to be incomplete — see below):

- **`rustc-hash = "=2.1.1"`** — `rustc-hash 2.1.3` (the default
  resolution) requires rustc 1.77+.
- **`unic-langid = "=0.9.5"` and `unic-langid-impl = "=0.9.5"`, pinned
  together.** `unic-langid-impl 0.9.6` uses `Option::is_none_or`
  (stabilized in rustc 1.82) directly in its source — not a declared
  `rust-version` mismatch Cargo catches up front, but a real compile
  error. Critically, **pinning `unic-langid-impl` alone isn't enough**:
  `unic-langid 0.9.6` itself hard-requires `unic-langid-impl = "^0.9.6"`,
  so `unic-langid` has to be downgraded to `0.9.5` too, which in turn
  requires `unic-langid-impl = "^0.9.5"` before the `0.9.5` pin on the
  impl crate can actually resolve. A prior session's notes had gotten as
  far as `tinystr = "=0.7.6"` without recording this `unic-langid`/
  `unic-langid-impl` pairing — likely exactly why that pinning pass
  didn't finish. Confirmed as the actual cause here, not assumed: with
  both pinned to `0.9.5`, `tinystr` resolves to `0.7.6` on its own
  (via `unic-langid-impl 0.9.5`'s `tinystr = "^0.7.0"` requirement) with
  no separate pin needed.
- **`fluent-templates`'s own transitive chain** (only relevant if a
  future release reconsiders it, since `v0.0.5` doesn't depend on it —
  see "Scope" above) needed **`block-buffer = "=0.10.4"`, `ignore =
  "=0.4.20"`, and `globset = "=0.4.14"`**, each because newer releases
  declare `edition = "2024"` outright (a hard parse-time wall under
  Cargo 1.75, not a compile error on this project's own code) rather
  than a `rust-version` field Cargo could reason about.
- **`rust-embed`, `rust-embed-impl`, and `rust-embed-utils`, pinned
  together to `"=8.11.0"`** (relevant only if `i18n-embed` is
  reconsidered later, per ADR 0015): `8.12.0` bumps to `sha2 ^0.11`,
  which pulls a `digest`/`block-buffer` major version requiring
  `edition2024`. `8.11.0` still resolves to `sha2 ^0.10.5` → `digest
  0.10.7` → `block-buffer 0.10.4`, all fine under 1.75.
- **A real runtime smoke test, not just a compile check**, against
  `fluent 0.16.1`/`fluent-bundle` directly (the crates `v0.0.5` actually
  depends on): parsed a real `.ftl` resource, resolved a plain message,
  resolved a pluralized message at `$count = 1` and `$count = 5`
  (confirming the `[one]`/`*[other]` CLDR plural-category branch
  actually fires correctly, not just that the syntax parses), and
  confirmed a missing key resolves to `None` rather than panicking.
  **A genuinely useful finding this surfaced**: `fluent-bundle` wraps
  every interpolated value in Unicode bidi-isolation marks (U+2068/
  U+2069) by default — correct, deliberate behavior for bidi-safe
  display, but something `canary-loc`'s own tests (and anything
  downstream doing exact string comparison, including a future
  `CanaryUI` snapshot test) need to either account for or disable via
  `FluentBundle::set_use_isolating(false)`. Worth documenting here
  precisely because it's the kind of thing that reads as a bug the
  first time a test fails on it.

All of the above should be re-verified at implementation time in case
the ecosystem has moved again, the same caveat every toolchain pin in
this project carries per
[`build-system.md`](../development/build-system.md#the-rustc-175-sandbox-validation-floor).

**Weblate**, named in `localization.md`'s broader context as a
zero-cost hosting option for community translation once real locale
files exist to host, was confirmed (by direct account, prior to this
roadmap being written) to offer free Libre hosting for qualifying
open-source projects up to 160k strings — not re-verified independently
here since it's a third-party hosting policy rather than something this
sandbox can build or run, and doesn't gate anything `v0.0.5` actually
implements.

## Explicitly not in scope

- **`CanaryUI` integration.** No widget API exists yet to integrate
  with; `canary-loc` is proven standalone, per "The two blockers this
  roadmap works around" above.
- **A real asset pipeline.** The `std::fs`-based placeholder loader is
  intentionally minimal and will be replaced, not extended, once
  `canary-assets` exists.
- **`fluent-templates`, `fluent-fallback`, `i18n-embed`, or any
  compile-time asset embedding.** See ADR 0015.
- **Compile-time validation that a `LocKey` resolves against real
  `.ftl` content.** The macro validates key *syntax* only — see
  "Scope," item 2.
- **Translator tooling or a Weblate integration.** Worth real locale
  content existing first; tracked as a future item, not this release's
  job.
- **Non-Fluent formats (gettext, ICU MessageFormat) as a runtime
  option.** One format, per ADR 0015 — no runtime format negotiation is
  planned.

## Definition of done

- [ ] `engine/canary-loc` exists as a new workspace member, building
      clean under this sandbox's `rustc` 1.75 floor with the pins above
      recorded in `build-system.md`.
- [ ] `LocKey` and the `loc::key!()` macro exist, with the macro
      rejecting a syntactically invalid key at compile time.
- [ ] A `LocaleBundle`-equivalent type resolves a `LocKey` (plain,
      pluralized, and interpolated cases) against a loaded `.ftl`
      resource, using `fluent`/`fluent-bundle` directly.
- [ ] Locale fallback (missing locale falling back to a configured
      default) works via `fluent-langneg`, tested against a real
      fallback scenario, not mocked.
- [ ] A missing key produces a developer-facing (`tracing`) fallback
      event rather than a panic or a silent blank string.
- [ ] The placeholder file-loader is doc-commented as temporary, naming
      `canary-assets` as its intended replacement.
- [ ] `docs/architecture/localization.md`'s "Status in this foundation"
      section is rewritten to match what's actually implemented.
- [ ] `docs/roadmap/status.md`'s subsystem map and `v0.0.4+` sequencing
      updated to reflect `v0.0.5` as localization, not rendering.
- [ ] [ADR 0015](../decisions/architecture-decision-records/0015-localization-format-and-key-mechanism.md)
      moved from `Proposed` to `Accepted` once the above lands.
- [ ] `cargo build`/`fmt --check`/`test`/`doc` clean; `clippy` verified
      if this sandbox can reach it this time, honestly flagged if not —
      the same open item every release has hit.

## Status

Not started. Scoped and ready to begin — including the toolchain
verification most releases have needed as a first step, already done
