# `v0.0.3` Roadmap: Tier A (Sandboxed WASM) Plugin Loading

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
the sandboxed, language-agnostic plugin tier
[ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)
and [`docs/architecture/plugin-system.md`](../architecture/plugin-system.md)
have described since `v0.0.1` but never implemented. Tier B (trusted
native) has been real since `v0.0.1`; this release is what makes "any
language with a Component Model toolchain can author a plugin" true
rather than aspirational.

## Scope

1. **A working Tier A loader in `canary-plugin-api`**, analogous to
   `NativePluginLoader` but backed by Wasmtime: load a WASI 0.2 /
   Component Model `.wasm`/`.cwasm` artifact, instantiate it with an
   explicit, per-instance capability grant, and expose it through the
   same `Plugin` trait Tier B already implements.
2. **WIT interface definitions** for, at minimum, the `Plugin` lifecycle
   (`name`/`on_load`/`on_unload`) and a first cut of ECS component
   access — a component reads/writes specific, named component types it
   declared up front. Worth studying before designing from scratch:
   [Wasvy](https://github.com/wasvy-org/wasvy), an existing
   WASI-Component-Model modding layer for Bevy, already exposes
   component bindings through WIT so mods in any Component Model
   language can read and write ECS components directly — a close
   real-world precedent for exactly this problem, on a comparable Rust
   ECS, worth learning from directly rather than reinventing blind
   (and worth re-checking for how current it still is by the time this
   release is actually implemented).
3. **Capability enforcement that's actually real for Tier A** — not the
   advisory-only `Capability` enum `v0.0.1` shipped. A component gets
   *no* ambient authority at instantiation; only the capabilities it was
   explicitly granted are reachable, enforced by the runtime boundary
   itself, not a runtime check that happens to catch violations.
4. **Capability declarations resolve through
   [`World::register_component`]/[`World::type_id_for_schema`]**
   ([ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md),
   `Accepted` as of `v0.0.2`) from day one, not a separate, ad hoc
   string-matching mechanism invented for this loader specifically. A
   Tier A component names a component type by its `SCHEMA_ID`; the host
   resolves that to a `TypeId` via the registry to actually grant
   scoped ECS access. This is the first real consumer of that registry
   beyond its own tests — see the registry's own doc comment on exactly
   this being "the seam" it was built for.
5. **A native-compilation proof of concept**: at least one path (a
   direct `wasmtime compile` invocation, or the equivalent
   `Engine::precompile_component` call) that produces an
   ahead-of-time-compiled artifact and loads it successfully, validating
   the "sandboxed and native-speed, not in tension" claim
   `plugin-system.md` already makes. A full build-pipeline integration
   (this becoming an automatic step of *publishing* a plugin) is
   explicitly not required — that's downstream of an asset/build
   pipeline that doesn't exist yet (Era 3) — but the mechanism itself
   should be proven, not just described.

## Explicitly not in `v0.0.3`

Each gets its own later release or era instead:

- **Real windowing** (`winit`-backed `canary-platform`) — next in
  sequence after this release, per
  [`docs/roadmap/status.md`](status.md#v003-sequenced-not-deeply-scoped-yet),
  but not bundled with it; a non-headless environment isn't needed to
  validate a plugin loader.
- **A scripting language layered on top of Tier A** (e.g. an embedded
  Lua compiled to a WASM component). [ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)
  explicitly leaves this as a possible future addition *once Tier A
  exists*, not a `v0.0.3` deliverable.
- **The plugin manifest format**, marketplace tooling, and capability
  review UX (risk register R-08; Era 6). There's no marketplace to serve
  yet.
- **Tier B signing/provenance** (risk register R-09). Unrelated to Tier
  A; Tier B's trust model is "already trusted by construction," not
  something this release changes.
- **The change-detection unification work named in
  [ADR 0014](../decisions/architecture-decision-records/0014-change-detection-as-shared-primitive.md).**
  Deliberately not ridden along with this release — it's a cross-cutting
  refinement best validated against Era 3 or Era 4's real needs, not
  built speculatively into a plugin loader that doesn't yet have a
  reason to touch it.
- **The parallel job-stealing scheduler.** Still its own, separately
  scoped piece of Era 2 — see `docs/architecture/core-runtime.md`.

## A note on scope risk, said honestly rather than discovered mid-release

This is a materially bigger lift than `v0.0.2`. The archetype ECS
migration was hard but self-contained — one crate, no new external
runtime dependency, no async, no second toolchain to compile test
fixtures with. Tier A adds: an async Wasm runtime (Wasmtime) as a real
dependency for the first time in this workspace, a WIT/Component Model
toolchain to author even a minimal test plugin, and (per the `v0.0.1`
Tier B precedent of testing against a *real* compiled artifact, not a
mock) a way to actually build a `.wasm` component at test time — which
depends on tooling (`cargo-component` or equivalent) this sandbox has
not yet confirmed it can reach or run against the `rustc` 1.75 floor
established for `v0.0.1`/`v0.0.2`. If that tooling turns out not to be
usable in whatever environment implements this release, the fallback is
a *pre-built* test fixture component checked into the repo (built once,
elsewhere, and verified reproducible) rather than one compiled fresh
every test run — a real but acceptable narrowing, in the same spirit
[ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md)'s
own scope was allowed to narrow during `v0.0.2`. Naming this now so it's
a recorded, deliberate fallback if it happens, not a surprise.

## Definition of done

- [ ] `canary-plugin-api` loads a real WASM component through Wasmtime
      and exposes it via the `Plugin` trait.
- [ ] WIT interfaces exist for the `Plugin` lifecycle and a first cut of
      component-scoped ECS access.
- [ ] Capability enforcement is real: a test proves a component *with* a
      granted capability can use it, and a component *without* it
      cannot — symmetric to Tier B's version-mismatch-rejection test
      from `v0.0.1`.
- [ ] Capability declarations resolve through the `v0.0.2`
      `CanaryComponent`/`register_component` registry, not a parallel
      mechanism.
- [ ] At least one AOT-compilation path is proven end to end.
- [ ] `docs/architecture/plugin-system.md`'s "Known limitations" updated
      (component identity's Tier A gap is closed; Tier A's
      not-yet-implemented note is removed).
- [ ] [ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)'s
      status line updated to note both tiers are now implemented,
      matching the pattern [ADR 0009](../decisions/architecture-decision-records/0009-plugin-abi-versioning-and-extensibility.md)
      already set for Tier B.
- [ ] Existing `canary-plugin-api` tests pass unmodified; new tests
      cover Tier A loading and capability enforcement specifically.
- [ ] `cargo build`/`fmt --check`/`test` clean; `clippy` verified if
      this sandbox can reach it this time, honestly flagged if not,
      matching every release so far.
