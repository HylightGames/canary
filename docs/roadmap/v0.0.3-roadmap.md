# `v0.0.3` Roadmap: Tier A (Sandboxed WASM) Plugin Loading

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
the sandboxed, language-agnostic plugin tier
[ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)
and [`docs/architecture/plugin-system.md`](../architecture/plugin-system.md)
have described since `v0.0.1` but never implemented. Tier B (trusted
native) has been real since `v0.0.1`; this release is what makes "any
language with a Component Model toolchain can author a plugin" true
rather than aspirational.

## Scope

1. **A working Tier A loader in `canary-plugin-api`**, analogous to
   `NativePluginLoader` but backed by a WASI 0.2 / Component Model
   runtime (Wasmtime): load a `.wasm` component, instantiate it with an
   explicit, per-instance capability grant, and expose it through the
   same `Plugin` trait Tier B already implements.
2. **A component data ABI — genuinely separate from component identity,
   and worth stating explicitly so it isn't accidentally conflated with
   it.** [ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md)
   solves "which component is this?" (a `SCHEMA_ID` string resolves to a
   host `TypeId`). It does not solve "what is the portable,
   cross-language representation of that component's *fields*?" — an
   arbitrary Rust struct has no inherent WIT representation, and nothing
   about resolving a `TypeId` tells a WASM component how to read or
   write one. The chain this release actually needs is identity
   (`SCHEMA_ID -> TypeId`, already built) *plus* a schema/data ABI
   (`SCHEMA_ID -> WIT record shape -> host adapter -> the TypeId's Rust
   value`, not yet built) — two different problems this item is the
   second of. **The first cut deliberately supports only a small,
   explicit set of schema-safe value types** — numeric primitives
   (`u32`/`i32`/`u64`/`i64`/`f32`/`f64`), `bool`, `string`, `list`, and
   `record` composed from those — not arbitrary native Rust components.
   Widening this set later is straightforward; walking back an
   accidentally-general foreign-reflection API is not, so this is a
   deliberate ceiling, not an oversight.
3. **WIT interface definitions** for, at minimum, the `Plugin` lifecycle
   (`name`/`on_load`/`on_unload`) and a first cut of ECS access, kept
   intentionally boring: `get`/`set`/`has-component`/`is-valid-entity`
   over the value types from (2) — not a general query/reflection
   surface. Worth studying before designing from scratch:
   [Wasvy](https://github.com/wasvy-org/wasvy), an existing
   WASI-Component-Model modding layer for Bevy, already exposes
   component bindings through WIT so mods in any Component Model
   language can read and write ECS components directly — a close
   real-world precedent for exactly this problem, on a comparable Rust
   ECS, worth learning from directly rather than reinventing blind
   (and worth re-checking for how current it still is by the time this
   release is actually implemented).
4. **Capability enforcement that's structurally real for Tier A** — not
   the advisory-only `Capability` enum `v0.0.1` shipped, and not merely
   "the host checks and rejects an unauthorized call at runtime." A
   component without a granted capability should have no way to *reach*
   the corresponding host function at all — nothing in its linked
   interface set to call — matching the Component Model's own
   host-provides-defined-interfaces design and the "never has an
   opportunity" framing `plugin-system.md` already commits to. A
   capability grant is a decision about what gets linked in at
   instantiation time, not an `if` statement inside an always-reachable
   host function.
5. **Capability declarations resolve through
   [`World::register_component`]/[`World::type_id_for_schema`]**
   ([ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md),
   `Accepted` as of `v0.0.2`) for *identity* specifically — resolving a
   `SCHEMA_ID` to the `TypeId` that gates scoped ECS access — which is
   distinct from, and doesn't by itself solve, the data ABI in (2).
   This is the first real consumer of the identity registry beyond its
   own tests.
6. **A baseline resource budget**, alongside the capability (authority)
   model above — a genuinely different sandboxing property. A component
   with *zero* granted capabilities can still attempt to exhaust memory
   or spin the CPU forever; "sandboxed" needs to mean both "can't reach
   what it wasn't granted" and "can't consume unbounded host resources."
   Doesn't need to be elaborate for a first cut — a default memory limit
   and an execution budget (Wasmtime's fuel or epoch-interruption
   mechanisms) applied to every Tier A instance establishes the
   principle. Tier A's sandbox is really three layers, worth keeping
   distinct when this is implemented: what a component can *access*
   (capabilities, item 4), how much it can *consume* (this item), and
   what it can *call at all* (the interface surface, item 3).
7. **A native-code-compilation path proven end to end**: at least one
   way (a direct `wasmtime compile` invocation, or the equivalent
   `Engine::precompile_component` call) to produce and successfully
   load a precompiled artifact. This proves the mechanism exists — WASM
   in, natively-executing code out, running correctly — not that it's
   fast; no performance claim is being made here, and none should be
   inferred from a successful load alone. The precompiled artifact
   (`.cwasm`) is an optimization/cache format tied to the exact engine
   configuration and target that produced it, **not a portable
   distribution format** — the canonical, distributable artifact stays
   the plain `.wasm` component; a `.cwasm` is a derived,
   environment-specific cache of it, roughly the relationship a `.pyc`
   has to a `.py`. A full build-pipeline integration (this becoming an
   automatic step of *publishing* a plugin) is explicitly not required —
   that's downstream of an asset/build pipeline that doesn't exist yet
   (Era 3) — but the mechanism itself should be proven, not just
   described.

## Explicitly not in `v0.0.3`

Each gets its own later release or era instead:

- **Real windowing** (`winit`-backed `canary-platform`) — next in
  sequence after this release, per
  [`docs/roadmap/status.md`](status.md#v003-sequenced-not-deeply-scoped-yet),
  but not bundled with it; a non-headless environment isn't needed to
  validate a plugin loader.
- **A scripting language layered on top of Tier A** (e.g. an embedded
  Lua compiled to a WASM component). [ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)
  explicitly leaves this as a possible future addition *once Tier A
  exists*, not a `v0.0.3` deliverable.
- **The plugin manifest format**, marketplace tooling, and capability
  review UX (risk register R-08; Era 6). There's no marketplace to serve
  yet.
- **Tier B signing/provenance** (risk register R-09). Unrelated to Tier
  A; Tier B's trust model is "already trusted by construction," not
  something this release changes.
- **The change-detection unification work named in
  [ADR 0014](../decisions/architecture-decision-records/0014-change-detection-as-shared-primitive.md).**
  Deliberately not ridden along with this release — it's a cross-cutting
  refinement best validated against Era 3 or Era 4's real needs, not
  built speculatively into a plugin loader that doesn't yet have a
  reason to touch it.
- **The parallel job-stealing scheduler.** Still its own, separately
  scoped piece of Era 2 — see `docs/architecture/core-runtime.md`.
- **Safe hot-unloading/reinstantiation with full resource reclamation.**
  `Plugin::on_unload` being *called* is in scope; guaranteeing every
  resource, handle, and ECS reference a component held gets safely
  reclaimed and the instance cleanly reinstantiated is a much bigger
  problem, especially once plugins can hold onto things across calls,
  and isn't solved by this release. `v0.0.3`'s unload is a logical
  lifecycle notification, not a hot-reload guarantee.

## A note on scope risk, said honestly rather than discovered mid-release

This is a materially bigger lift than `v0.0.2`. The archetype ECS
migration was hard but self-contained — one crate, no new external
runtime dependency, no second toolchain needed just to compile test
fixtures. Tier A adds a real external runtime dependency (Wasmtime) and
a WIT/Component Model toolchain to author even a minimal test plugin,
neither confirmed reachable from whatever environment actually
implements this release.

**Not necessarily an async dependency, though.** WASI 0.2 / the
Component Model as [ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)
committed to it is synchronous by design — imported functions appear
synchronous from the guest's perspective, and Wasmtime's embedding API
supports fully synchronous compilation and instantiation; its `*_async`
APIs are opt-in, needed only when a host function genuinely blocks on
I/O. Nothing in this release's scope (ECS reads/writes, lifecycle
hooks) is inherently I/O-bound, so the synchronous embedding API is
likely sufficient, and pulling in an async runtime (`tokio` or similar)
as a new workspace dependency is not something to presume up front.
That question only becomes live if a future capability (`Filesystem`,
`Network`) needs real blocking I/O — worth deciding *then*, against a
real need, not speculatively now.

**The Rust-version constraint is the more serious risk, and deserves an
explicit decision rather than "we'll see."** Checked directly rather
than assumed: Wasmtime's own stated policy is to support only the
latest three stable Rust releases at any given time, and its most
recent published releases require a minimum Rust version far newer than
the `rustc` 1.75 this sandbox installs via `apt` (Ubuntu Noble's
archive) — not a small gap, and one that only grows, since Wasmtime's
MSRV moves forward continuously with upstream Rust rather than holding
still. The `v0.0.1`/`v0.0.2` pattern of pinning an older-but-compatible
crate version (as done for `proptest`, `tempfile`, `libloading`) may
simply not have a solution here: an old-enough Wasmtime release to
compile under `rustc` 1.75 could plausibly predate this project's own
WASI 0.2 / Component Model commitment being stable upstream at all,
which would make it useless for this release's actual purpose, not just
inconvenient.

Before implementation starts, this needs to be resolved as a real,
documented decision, not discovered mid-release:

- Confirm whether any Wasmtime release satisfies *both* constraints
  (compiles under the `rustc` this sandbox can install, and supports
  WASI 0.2 / Component Model maturely enough for this release's scope).
  If one exists, pin it explicitly and record the pin here.
- If none does, the honest conclusion is that `v0.0.1`/`v0.0.2`'s
  "validate against this sandbox's `apt`-installed `rustc`" pattern
  doesn't extend to this release, and whatever environment actually
  implements `v0.0.3` needs a newer Rust toolchain than this sandbox
  currently provides — a real environment/tooling decision, not a
  reason to force an incompatible pin and call the release done.

Separately: per the `v0.0.1` Tier B precedent of testing against a
*real* compiled artifact, not a mock, this release also needs a way to
actually build a `.wasm` component at test time (`cargo-component` or
equivalent) — also unconfirmed in this sandbox. If that tooling turns
out not to be usable, the fallback is a *pre-built* test fixture
component checked into the repo, verified reproducible, rather than one
compiled fresh every test run — a real but acceptable narrowing, in the
same spirit [ADR 0010](../decisions/architecture-decision-records/0010-component-identity-across-language-boundary.md)'s
own scope was allowed to narrow during `v0.0.2`. If that fallback is
used, it needs reproducibility metadata alongside it (Rust version,
`wit-bindgen`/component-tooling versions, WASI version, target triple,
source commit, a checksum) — a golden artifact with a documented
recipe, not a `plugin.wasm` nobody remembers how to rebuild.
Naming all of this now so it's a recorded, deliberate set of decisions
if it happens, not a surprise.

## Definition of done

- [ ] A Wasmtime version is confirmed and pinned that satisfies both
      this workspace's Rust-version constraint and WASI 0.2/Component
      Model maturity — documented here, not assumed. If no such version
      exists, that finding is itself documented as the reason this
      release's toolchain floor had to move.
- [ ] `canary-plugin-api` loads a real WASM component through that
      runtime and exposes it via the `Plugin` trait.
- [ ] A component data ABI exists for a deliberately small set of value
      types (numeric primitives, `bool`, `string`, `list`, `record` of
      those) — not arbitrary Rust reflection.
- [ ] WIT interfaces exist for the `Plugin` lifecycle and the
      intentionally boring first-cut ECS surface (`get`/`set`/
      `has-component`/`is-valid-entity`) over that value-type set.
- [ ] Capability enforcement is structural, not merely checked-and-
      rejected: one test proves a component *with* a granted capability
      can use it; a second proves a component *without* it has no
      reachable way to even attempt it — not just that the attempt gets
      caught. Symmetric to, but stronger than, Tier B's
      version-mismatch-rejection test from `v0.0.1`.
- [ ] Capability declarations resolve through the `v0.0.2`
      `CanaryComponent`/`register_component` registry for *identity*,
      feeding the data ABI above for *representation* — not a parallel
      identity mechanism invented for this loader.
- [ ] A baseline resource budget (memory limit, execution/fuel budget)
      applies to every Tier A instance by default.
- [ ] At least one AOT-compilation path is proven end to end, described
      as a working native-code execution path — not a performance claim
      no benchmark backs up.
- [ ] If a prebuilt test fixture is used in place of compiling one at
      test time, it ships with reproducibility metadata: toolchain
      versions, target triple, source commit, checksum.
- [ ] `docs/architecture/plugin-system.md`'s "Known limitations" updated
      (component identity's Tier A gap is closed; Tier A's
      not-yet-implemented note is removed).
- [ ] [ADR 0003](../decisions/architecture-decision-records/0003-plugin-and-modding-architecture.md)'s
      status line updated to note both tiers are now implemented,
      matching the pattern [ADR 0009](../decisions/architecture-decision-records/0009-plugin-abi-versioning-and-extensibility.md)
      already set for Tier B.
- [ ] Existing `canary-plugin-api` tests pass unmodified; new tests
      cover Tier A loading, capability enforcement (both the positive
      and the structural-denial case), and resource-budget enforcement.
- [ ] `cargo build`/`fmt --check`/`test` clean; `clippy` verified if
      this sandbox can reach it this time, honestly flagged if not,
      matching every release so far.
