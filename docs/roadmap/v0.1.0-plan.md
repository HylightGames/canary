# `v0.1.0` Plan: A Real, Small Game Against Canary's Runtime

Recorded at the project owner's explicit direction (September 2026): the
bar for `v0.1.0` is not "every subsystem in `docs/architecture/` has an
API," it's **a competent developer could write a real, small game
directly against Canary's runtime, without bypassing the engine or
implementing fundamental engine systems themselves.** See
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#v010-sharpened-integration-not-a-checklist)
for the narrative version of this; this document is the concrete,
dependency-ordered sequence it implies, kept current as each release
lands (this is a living plan, not a one-time announcement — update it,
don't leave it to drift the way `future-roadmap.md` and `milestones.md`
were found to have drifted during the September 2026 documentation
sweep).

## The bar, per subsystem

Not "the crate exists and has tests" — "another real part of Canary
uses it":

- **Physics** moves an ECS `Transform`, driven by real collider/rigidbody
  components, not a standalone demo.
- **Rendering** draws actual `World` state (`Transform` + a renderable
  component) every frame, not a hand-fed vertex buffer like
  `examples/spinning-cube`.
- **Assets** feed the renderer and audio system real files from disk,
  not hardcoded Rust arrays.
- **Audio** plays real loaded sound assets, triggered by real game
  state.
- **`CanaryUI`** renders through the same RHI rendering already uses,
  and reads real input through the same path gameplay input does.
- **Project State** saves and loads a real `World` — enough of one that
  a saved/reloaded game continues meaningfully, not a serialization
  unit test against a toy struct.
- **Networking** replicates real component data between a real server
  and a real client process, not a loopback mock.
- **Live Collaboration** builds on Project State's serialization and
  Networking's transport — not a separate, disconnected feature.
- **Plugins** can participate in whichever of the above they have
  legitimate reason to touch (Tier A's existing `ReadEcsWorld`/
  `WriteEcsWorld` capabilities already prove the pattern; extending
  which capabilities exist is in-scope if a real subsystem below needs
  it) without bypassing the engine's structural enforcement.

## Why this order (dependency reasoning, not preference)

```
   canary-scheduler (v0.0.8, done)
          |
   App/Subsystem gets real delta-time + a real timed loop  <- v0.0.9
          |
   Transform + GlobalTransform + hierarchy (new crate)      <- v0.0.9
          |
   +------+-------------------+
   |                          |
ECS-driven rendering    (unblocks physics, audio-position,
(v0.0.9/10)               UI-in-world-space, later)
   |
Asset loading (v0.0.10) - meshes/textures feed the renderer above
   |
   +------------+-------------+
   |            |             |
Physics      Audio        CanaryUI
(v0.0.11)   (v0.0.12)    (v0.0.13)
   |
   +--- all three need Transform + (for audio/physics) the real
        timed loop; none need each other, so their relative order
        among themselves is low-stakes -- sequenced physics-first
        only because it's this project's own most-cited example
        subsystem, not because audio or UI genuinely depend on it
   |
Project State (v0.0.14) - a real World to save now exists,
   |                       with real components worth persisting
   |
Networking (v0.0.15) - reuses Project State's World-serialization
   |                    primitive for replication, doesn't reinvent it
   |
Live Collaboration (v0.0.16) - builds on both directly
   |
v0.1.0 - a real, small sample game exercising all of the above
         together, fixing whatever integration gaps that exposes
```

The through-line: **`Transform` is the single most load-bearing new
primitive**, needed by rendering, physics, audio (positional playback),
and UI (world-space anchoring) alike — building it once, early, and
correctly is exactly the "if physics needs pieces of the runtime or
transforms first, build those first" instruction this plan follows.
Similarly, **World serialization is built once** (for Project State)
and **reused, not reimplemented,** for Networking and Live
Collaboration — this is [ADR 0014](../decisions/architecture-decision-records/0014-change-detection-as-shared-primitive.md)'s
own "change detection as shared primitive" principle extended to
serialization itself, and is exactly the kind of architectural
reasoning this plan exists to make explicit rather than leave to be
rediscovered per-subsystem.

## The releases

### `v0.0.9` — Real-time loop + `Transform` + ECS-driven rendering

The foundational release: nothing above is buildable without it.

- `Subsystem::tick` gains a real delta-time parameter (`std::time::Duration`)
  — a breaking API change, made now rather than retrofitted once
  physics/audio timing depend on it being right.
- `App` gains a real wall-clock-timed loop (replacing `run_for(ticks:
  u32)`'s fixed tick count with no real-time relationship), with a real
  exit condition (a closed window, in the real-windowing case).
- A new crate, `canary-transform` (or equivalent — name decided at
  implementation time): `Transform` (position/rotation/scale, one
  representation serving both 2D and 3D — see
  [`docs/architecture/transform.md`](../architecture/transform.md) and
  [ADR 0017](../decisions/architecture-decision-records/0017-unified-transform-representation.md)),
  `GlobalTransform`, and a hierarchy-propagation system registered
  through `canary-scheduler`, proving the scheduler against a real
  gameplay-shaped system rather than only its own test doubles.
- `canary-render`/`canary-render-vulkan` gain a real integration point:
  a system that queries `World` for `GlobalTransform` + a simple
  renderable component and draws them, replacing
  `examples/spinning-cube`'s fully hand-fed vertex buffer approach (that
  example either gets rewritten on top of this or is explicitly
  superseded by a new one once this lands).

### `v0.0.10` — Minimal asset loading

Real files from disk feed the renderer `v0.0.9` built. Deliberately
minimal relative to `asset-system.md`'s full design (content-addressed
cooking, importers-as-plugins, hot reload) — those remain real,
intended future work, not required for `v0.1.0`'s bar. What's required:
`AssetId`/`AssetHandle<T>` (the runtime-facing API surface
`docs/architecture/execution-model.md`'s "Queries" section already
flagged as the genuinely-still-open half of asset identity, content
-addressing itself having been decided already), and a real loader for
at least one mesh format and one texture format.

### `v0.0.11` — Physics

A `PhysicsBackend` trait per `docs/architecture/physics.md`'s existing
design (backends never expose third-party types in public APIs, matching
the RHI pattern), with a real backend behind it. **Decision: 2D first**
(`rapier2d`, pure Rust, matching this project's "Rust-first, minimal
unnecessary dependencies" values), not 3D — simpler to verify end-to-end
against a real tiny game (collision, gravity, a controllable body) with
less surface area, and the existing Vulkan RHI already renders 2D content
fine as a special case (an orthographic camera and flat quads) without
needing a separate 2D renderer. 3D physics (`rapier3d`) behind the same
trait is real, intended future work once the trait is proven against a
second real game — not required for `v0.1.0`.

### `v0.0.12` — Audio

A real backend (`rodio`, the standard pure-Rust choice) behind Canary's
own trait, per `docs/architecture/audio.md`. An `AudioSource` component
triggered by real game state, playing real assets loaded via `v0.0.10`.

### `v0.0.13` — `CanaryUI` + windowed presentation

`egui` bootstrapped per [ADR 0011](../decisions/architecture-decision-records/0011-canaryui-abstraction-bootstrapped-on-egui.md),
rendering through the same RHI pipeline `v0.0.9` wired up, reading input
through the same path gameplay input uses — a real HUD/debug UI, not a
standalone `egui` demo window.

This is also where live window presentation lands (Vulkan swapchain
surface + acquire/present, against the `winit` backend `v0.0.4` already
proved): every release before this is honestly verifiable offscreen via
pixel readback, but an *interactive* UI cannot be accepted from a GIF —
a live screen is its acceptance criterion. Deliberately not pulled into
`v0.0.10`: the asset stage needs no screen, and scheduling presentation
earlier would rush it for no verification payoff. Backstop: no later
than `v0.1.0` regardless, since the sample game needs a screen by
definition.

### `v0.0.14` — Project State

Real `World` save/load, per `docs/architecture/state-and-versioning.md`'s
near-term scope. This release is where the shared serialization
primitive `v0.0.15`/`v0.0.16` both reuse gets built.

### `v0.0.15` — Networking

Server-authoritative replication of real component data, per
`docs/architecture/networking.md` and
[ADR 0013](../decisions/architecture-decision-records/0013-live-collaboration-server-authoritative-topology.md).
Deliberately minimal relative to the fuller design (client
prediction/reconciliation, rollback) — a real, if simple, transport and
full-state or basic-delta replication is the `v0.1.0` bar; the rest is
real, intended future work.

### `v0.0.16` — Live Collaboration

Builds on `v0.0.14` and `v0.0.15` directly, per this plan's own explicit
instruction not to let it become a separate, disconnected feature.

### `v0.1.0` — Integration proof

A real, small sample game — built using every system above together,
not a new subsystem itself. Whatever integration gaps it exposes get
fixed as part of this release, not deferred; this release **is** the
verification that the bar in "The bar, per subsystem" above is actually
met, not an assumption that it must be by construction.

## Explicitly not required for `v0.1.0`

The editor, visual scripting, the community marketplace, console
support, AI/ML integration, client prediction/rollback netcode, a full
asset-cooking pipeline with hot reload, and any beginner-friendly
tooling or workflow — all real, intended, and explicitly deferred, per
direct instruction. Don't delay `v0.1.0` for any of these; don't treat
their absence as this plan being incomplete.
