# `v0.1.0` Plan: A Real, Small Game Against Canary's Runtime

Recorded at the project owner's explicit direction (September 2026): the
bar for `v0.1.0` is not "every subsystem in `docs/architecture/` has an
API," it's **a competent developer could write a real, small game
directly against Canary's runtime, without bypassing the engine or
implementing fundamental engine systems themselves.** See
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#v010-sharpened-integration-not-a-checklist)
for the narrative version of this; this document is the concrete,
dependency-ordered sequence it implies, kept current as each release
lands (this is a living plan, not a one-time announcement — update it,
don't leave it to drift the way `future-roadmap.md` and `milestones.md`
were found to have drifted during the September 2026 documentation
sweep).

## The bar, per subsystem

Not "the crate exists and has tests" — "another real part of Canary
uses it":

- **Physics** moves an ECS `Transform`, driven by real collider/rigidbody
  components, not a standalone demo.
- **Rendering** draws actual `World` state (`Transform` + a renderable
  component) every frame, not a hand-fed vertex buffer like
  `examples/spinning-cube`.
- **Assets** feed the renderer and audio system real files from disk,
  not hardcoded Rust arrays.
- **Audio** plays real loaded sound assets, triggered by real game
  state.
- **`CanaryUI`** renders through the same RHI rendering already uses,
  and reads real input through the same path gameplay input does.
- **Project State** persists authored project data with stable identity
  and migration rules. The separate simulation snapshot contract captures
  deterministic state for save/reload and replay without serializing
  presentation handles, editor state, or temporary runtime caches.
- **Networking** replicates real component data between a real server
  and a real client process, not a loopback mock.
- **Live Collaboration** builds on Project State's serialization and
  Networking's transport — not a separate, disconnected feature.
- **Plugins** can participate in whichever of the above they have
  legitimate reason to touch without bypassing structural enforcement.
  R-34's Tier A active-world ownership loan is implemented and API-reviewed
  for serialized `on_load`/`on_unload` calls. The integration proof must
  exercise that exact supported scope against the game world; it must not
  imply per-frame plugin callbacks or concurrent access.

## Why this order (dependency reasoning, not preference)

```
   canary-scheduler (v0.0.8, done)
          |
   App/Subsystem gets real delta-time + a real timed loop  <- v0.0.9
          |
   Transform + GlobalTransform + hierarchy (new crate)      <- v0.0.9
          |
   +------+-------------------+
   |                          |
ECS-driven rendering    (unblocks physics, audio-position,
(v0.0.9/10)               UI-in-world-space, later)
   |
Asset loading (v0.0.10) - meshes/textures feed the renderer above
   |
   +------------+-------------+
   |            |             |
Physics      Audio        CanaryUI
(v0.0.11)   (v0.0.12)    (v0.0.13)
   |
   +--- all three need Transform + (for audio/physics) the real
        timed loop; none need each other, so their relative order
        among themselves is low-stakes -- sequenced physics-first
        only because it's this project's own most-cited example
        subsystem, not because audio or UI genuinely depend on it
   |
Project State (v0.0.14) - authored state + simulation snapshot
   |
Networking (v0.0.15) - reuses versioned codecs/snapshot contracts,
   |                    adds authority + removal history + ordering
   |
Live Collaboration (v0.0.16) - builds on both directly
   |
v0.1.0 - a real, small sample game exercising all of the above
         together, fixing whatever integration gaps that exposes
```

The through-line: **`Transform` is the single most load-bearing new
primitive**, needed by rendering, physics, audio (positional playback),
and UI (world-space anchoring) alike — it is now implemented early and
shared across those subsystems. The remaining `.13` dependency gaps are the
completed window-to-RHI presentation path, common input/action path, and a
frame driver that uses the `canary-runtime` R-34 foundation to prove them
together.
Project state and simulation snapshots share schema codecs and migration
rules, while keeping authored project data separate from the
deterministic simulation boundary. Networking may reuse those codecs and
snapshot contracts, but it must add removal history, canonical ordering,
authority, and frame-tagged simulation input rather than treating generic
`World` serialization as replication.

## How to execute the remaining milestones

Treat each milestone below as a gated work package, not just a release
label. The numbered work packages within a milestone are ordered: settle
the contract and record it first, then implement the smallest vertical
slice, then prove it through the supported consumer boundary and update
the living docs. Do not begin implementation work from a later milestone
until the preceding milestone's exit evidence is met. Small research or
spike work may inform a decision, but it does not count as accepting the
next milestone.

At each handoff, refresh [`status.md`](status.md), the relevant subsystem
architecture, and the linked risk-register entries. Keep implementation
choices open until their stated decision point; if evidence changes a
binding ADR, append an amendment instead of silently changing the plan.
There are no calendar estimates here: the acceptance evidence is the
completion signal.

## The releases

### `v0.0.9` — Real-time loop + `Transform` + ECS-driven rendering

The foundational release: nothing above is buildable without it.

- `Subsystem::tick` gains a real delta-time parameter (`std::time::Duration`)
  — a breaking API change, made now rather than retrofitted once
  physics/audio timing depend on it being right.
- `App` gains a real wall-clock-timed loop (replacing `run_for(ticks:
  u32)`'s fixed tick count with no real-time relationship), with a real
  exit condition (a closed window, in the real-windowing case).
- A new crate, `canary-transform` (or equivalent — name decided at
  implementation time): `Transform` (position/rotation/scale, one
  representation serving both 2D and 3D — see
  [`docs/architecture/transform.md`](../architecture/transform.md) and
  [ADR 0017](../decisions/architecture-decision-records/0017-unified-transform-representation.md)),
  `GlobalTransform`, and a hierarchy-propagation system registered
  through `canary-scheduler`, proving the scheduler against a real
  gameplay-shaped system rather than only its own test doubles.
- `canary-render`/`canary-render-vulkan` gain a real integration point:
  a system that queries `World` for `GlobalTransform` + a simple
  renderable component and draws them, replacing
  `examples/spinning-cube`'s fully hand-fed vertex buffer approach (that
  example either gets rewritten on top of this or is explicitly
  superseded by a new one once this lands).

### `v0.0.10` — Minimal asset loading

Real files from disk feed the renderer `v0.0.9` built. Deliberately
minimal relative to `asset-system.md`'s full design (cooking,
importers-as-plugins, hot reload) — those remain future work. The current
`AssetId` is provisional content identity; it is not the persistent
authored identity for scenes, prefabs, or editor selections. ADRs 0021 and
0022 require a stable `LogicalAssetId` registry in the project-state
milestone. The v0.0.10 slice provides `AssetHandle<T>` and real mesh and
texture loaders.

### `v0.0.11` — Physics

A `PhysicsBackend` trait per `docs/architecture/physics.md`'s existing
design (backends never expose third-party types in public APIs, matching
the RHI pattern), with a real backend behind it. **Decision: 2D first**
(`rapier2d`, pure Rust, matching this project's "Rust-first, minimal
unnecessary dependencies" values), not 3D — simpler to verify end-to-end
against a real tiny game (collision, gravity, a controllable body) with
less surface area, and the existing Vulkan RHI already renders 2D content
fine as a special case (an orthographic camera and flat quads) without
needing a separate 2D renderer. 3D physics (`rapier3d`) behind the same
trait is real, intended future work once the trait is proven against a
second real game — not required for `v0.1.0`.

### `v0.0.12` — Audio

A real backend (`rodio`, the standard pure-Rust choice) behind Canary's
own trait, per `docs/architecture/audio.md`. An `AudioSource` component
triggered by real game state, playing real assets loaded via `v0.0.10`.

### `v0.0.13` — `CanaryUI` + windowed presentation

This release adds input actions and a small game-facing `CanaryUI` slice on
the same live Vulkan presentation path. Its detailed work packages, current
progress, proposed input contract, UI acceptance, and live-proof requirements
are maintained in [`v0.0.13-roadmap.md`](v0.0.13-roadmap.md). That file is
the implementation handoff; this plan remains the dependency-order index.

**Acceptance boundary:** the R-34 runtime library and a clear-only window
presenter are prerequisite slices, not the full game proof. `.13` is not
accepted until a game and the headless consumer use the supported runtime
library, the scheduled simulation receives deterministic `SimulationInput`,
and a live window presents both game output and `CanaryUI` while respecting
input capture. See the milestone roadmap for exact phase-order and close-out
evidence.

### `v0.0.14` — Project State

Build the first `canary-state` crate and its two distinct products: authored
project state and deterministic simulation snapshots. Both use the agreed
schema and migration vocabulary, but they do not serialize the same set of
objects. Apply ADRs 0012, 0020–0022; do not choose an encoding just because it
is convenient for a first implementation.

Work packages, in order:

1. **Review and resolve the authored-state design package.** Revisit ADR 0012's proposed
   scope and status. Decide the stable `LogicalAssetId` and authored-entity
   identity registry, codec/schema/encoding version boundaries, migration
   composition and failure behavior, unknown-versus-missing field semantics,
   and how unknown schema data survives load/edit/save. Specify canonical
   ordering, atomic persistence behavior, and authored-level change
   tracking semantics, distinct from ECS `Tick` mutation detection and the
   later collaboration operation history. Keep `ContentHash`, `CookKey`,
   and artifact-storage identity distinct from logical asset identity
   (ADR 0022). Review [ADR 0026](../decisions/architecture-decision-records/0026-authored-state-and-simulation-snapshot-contract.md)
   and [`state-and-versioning.md`](../architecture/state-and-versioning.md).
   The on-disk encoding remains evidence-led: record and review the short
   format comparison before implementation, without creating another design
   document.
2. **Implement authored state.** Add the persistent identity registry and
   authored-level change tracking, plus versioned codecs/migrators.
   Round-trip project-authored entities and asset references through fresh
   runtime `Entity` allocations; prove authored changes are tracked
   independently of runtime ECS ticks. Unknown fields or schemas must
   survive a load/save cycle when the current build cannot interpret them.
   A failed migration or write must report a typed error and leave the last
   good project data recoverable.
3. **Implement the simulation boundary.** Define and implement
   `snapshot`/`restore`/`checksum`/`step(input)` for a declared simulation
   state: ECS state, deterministic resources, owned RNG streams, simulation
   clocks, and schema/version data. Explicitly exclude presentation handles,
   editor state, thread-pool internals, and temporary caches. Define which
   subsystem state is authoritative and how it participates rather than
   assuming that serializing all of `World` is correct.
4. **Prove and document both paths.** Add fixtures for old/new schema
   migration and unknown-data preservation; prove deterministic
   snapshot/restore/checksum behavior with the same inputs; verify
   presentation-only resources are excluded; and exercise interrupted or
   rejected persistence without losing the prior saved state. Update
   `state-and-versioning.md`, API docs, ADR 0012's status/scope, status, and
   risk entries with the behavior that actually landed.

**Exit evidence:** authored references survive runtime-ID changes,
authored change tracking is separate from runtime ECS ticks, supported
migrations are explicit and failures are recoverable, unknown data is
preserved by round-trip, and the simulation snapshot reproduces its declared
deterministic state without presentation resources. State/project files and
simulation snapshots have separately documented boundaries.

### `v0.0.15` — Networking

Implement the smallest real server-authoritative path that builds on project
state and the accepted QUIC/transport direction in ADR 0007. Client
prediction, reconciliation, and rollback remain out of scope for `v0.1.0`.
Mutation ticks alone are neither an operation log nor a removal signal.

Work packages, in order:

1. **Review and resolve the replication protocol proposal.** Review
   [ADR 0027](../decisions/architecture-decision-records/0027-minimal-server-authoritative-replication.md)
   and [`networking.md`](../architecture/networking.md) before exposing a
   wire format. Define the replication unit and
   component opt-in, canonical initial snapshot, mutation/removal/despawn
   ordering, protocol and schema compatibility, authoritative versus local
   predicted state, and frame-tagged `SimulationInput`. State the
   authentication/identity and trust boundary, message/size limits,
   backpressure behavior, disconnect/reconnect behavior, and which version
   domains are checked independently (ADR 0022). Build on ADR 0007's QUIC
   default and transport trait; change that decision only with concrete
   evidence and an ADR amendment.
2. **Add the state history needed by replication.** Implement a durable,
   bounded removal/destruction signal for components and entities, plus
   canonical snapshot iteration and the minimum stable network identity
   mapping. Reuse `.14` codecs where the contracts match; do not conflate
   authored project serialization, simulation snapshots, and wire messages.
   Resolve R-32/R-33 at the point the chosen representation is proven.
3. **Implement one end-to-end transport path.** Run a server and client as
   separate processes using the transport boundary and default QUIC path.
   Send an initial state, subsequent component changes/removals/despawns,
   and frame-tagged simulation input. Bound queues and payloads so a slow or
   malformed peer cannot produce unbounded memory growth or stall the game
   frame indefinitely. Expose typed errors for protocol mismatch and
   connection failure.
4. **Prove failure and update docs.** Exercise initial synchronization,
   changed state, component removal, entity despawn, incompatible protocol
   or schema versions, disconnect/reconnect behavior, and relevant duplicate
   or reordered delivery cases at the layer where they can actually occur.
   Run the proof across separate processes, then update architecture, ADR,
   status, and R-32/R-33 with the observed contract.

**Exit evidence:** a repeatable two-process server/client run exchanges
versioned, canonical state and frame-tagged input; clients converge after
state changes and removals; failure and resource limits are explicit. Do not
claim prediction or rollback support from this replication slice.

### `v0.0.16` — Live Collaboration

Build a narrow shared-authored-state vertical slice directly on `.14`'s
stable IDs/codecs and `.15`'s server-authoritative transport. ADR 0013
settles topology and authority only; proposed operation and permission
semantics are now documented in ADR 0028 and
[`live-collaboration.md`](../architecture/live-collaboration.md), and must be
reviewed against `.14`/`.15` evidence before acceptance. Do not treat ECS
change ticks or replicated gameplay state as a collaboration history.

Work packages, in order:

1. **Review and resolve the operation contract.** Review
   [ADR 0028](../decisions/architecture-decision-records/0028-authoritative-live-collaboration-operations.md)
   and [`live-collaboration.md`](../architecture/live-collaboration.md),
   then amend ADR 0013 and the state architecture with stable operation IDs
   and targets, authorship,
   server-assigned ordering, idempotency, authorization scope, accepted and
   rejected results, stale-version handling, conflict behavior, and client
   recovery/resynchronization. Define how accepted operations relate to
   version lineage and saved project state. State what history is retained
   and what undo/redo means for this first slice; do not promise arbitrary
   history rewriting or offline merge unless designed and proven.
2. **Choose a deliberately small edit surface.** Pick one authored object
   type and a small set of meaningful edits after reviewing the `.14`
   representation. Keep it independent of any editor UI so it can be
   exercised through a small client/API. Apply project schema migrations
   before validation, and enforce the shared permission rules at the server
   boundary.
3. **Implement the authoritative session path.** Submit edits from two
   separate clients to a session server, return accepted/rejected outcomes,
   and broadcast the accepted ordered result. Persist/reload the resulting
   authored state using `.14`'s declared format. Handle duplicate requests,
   invalid targets, denied operations, conflicting edits, and stale clients
   according to the written rules.
4. **Prove recovery and document limits.** Verify both clients converge on
   the accepted state, including after a rejected or repeated request and a
   reconnect/resync. Record operation history and version-lineage evidence;
   update ADR 0013, state/networking architecture, status, and risks. Be
   explicit about what this first slice does not yet provide.

**Exit evidence:** two independent clients can make a small shared authored
edit through an authoritative session; operation ordering, permissions,
conflict/rejection behavior, persistence, and recovery are observable and
documented. Do not describe the implementation as CRDT-based or
conflict-free unless a later ADR explicitly adopts and proves that design.

### `v0.1.0` — Integration proof

Use one small, documented game as the integration test of the supported
consumer API, not as another engine subsystem. Fix integration gaps exposed
by the game as part of this release. The release proves the bar above; it
does not assume subsystem acceptance automatically implies a usable whole.

#### Proposed sample scope

Use a one-room 2D collectathon as the integration consumer: one physics-driven
player moves with mapped digital actions, collects a small set of authored
items, and shows score/goal status in a `CanaryUI` HUD. One HUD button sends
game intent through the documented simulation boundary; it does not mutate
the `World` from a widget callback. Pickup state triggers a sound loaded from
disk. The room and its entities use authored stable IDs and can be saved and
reloaded; a simulation snapshot separately proves deterministic capture and
restore. Use real on-disk mesh/texture/audio assets through the public asset
APIs.

Keep the network and collaboration evidence as separate runnable paths from
the same project/game data: one authoritative server and one client process
exercise `.15` replication and frame-tagged input; two collaboration clients
exercise the `.16` authored-transform operation, revision conflict, and
reconnect history path. A Tier A sample plugin reads or overwrites a
registered game component during its documented lifecycle boundary. The
sample is intentionally small enough to keep the engine as the subject of
the release, while making each advertised boundary observable.

Work packages, in order:

1. **Prepare the consumer project.** Create a small example project that
   builds and runs only against documented public APIs. Include setup and
   launch instructions from a fresh checkout, asset files and their source
   licenses, and a clear expected interaction. Remove any dependency on
   private binary harness APIs from the proof.
2. **Exercise the complete runtime.** Load mesh, texture, and audio assets
   from disk; initialize a real audio device backend; create a live window;
   use mapped gameplay actions; move a physics-driven entity; render current
   ECS state; show a HUD derived from that state; play a sound triggered by
   game state; and save/reload authored state. Exercise the plugin against
   the active game `World` through the accepted scoped-access contract.
3. **Exercise integration boundaries.** Include the repeatable separate
   process server/client path and the `.16` shared-authored-edit path in
   release evidence. Check lifecycle ordering and failure handling across
   window close, asset/state errors, audio or renderer initialization
   failure, network disconnect, and plugin error to the degree each public
   contract claims to support recovery.
4. **Close release documentation and automation.** Automate deterministic
   build and headless/integration checks in CI where the runner supports
   them. For live window/audio/device checks that CI cannot reliably host,
   record the platform, command, expected result, and manual evidence in the
   release checklist. Update subsystem and consumer docs, `status.md`,
   changelog/release notes, and the pre-1.0 compatibility guidance in ADR
   0006 based on the version surfaces that now exist.

**Exit evidence:** a developer following the documented public consumer
path can build and play the sample without private harness APIs; the
subsystem checklist above is demonstrated in that game; and CI plus the
release checklist clearly distinguish automated evidence from required
live-device evidence. Any unsupported platform or backend is named rather
than implied to have been verified.

## Explicitly not required for `v0.1.0`

The editor, visual scripting, the community marketplace, console
support, AI/ML integration, client prediction/rollback netcode, a full
asset-cooking pipeline with hot reload, and any beginner-friendly
tooling or workflow — all real, intended, and explicitly deferred, per
direct instruction. Don't delay `v0.1.0` for any of these; don't treat
their absence as this plan being incomplete.
