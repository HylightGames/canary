# `v0.0.4` Roadmap: Real Windowing

Single focus, per the release cadence in
[`docs/vision/long-term-roadmap.md`](../vision/long-term-roadmap.md#release-cadence-one-focused-subsystem-per-00x-target-v010-as-substantially-feature-complete):
a real `winit`-backed implementation of `canary-platform`'s `Window`/
`InputSource` traits, alongside (not replacing) the headless-only
implementation `v0.0.1` shipped deliberately as a placeholder. See
[`docs/architecture/platform-abstraction.md`](../architecture/platform-abstraction.md).

## The assumption this roadmap overturns, verified rather than inherited

`platform-abstraction.md` states real windowing was deferred because
`v0.0.1`'s sandbox had "no display server, GPU drivers, or the system
libraries... that a real windowing dependency would need." Checked
directly rather than carried forward as still true: **this is no longer
the case.** This sandbox has:

- `libx11-dev` already installed, and `libwayland-dev`/
  `libxkbcommon-dev` installable via `apt` (both confirmed).
- `Xvfb` (X virtual framebuffer) already installed — a real, if virtual,
  X display server.
- `mesa-vulkan-drivers`, installable via `apt`, providing Mesa's
  software Vulkan implementation (`llvmpipe`, reporting as
  `PHYSICAL_DEVICE_TYPE_CPU`) — confirmed working end to end:
  `vulkaninfo --summary` against a running `Xvfb` enumerates a real,
  usable Vulkan device, and `glxinfo` confirms software OpenGL
  (`llvmpipe`) rendering too.
- **A real `winit` 0.30.13 window, created and driven through several
  redraw cycles, against `Xvfb`, end to end** — not a compile check, an
  actual running window with real event-loop traffic. See "Verified,
  not assumed" below for exactly what this proves and what it doesn't.

This means real windowing is genuinely testable here, and — because a
Vulkan RHI backend's software (`llvmpipe`/`lavapipe`) device is usable
for offscreen rendering regardless of which windowing backend eventually
presents to a real surface (see [ADR 0016](../decisions/architecture-decision-records/0016-native-rendering-backends.md)) —
the door this closed for `v0.0.1` (deferring windowing because "there's
no renderer to draw into it" and no way to validate one anyway) is open
further than `platform-abstraction.md` currently says.
That doesn't make rendering `v0.0.4`'s job — one focused subsystem per
release still applies — but it's worth recording precisely, since it
changes what's realistic to scope for whichever release rendering
becomes.

## Scope

1. **A real `winit`-backed implementation of `Window`/`InputSource`** —
   `WinitWindow`/`WinitInput` (naming to be finalized during
   implementation) alongside the existing `HeadlessWindow`/
   `HeadlessInput`, not replacing them: headless remains the right
   choice for dedicated servers and most tests, per
   `platform-abstraction.md`'s own reasoning for why this is a trait
   boundary at all.
2. **Bridging the existing pull-model trait to `winit`'s push model.**
   `Window::poll_events(&mut self)` was written expecting a traditional
   "pump events, return control" game-loop shape. Modern `winit` (0.30)
   deliberately moved away from exactly that model in favor of
   `ApplicationHandler` callbacks driven by `EventLoop::run_app`, which
   *takes over the thread* rather than returning control per frame.
   The bridge is `winit::platform::pump_events::EventLoopExtPumpEvents::pump_app_events`
   — confirmed to exist and work as expected in 0.30.13 — called with a
   zero timeout from inside `poll_events()`, driving an internal
   `ApplicationHandler` impl that buffers what happened (close
   requested, input events) into fields the rest of the trait impl
   reads. Worth being honest about up front: winit's own documentation
   describes `pump_app_events` as supported for exactly this
   compatibility case but discourages it beyond that — this is a real,
   acknowledged tension between winit's recommended ownership-of-the-
   main-loop model and this engine's existing (and, for a traditional
   game loop, more natural) per-frame-polling trait shape, not a
   frictionless fit. Documented as a deliberate tradeoff, not
   discovered as a surprise mid-implementation.
3. **Mapping `winit`'s input events to the existing `InputEvent`/`Key`
   types**, extending `Key`'s variant set as needed (it currently has
   exactly two named keys plus an escape-hatch `Other(u32)` — expanding
   this to cover a realistic keyboard is this release's job, not a
   future one, since a windowing backend nobody can actually type into
   isn't a meaningfully complete one).
4. **A real, running-window integration test**, using `Xvfb` the same
   way this roadmap's own verification did: create a real window,
   confirm it reports a sane size, drive a few `poll_events()` calls,
   confirm redraw/resize events flow through correctly, request close,
   confirm `should_close()` reports it. Mirrors the rigor
   `tests/native_loader.rs` and `v0.0.3`'s Tier A tests already
   established (test against the real thing, not a mock) rather than
   introducing a new, lower standard for this crate.

## Verified, not assumed

Two toolchain pins were found while scoping this release, needed to
build `winit` `0.30.13` under this sandbox's `rustc` 1.75:
`wayland-protocols = "=0.32.9"` and `quick-xml = "=0.39.4"` (which in
turn requires pinning `wayland-scanner = "=0.31.10"`, the version still
requesting `quick-xml`'s `^0.39` line rather than `^0.41`). **Re-verified
at implementation time, per this roadmap's own caveat that the ecosystem
might have moved again — it had:** two further pins were needed,
`wayland-protocols-plasma = "=0.3.9"` and
`wayland-protocols-wlr = "=0.3.9"`, each because their own newer
releases hard-require a `wayland-protocols` version above the pin above,
in lockstep with their own version number. All five are documented, with
the reasoning, in
[`build-system.md`](../development/build-system.md#the-rustc-175-sandbox-validation-floor).

The window/redraw test that produced "SUCCESS: real window created and
redrawn against `Xvfb`" proved `winit` itself works end to end in this
environment, but deliberately didn't prove `pump_app_events` integrates
cleanly with a `poll_events`-shaped call site, or that input round-trips
through `Xvfb`'s synthetic input path — both flagged as real
implementation work, not already-done groundwork. **Both are now
implemented and proven, not just planned:**

- `Window::poll_events` bridges to `pump_app_events` cleanly, but not
  frictionlessly — `winit`'s own documentation describes
  `pump_app_events` as supported for exactly this compatibility case but
  discourages it beyond that, a real, acknowledged tension worth being
  honest about rather than presenting as a perfect fit. Documented in
  `winit_backend.rs`'s own module docs.
- Real synthesized keyboard input **does** round-trip through `Xvfb`'s
  XTEST extension and is correctly observed as
  `InputEvent::KeyPressed(Key::W)` — proven in
  `engine/canary-platform/tests/winit_backend_window.rs`, not assumed
  from the redraw test alone.
- Two further `winit` constraints surfaced only once real tests were
  written, not knowable from the scoping-phase spike above:
  `EventLoop::new()` panics off the main thread (which is where every
  `cargo test` function runs), and only one `EventLoop` can exist per
  process, ever — even across separate `#[test]` functions in the same
  binary. Worked around with a Linux-only, explicitly test-only
  `WinitWindow::new_for_testing` constructor and by consolidating what
  would have been several test functions into one — see that test
  file's own module docs for the full reasoning.

## Explicitly not in scope

- **Rendering.** A window with nothing drawn into it. Whichever release
  takes this on can use everything this release proves about `Xvfb`
  and software Vulkan, but that's a separate, dedicated release's
  scope, not bundled here — see
  [`docs/roadmap/status.md`](status.md) for current sequencing.
- **Gamepad/joystick input, IME, or any input beyond keyboard.**
  `InputEvent`'s existing shape (key press/release only) is extended
  with more keys, not more event kinds, in this release.
- **Multi-window support.** One window, matching the existing
  `WindowDescriptor`/`Window` trait's implicit single-window shape —
  and, it turns out, matching a real `winit` constraint found while
  implementing this (`EventLoop`, and so `WinitWindow`, can only be
  created once per process — see "Verified, not assumed" above).
  Revisit if a real multi-window need materializes (the editor,
  eventually) — that will need `WinitWindow` to change shape (sharing
  one `EventLoop` across multiple logical windows), not just relaxing a
  self-imposed limit.
- **Mobile or console windowing backends.** `winit`'s desktop
  (Windows/macOS/Linux) support only.
- **A macOS/Windows equivalent of the real windowing integration test.**
  The Linux/`Xvfb`/XTEST-based test this release added is real,
  automated, and runs in CI — but only on Linux. Real, intended future
  work, not fixed here.

## Definition of done

- [x] A real `winit`-backed `Window`/`InputSource` implementation
      exists alongside (not replacing) the headless one.
- [x] The `pump_app_events` bridge is implemented and its tradeoffs
      documented in the same place the trait itself is defined, not
      only in this roadmap.
- [x] `Key` covers a realistic keyboard, not just two named keys.
- [x] A real window is created, driven through several `poll_events()`
      calls, and cleanly closed, in a test — against `Xvfb`, the same
      way this roadmap's own verification worked, not a mock.
- [x] `docs/architecture/platform-abstraction.md`'s "Status in this
      foundation" section is rewritten for what's actually true after
      this release, including correcting the "cannot actually build or
      test" claim this roadmap already found to be false.
- [x] Existing `canary-platform` tests (headless) pass unmodified.
- [x] `cargo build`/`fmt --check`/`test`/`doc` clean; `clippy` verified
      — reachable in this sandbox for the first time this session (a
      genuine capability change, not just luck), and used to confirm a
      clean result across both the default and `winit-backend` feature
      configurations. Also used to clear the small number of
      pre-existing warnings in unrelated older code that surfaced once
      clippy was finally reachable here — a separate, narrowly-scoped
      commit from this release's own work, not folded into it.

## Status

Implemented. `WinitWindow`/`WinitInput` exist behind the `winit-backend`
Cargo feature (off by default); the real integration test passes against
`Xvfb` both locally and in CI's dedicated `windowing-integration` job.
