# `v0.0.13` Roadmap: Windowed Game UI and Shared Input

This is the working handoff for completing `v0.0.13`. The release proves
that a small game can use Canary's documented runtime, input, UI, renderer,
and window path together. It is a prerequisite to project state in `.14`;
it is not the editor milestone. The larger dependency sequence remains in
[`v0.1.0-plan.md`](v0.1.0-plan.md#v0013-canaryui--windowed-presentation).

## Dependency order

### 1. Runtime ownership and plugin access — complete foundation

The implementation provides a `canary-runtime` library, pre-run world
population, runtime ownership, `RunContext`, typed plugin load/unload failure
handling, and scoped active-world access for existing Tier A lifecycle
callbacks. Follow the accepted implementation contract in
[`2026-09-r34-api-review.md`](../reviews/2026-09-r34-api-review.md). Do not
extend the plugin ABI with per-frame callbacks as part of `.13`.

Before treating the whole game-runtime composition requirement as complete,
the close-out work still needs a frame driver that runs the simulation
schedule between input and presentation phases and migrates the headless
consumer to the public library. Keep this distinction visible in status:
the scoped-access foundation is complete; the complete game-consumer proof is
not.

The first frame driver must also close the `RunContext` timing details before
consumers rely on them. Today `begin_frame` advances `frame_index` and folds
`frame_dt` into `sim_time` before any schedule runs, while
`advance_tick_for_pass` advances the world's tick separately. The accepted
R-34 API review describes `RunContext.tick` as the current or most recent
scheduled pass and places the resource update before tick advancement. The
full runtime must preserve that interpretation or record an explicit review/
ADR amendment with an unambiguous field meaning. In either case, outer-frame
metadata may advance on event/presentation-only frames, but simulation time
and logical tick must not. Keep physics substep time distinct as ADRs
0021–0022 require.

### 2. Window presentation — implementation in progress

Keep platform and RHI public types Canary-owned. Finish and review the current
window-handle, surface, swapchain, and `VulkanPresenter` work as a separate
implementation change. The first supported policy is deliberately small:

- one live desktop window and one Vulkan presenter;
- FIFO present mode and a backend-neutral capability/format vocabulary;
- one cleared frame acquired, submitted, and presented at a time;
- resize-generation or extent changes recreate the swapchain;
- a zero-sized/minimized window suspends presentation;
- suboptimal/out-of-date outcomes are reported distinctly from fatal errors;
- offscreen rendering remains usable without the presentation feature.

The current live smoke evidence is 5/5 frames presented. Keep the test
explicitly hardware/display-gated; it must not make ordinary headless tests
depend on X11 or a presenting Vulkan ICD. Re-run it with the documented
command and record OS, display server, Vulkan device/ICD, and result when the
change is ready to land. Do not claim cross-platform presentation from the
Linux proof.

The clear-only window proof is a prerequisite for UI presentation, not the UI
proof itself. Before `.13` closes, the UI draw output must reach the same
Canary-owned renderer/device path that presents the game frame; a second
unrelated Vulkan-only UI path does not satisfy the abstraction boundary.

### 3. Shared input intent — design then implement

The semantic contract and UI-capture policy are in
[`input-and-simulation.md`](../architecture/input-and-simulation.md) and
[ADR 0025](../decisions/architecture-decision-records/0025-deterministic-input-actions-and-ui-capture.md).
Review and settle those records before code. Implement the input-action layer
above `canary-platform` in a dedicated `canary-input` crate; keep OS events in
`canary-platform` and keep `egui` types out of both public interfaces.

Work through these pieces in order:

1. Extend normalized raw events only as far as the first UI/game consumer
   needs: keyboard transitions, pointer position/buttons, and window focus
   loss. Preserve event order. Repeats must not create duplicate action
   presses; focus loss must clear held state so actions cannot stick.
2. Add game-owned action identifiers and a mapping profile for the first
   local player. The first profile needs digital actions only; analog axes,
   gamepads, remapping UI, persisted control profiles, and multi-device
   player assignment are deferred.
3. Produce a deterministic per-step `SimulationInput` snapshot with player
   identity, ordered action values, edge state, and the tick/frame identity
   assigned by the runtime. The game simulation reads that logical snapshot,
   never raw platform key codes.
4. Route raw events through the UI capture decision before gameplay mapping.
   UI-consumed keyboard/pointer input is unavailable to gameplay for that
   event unless an explicit pass-through binding allows it. If capture or
   focus changes while a control is held, send a cancellation/release into
   gameplay before clearing the held state.
5. Pass UI-originated changes into the next declared simulation boundary as
   intent/commands. UI callbacks must not mutate the `World` during a running
   schedule.

### 4. `CanaryUI` game slice — design then implement

Use the accepted architecture in
[`ui-toolkit.md`](../architecture/ui-toolkit.md) and ADR 0011. The minimum
implementation has a backend-neutral `canary-ui-core` boundary and an
optional `canary-ui-egui` adapter. Game code sees Canary-owned events,
actions, and UI output; it does not name `egui`, Vulkan, or `winit` types.

The slice must include one real-window HUD with at least one interactive
control, render it in the same presentable frame as the game, and read its
displayed value from a snapshot or view supplied by the game. The UI returns
intent; the runtime applies any resulting game change at a declared
simulation boundary. A button that invokes a gameplay mutation directly from
the UI callback does not meet the contract.

Keep `.13` bounded to one window, one backend, basic layout/text/button
primitives, a single game UI, and keyboard/pointer capture. Full text input,
IME/accessibility conformance, docking, editor panels, theming systems,
animations, gamepad UI navigation, and a native UI backend remain future
work. Do not leak those omissions into the API as `egui`-specific types.

### 5. Complete the consumer frame loop and prove the vertical slice

The sample and headless harness must use the same public runtime library.
The runtime (or its documented frame driver) owns this ordering:

1. initialize runtime services and load required plugins;
2. pump platform events on the platform-required thread;
3. route UI input, apply capture, and create logical player input;
4. advance the world tick immediately before the scheduled simulation pass;
5. process observations/audio effects and extract owned render/UI state;
6. update and draw UI/game presentation, then present the window frame;
7. on stop or error, unload plugins and shut down services in reverse order.

For the `.13` first consumer, preserve one scheduled simulation pass per
outer frame. Event/presentation-only iterations may update `frame_index`
without advancing the ECS tick. Do not add a general fixed-step runner,
rollback, hot reload, pause/resume, or editor play mode here.

The runnable proof must let the user move one game entity with mapped digital
actions, see current game state in the HUD, operate a UI control, and verify
that UI-captured input does not also fire gameplay. Record an interactive
window run with the platform/GPU/backend, command, result, and any known
limitations.

## Acceptance checklist

- [ ] Proposed ADR 0025 and the `.13` UI contract have been reviewed; any
      changes are reflected in the architecture docs before implementation.
- [ ] Window presentation gates cover adapter capability rejection, format
      negotiation, minimized windows, resize/recreate, suboptimal/out-of-date
      status, fatal surface/device errors, and safe destruction order.
- [ ] Input tests cover stable event ordering, duplicate/repeated press,
      multiple bindings, release, focus loss, pointer capture, explicit
      pass-through, and deterministic `SimulationInput` delivery.
- [ ] UI/game integration tests prove a consumed event cannot also produce a
      gameplay action and that UI-originated state changes enter at the next
      defined simulation boundary.
- [ ] Public UI and input APIs contain no `egui`, `winit`, `ash`, Vulkan, or
      raw-window-handle types.
- [ ] The game sample and headless harness use the supported runtime library;
      the runtime tick advances once per scheduled pass and not for
      presentation-only work.
- [ ] `RunContext.tick` has one documented meaning consistent with the
      accepted R-34 API review, or an explicit amendment, and tests prove the
      value consumers observe. Simulation time advances only with simulation
      passes, while `frame_index`/`frame_dt` describe outer frames.
- [ ] A live run shows game output plus HUD in the same window, accepts a
      mapped game action and a UI action, and demonstrates focus/capture.
- [ ] Architecture, status, this roadmap, changelog/release notes, and any
      new risks match the code that landed. `v0.0.14` does not start until
      this checklist's blocking items are complete.

## Deliberately deferred

Controller/analog input, configurable remapping, serialized input settings,
general fixed-step simulation, UI editor tooling, plugin-per-frame execution,
multiple windows, additional rendering/UI backends, and the full editor are
not prerequisites for this release. Their future use must build on the
logical-action, capability, and backend-neutral boundaries defined here.
