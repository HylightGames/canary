# `v0.0.11` Roadmap: 2D Physics (`canary-physics`)

Single focus, per [`docs/roadmap/v0.1.0-plan.md`](v0.1.0-plan.md#v0011--physics):
real simulated bodies move real ECS `Transform`s, drawn through the
renderer `v0.0.9`/`v0.0.10` built. Deliberately minimal relative to
[`docs/architecture/physics.md`](../architecture/physics.md)'s full
design (joints, scene queries, 3D backends) — those remain real,
intended future work, not required for `v0.1.0`'s bar. What's
required: a `PhysicsBackend` trait (the solver seam engine and game
code program against, with no third-party types in public signatures),
one real backend behind it (Rapier2D, the canonical 2D choice per
[ADR 0019](../decisions/architecture-decision-records/0019-physics-backend-lineup.md)),
fixed-timestep stepping wired into the subsystem schedule ahead of
transform propagation, and a tiny game-shaped scene proving the whole
chain moves pixels.

## Why this, and why bounded this way

`v0.0.10` closed its loop: real files from disk feed the renderer. But
nothing in the `World` moves on its own — every pose is still authored
by hand or by a spin script. `v0.1.0`'s bar ("physics moves an ECS
`Transform`, driven by real collider/rigidbody components, not a
standalone demo") fails verbatim until a solver owns integration, and
the sample game needs gravity, collision, and something scriptable to
push bodies around. So this release builds the physics primitive once,
against `Transform` and the existing soup bake as its consumers, rather
than letting each future game invent its own motion.

Bounded by taking only the smallest slice a falling-box-on-ground
scene plus one scripted kinematic platform needs: three body roles
(dynamic, fixed, position-kinematic), three solid collider shapes
(ball, cuboid, capsule), velocity seeding plus gravity scale plus axis
locks plus one material, and a fixed-step accumulator with a
spiral guard. Each excluded piece names its owning future:
velocity-kinematics, joints, scene queries, trimesh/heightfield
colliders (later physics milestones); Jolt/Rapier3D (the 3D release);
a real 2D camera (deferred with the renderer's camera work);
`App`-level scheduler redesign and ECS rework (explicitly refused, the
subsystem self-steps instead).

Checked before scoping: the three review triages and the risk
register. Adjacent but non-blocking: the fixed-step accumulator is the
honest local answer to record/replay reproducibility (single-machine
repeatability, not cross-platform determinism), and hierarchy fights
are resolved by simulating roots only, with render-only children
skipped.

## Scope

- **New crate, `canary-physics`** (one-crate-per-subsystem rule),
  depending on `canary-ecs`, `canary-scheduler`, and
  `canary-transform` plus `glam`/`thiserror` and `rapier2d` — it knows
  nothing about `canary-render`; composition flows upward through
  `canary-runtime`'s `EcsSubsystem`, preserving each leaf's
  dependency direction.
- **`PhysicsBackend` trait** (`engine/canary-physics/src/backend.rs`):
  object-safe (`Box<dyn PhysicsBackend>` behind configuration, pinned
  by a compile-time dyn-compatibility test) and leak-free (poses cross
  as `[f32; 2]` plus z-rotation, `glam::Vec2` only on the sync return;
  no rapier or `nalgebra` type in any public signature, rechecked via
  `cargo doc` plus grep). Methods: `create_body` / `attach_collider` /
  `step` (fixed-only, exact equality) / `sync_transform` (read half,
  `None` on stale) / `remove_body` / `set_velocity` / `apply_impulse` /
  `set_gravity` / `gravity` / `body_count`. Stale handles are signals
  (`None`/`false`), not errors; creation and stepping keep typed
  `PhysicsError` failures.
- **Minimal components** (`components.rs`): `RigidBody` (dynamic,
  fixed, position-kinematic; velocity-kinematics out),
  `Collider` (ball, cuboid, capsule; every scalar validated finite and
  positive), `Velocity`, `GravityScale`, `LockedAxes`, one
  `ColliderMaterial` (Rapier's own defaults), and the `PhysicsConfig`
  resource (gravity plus the ADR 0019 dimension/backend selection,
  `dimension = "2d"` / `backend = "rapier"`, both `#[non_exhaustive]`
  so 3D arrives additively).
- **Private `RapierBackend`** (`rapier_backend.rs`, module private,
  type re-exported only so schedules and resource lookups can name it):
  generational entity-to-handle slot map mirroring `Entity`'s proven
  shape, per-step gravity forwarding, `reset_forces` hygiene after
  every step, boundary finiteness checks on every float entering
  solver state, sync-side NaN guard that skips instead of poisoning
  `Transform`. Default rapier features only (`dim2`, `f32`, `std`,
  `block-solver`): no `parallel` (it would trade the proven
  single-machine determinism for throughput these body counts do not
  need), no `serde-serialize` (no persistence consumer yet).
- **Fixed-step design** (`systems.rs`): `PhysicsClock` (accumulator
  plus `FIXED_DT = 1/60`) plus `SimulationTime` (integrated physics
  seconds, deliberately distinct from ECS `Tick`) plus `FrameDelta`
  (measured frame time inserted as a resource by the owning
  subsystem's `tick(dt)`, no `App` redesign). Per tick the system
  quantizes frame time into whole fixed steps, clamps to
  `MAX_STEPS_PER_TICK = 4` with the spiral guard (leftover dropped,
  accumulator reset, documented slow-motion-instead-of-death policy),
  steps the backend at exactly `FIXED_DT`, then syncs x/y plus
  z-rotation only (plane depth, off-axis swing, and scale preserved
  via twist/swing recomposition). Missing `FrameDelta` degrades to
  exactly one step; nonpositive or non-finite frame time simulates
  nothing.
- **Ordering mechanism**: `register_physics_step` MUST run first in
  the subsystem constructor, before propagation, soup, mesh, and
  textured bakes (`engine/canary-runtime/src/main.rs` owns this
  order). Registration order plus solo-write staging is the whole
  mechanism: physics declares `writes::<Transform>()`, propagation
  declares `reads::<Transform>`, so the two can never share a stage
  and physics always runs first. Both directions are pinned by tests
  (fresh global when first, one-tick-stale global when reversed).
- **Box2D benchmark verdict**: N-box-pile plus ground workload,
  rapier2d versus Box2D 3.2.0 (via `boxdd`) in a throwaway harness
  that never became a runtime dependency. Medians: 0.053 ms (rapier)
  vs 0.060 ms (Box2D) at 100 boxes, 0.171 ms vs 0.205 ms at 300
  boxes. Rapier is faster by 1.13x at 100 and 1.19x at 300, on top
  of being pure safe Rust with no FFI boundary. No STOP-2: nothing
  in the numbers demands a re-decision, so rapier stands per
  ADR 0019 and no Box2D backend exists anywhere in the tree.
- **Version pin**: `rapier2d = "0.35"` in
  `engine/canary-physics/Cargo.toml`, resolving to `0.35.3` in
  `Cargo.lock` (verified by a real build on this toolchain at
  implementation time, per `build-system.md` pin policy; rationale
  comments live next to the requirement).
- **Game proof plus pixel proof**
  (`engine/canary-render-ecs/tests/physics_game_proof.rs`): ground
  (`Fixed` cuboid at `(0, -1.2)`), falling box (`Dynamic` cuboid at
  `(0, 1.0)`, collider load-bearing since mass comes from colliders),
  scripted platform (`KinematicPosition` driven from `x = 0.65` to
  `x = 1.1` at `y = 0.5` by writing `Transform`, the same seam future
  input code will use), drawn as z-pinned quads through the unchanged
  soup bake with fixed camera constants (zero RHI churn). Four
  headless tests (ground holds, box lands and rests, platform tracks
  its script, zero-frame stillness) run in the normal suite; three
  pixel tests (pre-vs-post frames differ with an unstepped-pipeline
  negative control, ground pixels stable, platform redraws at its
  scripted pose) are `#[ignore]`-gated for real Vulkan ICDs, same
  pattern as `render_ecs_readback`.
- **Determinism scope**: same steps give bit-identical trajectories,
  proven by comparing float bits across two runs — single-machine
  repeatability for record/replay and regression tests, NOT
  cross-platform determinism (float association, SIMD codegen, and OS
  math libraries differ across targets; no `parallel`, no
  `enhanced-determinism`, and the docs say so wherever the claim
  appears).
- **Backend-selection config honest state**: `PhysicsConfig` names
  the dimension and backend today with exactly one variant each. The
  selection is real data (gravity is already hot-tweakable through
  it), not a comment promising a menu — but only rapier2d exists
  behind it, and the docs say so.

## Explicitly not in scope

- Joints (impulse and multibody joint sets exist empty inside the
  backend only because `step` requires them), scene queries
  (raycasts, sweeps, overlaps), velocity-kinematic bodies,
  trimesh/heightfield/polyline colliders, sustained-force APIs —
  later physics milestones, each named in the work plan, none
  partially implemented here.
- 3D physics: Jolt (canonical 3D) and Rapier3D (alternative 3D)
  arrive with the 3D release, post-`v0.1.0` per the `v0.1.0` plan;
  nothing 3D lives in this crate.
- A Box2D backend: measured, beaten, not shipped. The benchmark
  harness was throwaway; no Box2D dependency exists in the tree.
- A real 2D/orthographic camera: the game proof reuses the fixed
  perspective constants with z-pinned quads, deferred alongside the
  renderer's camera component.
- `App`-level scheduler redesign and ECS rework: explicitly refused.
  Frame time reaches the accumulator as an ordinary `FrameDelta`
  resource through the existing `tick(dt)` seam; no `Subsystem`
  method changed, no signature in `canary-core` moved.
- Input-driven control: the platform is scripted by writing
  `Transform` poses directly; no input system exists yet.

## Verified, not assumed

- **66 `canary-physics` tests green** (`cargo test -p canary-physics`:
  66 passed, 0 failed), plus 4 headless game-proof tests green with 3
  pixel tests ignored pending a real ICD (`cargo test
  -p canary-render-ecs --test physics_game_proof`). Counts read off
  the runners, not estimated.
- **Known-motion assertions, not "it stepped".** One simulated second
  of free fall drops more than a meter; a fixed body holds its pose
  across 120 steps; the box lands and rests on the ground (collision,
  no tunneling); fifty bodies survive four simulated seconds finite;
  mid-soak removal leaves neighbours live.
- **Negative controls throughout.** Reversed registration bakes a
  provably stale global; the unstepped pipeline fails the pixel tests
  by construction; invalid colliders `Err` with the offending value
  named and never fail the tick; NaN `Transform`s never simulate
  while neighbours fall; forged handles resolve to nothing.
- **Ordering proven both directions**, mirroring the render-ecs
  precedent: physics-first sees a fresh global, propagation-first
  bakes the pre-step pose.
- **Determinism proven at the bit level** (float bits compared
  across runs), scoped to one machine in the test names and docs.
- **Preservation proven by property test** (256 random poses: sync
  writes exactly x/y plus z-twist; depth, swing, and scale come back
  bit-identical) alongside the single-pose example test.
- **No third-party types in any public signature**, checked via
  `cargo doc` plus grep over public signatures; `canary-render`
  still dependency-free (`cargo tree` check).
- Full workspace `build`/`clippy -D warnings`/`test`/`fmt --check`
  clean, `cargo doc` zero warnings, both `winit-backend` states,
  `wasm32-wasip2` check where applicable, CI green including the
  rendering-integration job that runs the `#[ignore]`-gated pixels.
