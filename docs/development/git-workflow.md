# Git Workflow

Canary uses a small, two-branch model — deliberately lighter than
GitFlow's `main`/`develop`/`release/*`/`hotfix/*`/`feature/*` sprawl,
which is more process than an open-source engine at this stage needs.

```
stable                  <- stable, always buildable, represents releases
 |
dev                     <- active development
 |
feature/<name>          <- temporary, merges back into dev
```

## `stable`

The version of Canary people can trust.

- Always compiles, always passes CI.
- Only receives changes via a reviewed merge from `dev` at release time —
  never a direct commit.
- Represents releases: every commit on `stable` corresponds to a tagged
  version (`v0.0.1`, `v0.0.2`, ..., `v1.0.0`), per
  [ADR 0006](../decisions/architecture-decision-records/0006-versioning-scheme.md).

```sh
git tag -a v0.0.2 -m "..."
git push origin v0.0.2
```

## `dev`

Where active development happens: new systems landing, architecture
changes, plugin work — everything that isn't yet a released version. CI
runs on `dev` exactly as it does on `stable` (see
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)); the
difference is what `stable` is reserved for, not a lower quality bar on
`dev`.

## `feature/<name>` branches

For anything larger than a small fix, branch from `dev`, not `stable`:

```
dev
 |
 +-- feature/render-graph
 +-- feature/canary-audio
 +-- feature/canary-ui
 +-- feature/plugin-sdk-tier-a
```

```
feature/<name>  --PR-->  dev  --release-->  stable
```

Small, self-contained fixes can go straight to `dev` via a normal PR
without a named feature branch — this model exists to keep large,
in-progress work isolated, not to add ceremony to every change.

## Cutting a release

1. `dev` is in a state that satisfies the target version's roadmap
   document (e.g. [`v0.0.2-roadmap.md`](../roadmap/v0.0.2-roadmap.md))
   and its own definition of done.
2. Run through [`docs/reviews/RELEASE_CHECKLIST.md`](../reviews/RELEASE_CHECKLIST.md)
   (or the equivalent for the release in progress).
3. Promote `dev` to `stable`. The one-time 2026-11-15 reset left `stable`
   containing only the `v0.1.0` history, so later releases fast-forward it
   to the release commit; do not repeat the reset. See
   [the resolved blocker](#stable-promotion-blocker-2026-11-02--resolved-2026-11-15).
4. Tag `stable` at that commit (`git tag -a vX.Y.Z`), push the tag — this
   triggers [`.github/workflows/release.yml`](../../.github/workflows/release.yml).
   The workflow verifies tag `vX.Y.Z` matches the workspace version, requires
   `docs/release-notes/vX.Y.Z.md`, publishes that file with no autogenerated
   fallback, and requires the tag commit to be reachable from `origin/stable`.
   The `publish` job runs behind the `release` GitHub environment and
   creates a **draft** release, so a human must approve the job and then
   publish the draft (see [Publication gate](#publication-gate)). The
   publish path was exercised end to end by the `v0.1.0` tag run.
5. Continue on `dev` for the next release.

## `stable` promotion blocker (2026-11-02) — resolved 2026-11-15

**Resolved:** option 1 below was executed on 2026-11-15; `stable` now
contains only the `v0.1.0` history and later releases fast-forward it. The
record is retained for the decision and runbook.

The `feature/<name> --PR--> dev --release--> stable` model above is the
policy, but at the time **the `dev` → `stable` promotion was not executable
as documented.** Measured on 2026-11-02:

- `stable` has 2 commits not on `dev`: `d89d6ff` ("Update Cargo.toml
  with homepage and readme") and `7176ed0` ("Add custom funding link to
  FUNDING.yml"). Both appear superseded by later `dev` history, but that
  must be confirmed before any reset.
- `stable` is 238 commits behind `dev`. The count grows as `dev`
  advances (the 2026-10-24 audit recorded 237), so re-measure before
  acting: `git rev-list --left-right --count origin/dev...origin/stable`.
- A fast-forward is therefore impossible, and the repository rulesets
  forbid the obvious alternatives. Both `dev` and `stable` enable
  `required_linear_history` and `non_fast_forward`; `stable` also
  requires signed commits; `bypass_actors` is empty on both. A merge
  commit is rejected (linear history) and a force push is rejected
  (non-fast-forward); rebasing 238 commits would rewrite the evidenced
  history and still conflict on `Cargo.toml`.
- The `release.yml` step "Tag must be reachable from `origin/stable`"
  cannot pass until the promotion is performed, so tagging `v0.1.0`
  first would fail the release workflow.

### Options considered (option 1 chosen)

1. **Admin-approved force-reset of `stable` (preferred).** Confirm the
   two `stable`-only commits are superseded, temporarily add the
   maintainer as a bypass actor (or temporarily relax
   `non_fast_forward`/`required_signatures` for `stable`), force-reset
   `stable` to the release commit, then restore the ruleset immediately.
   Example: `git push --force-with-lease origin <release-commit>:stable`.
   This preserves the exact evidenced SHA; record the before/after
   `stable` SHAs, the ruleset change, and a tree-equality check
   (`git diff --quiet <evidence-commit> <tag-commit>`).
2. **Branch replacement.** Delete and recreate `stable` at the release
   commit. This needs the same one-time bypass as option 1 plus a check
   that the default branch, rulesets, and required checks re-attach to
   the replacement. Same outcome, more moving parts.
3. **Temporary ruleset exception for a promotion PR.** Allow one PR from
   `dev` into `stable` with either a merge commit or a squash merge,
   then restore the ruleset. A merge commit resolves the `Cargo.toml`
   conflict but leaves `stable` non-linear at the boundary; a squash
   merge produces a new SHA, which breaks SHA-addressed release evidence.

Option 1 was chosen and executed as a reviewed, documented operation;
see the runbook below and the release checklist. A scratch-repository
rehearsal remains part of roadmap `V2-02`.

### Execution runbook (option 1: reset `stable` to the release commit)

Executed on 2026-11-15 to make `stable` contain only the released
`v0.1.0` history. The steps remain the record for that one-time operation.

```sh
git fetch origin

# 1. Confirm the two stable-only commits are superseded and record the
#    current stable SHA. Do not proceed if either check surprises you.
git log --oneline origin/dev..origin/stable          # expect exactly 2
git log --oneline origin/stable..origin/dev | wc -l # expect ~240
git diff --stat origin/stable origin/dev -- Cargo.toml FUNDING.yml
STABLE_BEFORE="$(git rev-parse origin/stable)"
RELEASE_COMMIT="$(git rev-parse origin/dev)"        # the evidenced commit

# 2. In GitHub -> Settings -> Rules -> Rulesets, temporarily add the
#    maintainer as a bypass actor on the `stable` ruleset (or relax
#    non-fast-forward / required signatures for the duration). Record
#    the ruleset change and timestamp.

# 3. Reset stable to the release commit. --force-with-lease refuses if
#    stable moved since STABLE_BEFORE was recorded.
git push --force-with-lease=stable:"$STABLE_BEFORE" \
  origin "$RELEASE_COMMIT":stable

# 4. Verify before restoring the ruleset.
git fetch origin
test "$(git rev-parse origin/stable)" = "$RELEASE_COMMIT"
git diff --quiet "$RELEASE_COMMIT" origin/stable   # tree equality

# 5. Restore the `stable` ruleset immediately and re-check it in
#    Settings. Record: STABLE_BEFORE, RELEASE_COMMIT, the ruleset
#    change, and the tree-equality result in the release checklist.

# 6. Tag the release commit (annotated; release.yml rejects lightweight
#    tags) and push the tag only after the manual gates pass.
git tag -a v0.1.0 "$RELEASE_COMMIT" -m "Canary Engine v0.1.0"
git push origin v0.1.0
```

After this one-time reset, `stable` only fast-forwards, so the published
process above works as written for every later release. Option 2 (delete
and recreate the branch) is the same operation with more consequences for
default-branch and ruleset wiring; option 3 (a promotion PR) produces a
different SHA and breaks SHA-addressed evidence. Prefer option 1.

## Publication gate

`.github/workflows/release.yml` creates the GitHub Release as a
**draft** (`draft: true`) and its `publish` job targets the `release`
environment. Both are human gates: the workflow alone never publishes a
public release.

Required repository configuration (kept in GitHub settings, not in this
file, and **not created by the workflow**):

- Settings → Environments → `release`: add required reviewers (and,
  optionally, a deployment branch/tag rule limiting it to `v*` tags).
  If the environment does not exist, GitHub creates it without
  protection and the job will not wait for approval.
- Keep the `stable` ruleset and tag protection in place; the draft
  release is published manually after review.

**Configured 2026-11-15:** the `release` environment exists with
`notthecloudy` as a required reviewer (self-review allowed) and a custom
deployment policy limited to `v*` tags. Verify before tagging with
`gh api repos/HylightGames/canary/environments/release --jq '.protection_rules'`.
**Exercised 2026-11-15:** the `v0.1.0` tag run passed all five
verification jobs (tag/version, integration gate, and release build on
Ubuntu, macOS and Windows), created the draft, and the draft was
reviewed and published. Re-dry-run on a scratch repository after changing
the release jobs; the `workflow_dispatch` dry run remains in roadmap
`V2-02`.

## Why two branches

For a small application, a single branch is fine. For an engine, it
isn't: a single bad commit on the one branch everyone builds against can
break the renderer, the editor, plugins, the build system, and every
example simultaneously. Two branches cost almost nothing and mean
`stable` never becomes, even briefly, a construction site.
