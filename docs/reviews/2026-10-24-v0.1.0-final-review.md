## 7. Security assessment

### Threat model (current architecture)

| Boundary | Assets | Attackers | Entry points | Protections observed | Findings |
|----------|--------|-----------|--------------|----------------------|----------|
| Local files: saves, snapshots, project documents, assets, locale files | The player's process and data | Anyone who can hand the user a file (downloads, mods, shared projects) | `AuthoredDocument::load`, `decode_snapshot`, asset loaders, locale loader | Asset loaders: 64 MiB file cap, header-checked decode budgets, `try_reserve`, root confinement. | Network replication (QUIC) | The server process and its host | A peer that can reach the server | `QuinnTransport::bind_server`, frame and message decoders | Loopback-only bind enforced in the single bind path; length checked before allocation (1 MiB frames); per-peer limits of 64 messages and 8 MiB; decoder fuzz and 20,000 hostile datagrams survived | `030` (accepted), `017` (disclosure) |
| Live collaboration | Shared authored state | A malicious or buggy collaborator | `canary-collab` wire decoders and operations | Credential-bound permissions, session epochs, bounded outbox; decoder fuzz passes | Not reviewed beyond tests and fuzz |
| Native plugins (Tier B) | The whole process | A malicious library | `NativePluginLoader` | Trusted by design: allow-list, path confinement, ABI-version check before use, drop order (plugin before library), documented | None |
| WASM plugins (Tier A) | Host memory and CPU | A malicious or buggy guest | `WasmPluginLoader::load` | Fuel 10,000,000 per call re-armed per call; per-memory cap of 64 MiB; no WASI; capability-gated host functions | `008` (aggregate memory and tables) |
| Surface provider and GPU | The process | A buggy window provider | `SurfaceHandlesProvider` (`unsafe trait`) | Per-frame liveness check; ADR 0030 contract; validation-clean on llvmpipe | `024` |
| Build, CI and release | Release integrity | A compromised action or tag | Workflows, release tag | `ci.yml` and `release.yml` SHA-pinned; `cargo audit`; Trivy; least-privilege `contents: read` by default | `006`, `011`, `015`, `019`, `020` |

### Concrete vulnerabilities, hardening and theory, kept separate

- **Reproduced defects (local exposure only):** `003` a crafted snapshot of about
  20 KB aborts the process; `009` loading allocates the full file size with no
  budget; `008` a Tier A guest can hold 4x its memory budget in aggregate and
  grow tables far past it. None is remotely reachable in `v0.1.0` as shipped:
  the network and collaboration wire types do not embed the recursive value
  type, and the server cannot bind beyond loopback.
- **Hardening opportunities:** `011`, `014`, `015`, `016`, `019`, `020`, `023`.
- **Theoretical or unverified:** `024` (teardown order on non-X11 platforms).
- **Accepted and documented:** `030` (no client authentication, loopback only).
- **Examined and found sound:** the native loader's confinement, allow-list and
  ABI check; `RawPlugin` drop order (plugin before library); absence of any
  `unsafe impl Send` or `Sync`; the network framing and limits; asset decode
  budgets; atomic write behavior.

A clean `cargo audit` is not evidence that the application is secure, and 60,000
iterations per decoder is not exhaustive fuzzing. No Miri or sanitizer run was
possible (they need a nightly toolchain unavailable offline).

### Observations and what to do about them

None of these is a defect. Each is classified as a current design limit or optimization work, and none blocks `v0.1.0`.

1. **Mutable two-component queries are slower and scale worse than read-only ones.** At 10,000 entities the mutable query costs 16.2 ns per entity against 2.61 ns for a read-only query (about 6x), and it scales 21x (run 1) and 21x (run 2) for 10x the entities, so it is super-linear in both runs. A plausible cause is per-entity change-tick writes or cache effects; the audit did not profile it. Classification: optimization candidate. Do after the stress sample exists; owned by roadmap `V2-13`.
2. **Propagating 10,000 simultaneously moving transforms costs about 5.59 ms** (560 ns per entity), roughly a third of a 60 FPS frame, while an unchanged scene costs 11.5 µs. The dirty-flag design is excellent for static scenes and expensive for scenes where everything moves (the proposed `examples/stress`). Classification: current design limit. Optimize with the stress sample as the workload: incremental or parallel propagation (roadmap `V2-13` and `V2-03`).
3. **Structural changes are not cheap but are linear.** Spawning with two components is about 354 ns per entity and an archetype-moving insert about 244 ns. Fine for the current scale; budget them before wave-spawning gameplay depends on them.
4. **Read paths are fast and linear.** Read-only queries cost under 3 ns per entity and scale as expected; asset handle lookups, localization lookups (tens of nanoseconds) and PNG decoding of a 256 by 256 image (about 120 microseconds) raise no concern at the current scale.
5. **Not measured, and needed before any "production-capable" claim:** frame and simulation-step overhead, physics stepping and reconciliation, rendering preparation and presentation, replication cost and latency, snapshot serialization and hashing, collaboration operations, startup time and memory growth. Roadmap `V2-11` (profiler and allocation counters) and the budget table make them measurable.

## 9. Chaos, stress and failure-injection testing

All campaigns are bounded, seeded and local; seeds and commands reproduce them.
Tests were written as cargo tests and run in a scratch clone pinned to `ebc8f7f`
so the audited tree stayed clean; the bundle `canary-audit-proposed-tests/` holds
them with a README. "In-process" means no real sockets; the socket-level run is
labelled separately.

| Campaign | Method and seeds | Result | Reproduction |
|----------|------------------|--------|--------------|
| ECS structural chaos | Spawn, despawn, insert, remove, get, get_mut, forged `Entity::from_raw_parts` handles and stale handles, checked against a reference model every 250 steps; seeds `1, 2, 3, 0xC0FFEE, 0xDEADBEEF` x 12,000 operations; determinism seed 77; 20,000-spawn churn | **Pass**, no divergence, no aliasing of a recycled slot | `cargo test -p canary-ecs --test audit_chaos` |

| Network decoder fuzz (in-process) | Nine decoders; random and mutated bytes (bit flips, truncation, varint saturation); seeds `1, 2, 3` x 60,000 | **Pass**: no panic; max transient allocation 219,464 bytes; about 1,800 accepted inputs per seed | `cargo test -p canary-net --test audit_decoder_fuzz -- --nocapture` |

## 13. What was not tested, and why

- Real GPUs, windows on Wayland, Windows and macOS, audio hardware: not available.
- Miri, sanitizers and `cargo-fuzz`: need nightly, unavailable offline.
- Release-mode whole-workspace builds and benchmarks beyond the small crates
  listed in section 8: single vCPU and a disk that could not hold a second
  profile.
- A performance comparison against the previous tag for `canary-physics`,
  `canary-render-ecs` and `canary-net` (the crates that changed since `v0.0.16`):
  would have required a second release build of Rapier and the Vulkan stack.
- Long soak tests, real-network faults, device loss, audio failure.
- Reading every line: about 68,600 lines of production Rust exist; the review read
  the parts named in section 3 and relied on inventory, sweeps, the repository's
  own tests and new tests elsewhere.
- Most ADRs were not compared line by line with their code.
- `tools/xtask` was not reviewed.
