## Verdict

`dev` at `4233ad2` is **not ready to be cut as v0.1.0.** Three findings block the cut. Two are mechanical and one is a scope decision.

- **F-01.** The proof sample cannot start from a fresh checkout. Its committed `rgba2x2.png` is corrupt (the CR byte of the PNG signature is gone), so `collectathon`, `collectathon_headless` and `collectathon_server` all exit at startup.
- **F-02.** The `Security` workflow is red on `dev` HEAD. Three `wasmtime` advisories published 2026-10-02 hit the locked 49.0.1; the patched release is 49.0.2.
- **F-03.** The sample does not demonstrate the plan's own rendering and asset bar. It draws through a hand-built vertex buffer and a private projection, never draws the mesh and texture it loads, and the engine's render bridge has no camera. Either the sample or the bar has to change.

Around those: no CI job runs any sample binary (F-04), which is how F-01 passed green CI; the sample's simulation speed follows the monitor's refresh rate (F-05); a Linux fresh checkout does not build without undocumented system packages (F-06); `stable` and the release tags no longer match the documented release flow (F-07); and there is no documented way for a game outside this workspace to depend on the engine (F-08).

What is in good shape, and was checked rather than assumed: all four hard gates pass on this commit (0 warnings, 918 tests passed, clippy `-D warnings` and `cargo fmt --check` clean); all 22 `#[ignore]`-gated GPU and window tests pass on a real software Vulkan ICD (Mesa lavapipe) and Xvfb, fail loudly rather than vacuously when the ICD or display is missing, and every one of them is executed by a named CI step; the crate graph is acyclic and backend-isolated; there is no `wgpu`; `unsafe` is confined to three crates and 103 of the 114 render-vulkan blocks carry a `SAFETY:` comment; no locked crate is yanked; no secrets in 195 commits. See "Verified sound".

The pattern worth naming: one commit pair (`387ba00` then `e5f5db3`, ten minutes apart on 2026-10-02) produced F-01, F-11 and the `[x]` evidence the sample README cannot back, and nothing automated was positioned to notice (F-04). The engine code is in better condition than the release machinery around it.

### Blockers

### F-01 — The proof sample cannot start from a fresh checkout: its committed `rgba2x2.png` is corrupt

**Severity:** Blocker · **Decision needed:** no (mechanical) · **Triage:** unassigned
**Where:** `examples/collectathon/assets/rgba2x2.png` (blob introduced by `e5f5db3`, unchanged at HEAD).

**Evidence (observed).**

- The blob is 74 bytes and begins `89 50 4e 47 0a 1a 0a`. A PNG signature is `89 50 4e 47 0d 0a 1a 0a`. The canonical fixture, `engine/canary-assets/tests/fixtures/rgba2x2.png`, is 75 bytes, and `canonical.replace(b"\r\n", b"\n") == sample` holds byte for byte: the only difference is the CR of the signature, i.e. a CRLF to LF normalisation.
- History: at `387ba00` (2026-10-02 17:17) this path was a Git LFS pointer (`oid sha256:7f2538a6…`, size 75). `e5f5db3` (17:27, "keep small fixtures as regular blobs, not LFS") replaced it with the 74-byte blob.
- Every other committed binary fixture was validated structurally (GLB magic and header length, RIFF length, `OggS` capture pattern, PNG signature) and is intact. Only this file is damaged.
- The sample binaries run as shipped from a fresh clone of HEAD (Xvfb and lavapipe where a display is needed):

  | binary | result |
  |---|---|
  | `collectathon_headless` | exit 1: `invalid asset file '…/rgba2x2.png': not a parseable PNG file: Invalid PNG signature.` |
  | `collectathon_server` | exit 1: `server asset load: invalid asset file …`; never prints `READY` |
  | `collectathon` (windowed) | exit 1 after window and audio bring-up: `InvalidFormat { path: …/rgba2x2.png, reason: "not a parseable PNG file: Invalid PNG signature." }` |
  | `collectathon_collab_client` | runs (it loads no assets) |
  | `collectathon_client` | needs a server, so cannot run on its own |

- Control experiment: with the canonical bytes copied over the sample's file (then reverted), everything the README documents ran. The headless twin printed `score 1 collected 1/4 … after 90 frames`. Server and client converged (snapshot of 6 entries across 5 entities, delta of 5 changes and 1 removal, ack, clean disconnect). The windowed binary presented 600 of 600 scripted frames under Xvfb and lavapipe with none skipped. The defect is this one file.
- `examples/collectathon/README.md:58` says the mesh, texture and audio fixtures "are byte copies of" the `canary-assets` fixtures. For the PNG that is false.

**Why it matters.** This sample is the integration proof the plan's exit evidence rests on: "a developer following the documented public consumer path can build and play the sample" (`v0.1.0-plan.md:393`). As committed, three of its four game binaries die at startup. The README's `[x]` for the server/client replication run is not reproducible at HEAD, because the server exits before `READY`; it must have been recorded from a working tree that did not match the committed blob.

**Direction (not applied).** Restore the canonical bytes. Stop it recurring with a `binary`/`-text` attribute for fixture paths (F-11) and a check that loads every file under `assets/` through the public loaders (F-04).

### F-02 — `Security` workflow is red on `dev` HEAD: three new `wasmtime` advisories against the locked 49.0.1

**Severity:** Blocker (release gate) · **Decision needed:** confirm the exposure statement below · **Triage:** unassigned

**Evidence.**

- The `Security` run on `4233ad2` (2026-10-03T15:08Z) concluded `failure` at the `cargo audit` step. The job log is not retrievable from the review sandbox, so I reproduced it: RustSec advisory-db at `ef6173c` matched against all 519 registry packages in `Cargo.lock` gives RUSTSEC-2026-0325 (mis-typed WebAssembly tag imports can lead to GC heap corruption), RUSTSEC-2026-0326 (rooting for GC values live across `try_call` may be missing, causing GC heap corruption) and RUSTSEC-2026-0327 (component async-lifted callback result count is unvalidated, causing a native stack buffer overflow), all against `wasmtime 49.0.1`. All three list `>= 49.0.2` (and `>= 48.0.4, < 49.0.0`) as patched; 49.0.2 is published on crates.io. The advisories date from 2026-10-02. The previous Security run (`16f93cc`, v0.0.16) was green.
- The existing baseline in `security.yml` (`cargo audit --deny warnings --ignore RUSTSEC-2026-0192`, `ttf-parser` unmaintained via `rapier2d`, with a written rationale) is unchanged and reproduces as the only other hit.
- Exposure, as I read it (not confirmed against the GHSA pages, which the sandbox could not fetch): Canary builds `wasmtime` with `component-model`, `cranelift`, `runtime` and `std` (plus `wat` in the resolved graph); the `gc`, `component-model-async` and `async` features are not enabled. All three advisories sit in GC or async-component code that this feature set does not compile in, so they are probably not reachable from Canary today.

**Why it matters.** The workflow also runs weekly, so it stays red until the lockfile moves. More fundamentally Tier A is the sandbox for untrusted plugin code, so a `wasmtime` advisory is the one dependency class a v0.1.0 should not ship over, even when the reachability argument looks good. No release checklist names Security as a gate, but every tag since v0.0.14 was cut on a green Security run.

**Direction (not applied).** Take `wasmtime` and its `wasmtime-*` and `cranelift-*` family to 49.0.2 (a lockfile update if the caret allows it), re-run the audit, confirm the reachability reading against the GHSA text and record the conclusion; consider naming Security in the release checklist.

### F-03 — The sample does not demonstrate the plan's rendering and asset bar, and the engine has no camera

**Severity:** Blocker (bar and scope) · **Decision needed:** yes · **Triage:** unassigned

The plan's bar, per subsystem (`v0.1.0-plan.md:23-27`): "**Rendering** draws actual `World` state (`Transform` + a renderable component) every frame, not a hand-fed vertex buffer like `examples/spinning-cube`. **Assets** feed the renderer and audio system real files from disk, not hardcoded Rust arrays."

**Evidence (observed in code).**

- `examples/collectathon/src/scene.rs` draws from values the sample computes (`world_ndc(player_x, player_y)` and a `PickupDraw` slice), builds a fresh `Vec<f32>` vertex stream each frame, uploads it as a new buffer and draws with a private WGSL shader (`shader.rs`, which is why the sample depends on `naga`). Its module docs name the `spinning-cube` "rebuild the vertex buffer per frame" approach as the one it follows (`scene.rs:8`).
- The sample contains no `Renderable`, `extract_scene`, bake call, camera, `create_texture`, `TexturedRenderable` or `MeshRenderable`. `canary-render-ecs` is a declared dependency of `collectathon` and is mentioned only in a doc comment.
- `GameAssets { meshes, textures, sounds }` loads `quad.glb`, `box.glb`, `rgba2x2.png` and a WAV. The mesh and texture stores are inserted into the world as resources and read by nothing; only the sound feeds the audio trigger. The assets load, and are never drawn.
- The bridge the plan means does exist and is tested (`render_ecs_readback` and `physics_game_proof`, both of which pass here under lavapipe). Its projection is a fixed virtual camera: `CAMERA_DISTANCE = 3.2`, `FOCAL_LENGTH = 2.2`, default square aspect (`extract.rs`, `textured_renderable.rs`). `extract.rs:52` still says a camera component, view matrix and projection choice are "v0.0.10+ scope"; `status.md` lists "a real 2D/orthographic camera" as deferred. The plan's v0.0.11 section nevertheless says the RHI "renders 2D content fine as a special case (an orthographic camera and flat quads)". A 2D game cannot use the bridge without squeezing its world into the fixed frustum, and hand-rolling the projection, vertex building and shader is what the sample does instead. The present-and-retry loop alone is about 60 lines of `bin/collectathon.rs` (`:296-356`).

**Why it matters.** "Without bypassing the engine or implementing fundamental engine systems themselves" is the plan's own criterion, and the sample's per-frame render path is code a game author is not supposed to have to write. This is the one blocker where the code is not wrong: the bar and the sample disagree.

**Direction (not applied; decision needed).** Either (a) bring the sample onto the bridge, which needs an answer for the camera (a component with an orthographic projection, or authoring the world inside the fixed frustum) and draws the loaded mesh and texture; or (b) amend the plan to say what v0.1.0 actually offers (RHI plus a hand-rolled projection) and move camera and renderable into "Explicitly not required". Both are legitimate. Shipping v0.1.0 with the plan and the sample saying different things is not.

### F-04 — No CI job runs any sample binary or end-to-end proof, and the recorded evidence is not reproducible

**Severity:** High · **Decision needed:** no · **Triage:** unassigned

**Evidence.**

**Direction (not applied).** A CI step that runs `collectathon_headless` and asserts its summary line, the server/client pair on loopback, and the collab client; a unit test that loads every file under `assets/` through the public loaders.

### F-05 — Simulation time follows the presentation rate; there is no wall-clock or fixed-step driver on the consumer path

**Severity:** High · **Decision needed:** yes (documented deferral) · **Triage:** unassigned

**Evidence.**

- `examples/collectathon/src/bin/collectathon.rs:188` sets `let step = Duration::from_millis(STEP_MS)` (`game.rs:34`, `STEP_MS = 16`) and `:231` passes `frame_dt: step` to the frame driver on every outer frame. The file contains no `Instant`, `SystemTime`, `elapsed` or `sleep`. Each pass through the loop advances the simulation by 16 ms whether the frame took 7 ms (144 Hz) or 33 ms.
- Observed: `collectathon 600` under Xvfb and lavapipe presented 600 frames in 16.42 s of wall clock (36.6 frames/s) while the simulation advanced 600 x 16 ms = 9.60 s. On a 144 Hz display with FIFO presentation the same binary would run the game about 2.3 times faster than real time.
- On `FrameOutcome::Skipped` (zero-extent or minimised window) the loop `break`s out of the present attempt and starts the next outer frame with no wait (`:329`).
- This is documented: `runtime-composition.md:142` says the frame driver takes a "caller-provided frame duration; it is not yet a wall-clock window loop", and `:126` says a general fixed-step game runner is "a separate design" and not required. The engine does have a wall-clock `App::run` (`canary-core`), but the sample's path (`FrameDriver::drive_frame`) does not use it.

**Why it matters.** A game whose speed depends on the monitor is not "a real, small game". The deferral was reasonable while the sample was a proof of integration; with the bar stated as "a competent developer could write a real game", every consumer has to write their own timing loop on day one.

**Direction (decision needed).** Either provide a small accumulator-based fixed-step helper on the runtime (physics already carries a bounded accumulator internally, `runtime-composition.md:123`), or state in the plan that v0.1.0 leaves timing to the game and say so in the sample README.

### F-06 — Fresh-checkout system prerequisites are undocumented; the Linux build fails without them

**Severity:** High · **Decision needed:** no · **Triage:** unassigned

**Evidence.**

- On a stock Ubuntu 24.04 image `pkg-config` finds none of `alsa`, `wayland-client`, `xkbcommon`, `xrandr`, `xi` or `xcursor`. With `alsa.pc` unavailable (simulated with `PKG_CONFIG_LIBDIR=/nonexistent`) the build stops in `alsa-sys 0.4.0`: `error: failed to run custom build command for alsa-sys v0.4.0` (exit status 101). `alsa-sys` is pulled in by `rodio`/`cpal` for the audio backend.
- CI installs `libwayland-dev libxkbcommon-dev libxrandr-dev libxi-dev libxcursor-dev pkg-config libasound2-dev` (`ci.yml:75`), but none of `README.md`, `CONTRIBUTING.md`, `docs/development/*`, `examples/*/README.md` or `scripts/setup-check.sh` mentions them. `setup-check.sh` verifies only `git`, `rustc`, `cargo`, `rustup` and the `wasm32-wasip2` target. The sample README begins "From a fresh checkout, with the `stable` toolchain from `rust-toolchain.toml`" (`:23`).
- The release workflow had the same omission until `742b469` (2026-09-30), the day after v0.0.14's Release run failed.

**Why it matters.** The exit evidence is a developer following the documented path from a fresh checkout. On Linux that path currently ends in a `pkg-config` error that the documentation never warned about.

**Direction (not applied).** List the packages per platform in the sample README and `build-system.md`, and have `setup-check.sh` check for them.

### F-07 — Release-process drift: `stable`, tags and GitHub Releases

**Severity:** High · **Decision needed:** yes · **Triage:** unassigned

**Evidence.**

- `docs/development/git-workflow.md` says `stable` "represents releases: every commit on `stable` corresponds to a tagged" release (`:22`), and the flow is `dev --release--> stable`: "Merge `dev` into `stable`" (`:54`, `:68`).
- `stable` is `7176ed0`: `chore(release): cut v0.0.2` plus two later commits that are not on `dev` ("Update Cargo.toml with homepage and readme", "Add custom funding link to FUNDING.yml"). `git rev-list --left-right --count origin/stable...origin/dev` gives `2 187`. No release since v0.0.2 was merged into it, and the v0.0.16 tag is not an ancestor of it.
- Tags are v0.0.1 and v0.0.3 to v0.0.16. **`v0.0.2` does not exist**, although its release commit does (on `stable`). Tags v0.0.3 to v0.0.11 are documented retroactive backfill tags (`2b5a82f`, "record backfill tags across v0.0.3-v0.0.11"); the commits tagged v0.0.11, v0.0.12 and v0.0.13 show no workflow runs either.

### F-10 — `canary-net`'s two-process test fails when libtest runs single-threaded

**Severity:** Medium · **Decision needed:** no · **Triage:** unassigned

**Evidence (observed).**

- The first `cargo test --locked --workspace` on this 1-vCPU machine failed: `session_roundtrip_over_loopback_quinn` after 30.01 s with "timed out waiting for the server READY line" (`engine/canary-net/tests/session_roundtrip.rs:523`). It reproduces when the test binary is run on its own.
- Root cause. The test re-executes its own binary as the server (`--exact child_server_main --nocapture`) and waits for a stdout line that starts with `READY `. With libtest at concurrency 1 the harness prints `test child_server_main ... ` without a newline before the test body runs, so the child's output is `test child_server_main ... READY 127.0.0.1:33463`, which never starts with `READY `. Raw bytes from `od -c`: `t e s t   c h i l d _ s e r v e r _ m a i n   . . .   R E A D Y   1 2 7 . 0 . 0 . 1 : 3 3 4 6 3 \n`. With `RUST_TEST_THREADS=2` (inherited by the child) the child prints `READY …` on its own line and the whole test passes in 0.02 s.
- The same happens on any 1-CPU or cgroup-limited runner and with `-- --test-threads=1`. With concurrency 2 all other gates passed on the same machine, and the full workspace run is green: 918 passed, 0 failed, 22 ignored.

**Why it matters.** `cargo test --workspace` is a hard gate in AGENTS.md, and small containers, VMs and AI sandboxes are exactly where it gets run. GitHub's hosted runners have more than one core, which is why CI never sees it.

**Direction (not applied).** Have the child print a leading newline before `READY`, or have the parent search each line for `READY ` instead of matching a prefix.
