Each finding has a stable ID (`CANARY-REL-nnn`), evidence, severity, release impact, a concrete resolution and the regression coverage that would keep it fixed. Severity follows impact on the `v0.1.0` release claim: **Blocker** invalidates the claim, **High** must be resolved or explicitly reconciled before the tag, **Medium** should be fixed, **Low** is worth fixing, **Informational** records an accepted limit or an observation.

## Findings

### CANARY-REL-001

**`stable` cannot be promoted from `dev` under the current history and rulesets**

| Field | Value |
|---|---|
| Category | release process |
| Severity | High |
| Release impact | Blocks cutting `v0.1.0` until a promotion path is chosen |
| Confidence | confirmed |
| Kind | observed defect |

**Evidence**

- `git rev-list --left-right --count origin/stable...origin/dev` prints `2 237`; merge base `946a687` ("chore(release): cut v0.0.2").
- `git merge-tree --write-tree origin/dev origin/stable` reports a conflict in `Cargo.toml`.
- Repository rulesets (REST API): both `dev` and `stable` enable `required_linear_history` and `non_fast_forward`; `stable` also `required_signatures`; `bypass_actors` is empty on both. (Legacy branch-protection settings returned 403 to the audit token, so they are unverified.)
- `docs/development/git-workflow.md:68` instructs "Merge `dev` into `stable`"; `.github/workflows/release.yml:61` requires the tagged commit to be an ancestor of `origin/stable`.
- The two stable-only commits (`d89d6ff` workspace metadata, `7176ed0` `FUNDING.yml`) look superseded: `FUNDING.yml` is byte-identical on `dev`, and `dev` deliberately sets a different `homepage`.

**Current behavior.** A merge commit is forbidden (linear history), a force push is forbidden, a fast-forward is impossible because `stable` has unique commits, and rebasing 237 commits conflicts. A squash merge would work mechanically but yields a commit whose SHA differs from the commit the release evidence names.

**Expected behavior and impact.** A documented promotion procedure that preserves the evidenced tree and works under the repository's own rulesets. Impact: the release would be improvised (temporary ruleset edits, force pushes) at the moment least suited to improvisation.

**Reproduction.** Run the three git commands above in a clone of `https://github.com/HylightGames/canary`; read the rulesets with `GET /repos/HylightGames/canary/rulesets/{id}`.

**Recommended resolution.** (1) Confirm the two stable-only commits are superseded (they appear to be). (2) Reset `stable` once to the evidenced `dev` commit using a documented, temporary maintainer bypass on the `stable` ruleset, then restore it; record the SHA. After that `stable` only fast-forwards. (3) Rewrite step 3 of `git-workflow.md` to say so. (4) Add the tree-equality check from `006`. Alternative: squash-merge a PR and verify tree equality; not recommended as the default because it breaks SHA-addressed evidence.

**Regression coverage.** Rehearse on a scratch repository with identical rulesets (roadmap `V2-02`); `release.yml` step asserting `git diff --quiet <evidence-sha> <tag-sha>`.

**Dependencies and trade-offs.** `002` (the bump commit must also reach `stable`), `005`, `006`.

### CANARY-REL-002

**The `0.1.0` version bump is undocumented and changes the commit that must be tagged**

| Field | Value |
|---|---|
| Category | release process |
| Severity | High |
| Release impact | Blocks tagging until the bump is performed and the gates re-run on the bump commit |
| Confidence | confirmed |
| Kind | observed defect |

**Evidence**

- Root `Cargo.toml:31` sets the workspace version to `0.0.16`; 31 further manifest lines pin `version = "0.0.16"` on inter-crate path dependencies (`git grep -F 'version = "0.0.16"' -- '*.toml'` finds 32 lines in total).
- `.github/workflows/release.yml:42` derives the expected tag from the first `^version` line of the root manifest.
- `docs/reviews/RELEASE_CHECKLIST.md`, `docs/development/git-workflow.md` and `docs/release-notes/v0.1.0.md` contain no bump step (a grep for bump/version-to-0.1.0 finds nothing relevant).
- `docs/release-notes/v0.1.0.md` states that no `v0.1.0` tag exists yet.

**Current behavior.** Tagging `v0.1.0` on the audited commit fails `verify-tag`. The fix is a multi-file commit (root version, 31 pins, `Cargo.lock`, `CHANGELOG.md`) that necessarily changes the tree, so CI and manual evidence recorded for the pre-bump commit no longer describe what gets tagged.

**Expected behavior and impact.** The bump is a documented, automated and tested step that happens before the final evidence is collected.

**Reproduction.** Read `release.yml:42` and `Cargo.toml:31`; `git tag v0.1.0 ebc8f7f` followed by the workflow's version comparison fails.

**Recommended resolution.** Add `cargo xtask bump <version>` that rewrites the workspace version and every path-dependency pin and refreshes `Cargo.lock`; add the checklist step "bump, then gather evidence on the bump commit, then tag that commit"; add a CI guard that every pin equals the workspace version.

**Regression coverage.** An xtask test that runs the bump on a temporary copy and asserts `cargo metadata --locked` resolves with every member at the new version; a CI job failing on any pin that differs from the workspace version.

**Dependencies and trade-offs.** `001`, `005`, `006`.

### CANARY-REL-003

**Deeply nested snapshot values can exhaust the stack during decode**

| Field | Value |
|---|---|
| Category | security / robustness |
| Severity | Medium |
| Release impact | Should be fixed before any consumer opens untrusted save files; not a blocker for a first release if documented |
| Confidence | confirmed |
| Kind | observed defect |

**Evidence**

- `SnapshotValue` is recursive: `engine/canary-state/src/value.rs:32` (`List(Vec<SnapshotValue>)`) and `:34` (`Map(BTreeMap<String, SnapshotValue>)`).
- `engine/canary-state/src/snapshot.rs:199` decodes with `postcard::from_bytes` directly. `postcard` has no recursion limit, and each nesting level costs two input bytes (variant tag and length).
- No depth guard exists in `canary-state`, `canary-collab`, `canary-net` or `canary-runtime` (searches for depth/recursion terms find nothing). The authored-JSON path is protected by `serde_json`'s default limit of 128.
- Network and collaboration wire types do not embed `SnapshotValue`, so the exposure is local files (save files, snapshots, project files), not the network.

**Current behavior.** Reproduced on the audited commit with the proposed test: decoding a `SnapshotValue` from a 20,001-byte input (10,000 nested lists) aborted the process with `SIGABRT` (exit status 6, a stack overflow) in a debug build on a test thread (2 MiB stack). Nesting of 1,000 decoded normally. The authored-JSON path returned an error for a file of 1,000,000 `[` characters (serde_json's depth limit). Release builds and an 8 MiB main-thread stack tolerate more depth, but a 1 MiB input could encode about 500,000 levels; that case was not run.

**Expected behavior and impact.** Opening a hostile or corrupt file returns a typed error at every nesting depth. Impact: a crafted snapshot or save file aborts the process (denial of service for any game loading downloaded saves or mods).

**Reproduction.** `cargo test -p canary-state --test audit_snapshot_depth -- --ignored deeply_nested_snapshot` (proposed test; the decode runs in a child process so an abort is reported as a failure).

**Recommended resolution.** Smallest sound fix: a manual `Deserialize` for `SnapshotValue` that carries a depth counter (a `DeserializeSeed` or a thread-local guard) and rejects nesting beyond a documented bound (64 is ample); also bound input size (`009`). If deep values can be built in code, make `Drop` iterative.

**Regression coverage.** `engine/canary-state/tests/audit_snapshot_depth.rs` (proposed); un-ignore once the bound lands, and extend it to call `decode_snapshot` end to end.

**Dependencies and trade-offs.** `009` (size budget), roadmap `V2-07`.

### CANARY-REL-004

**The developer path needs about 1,200 lines of example-owned renderer and loop glue**

| Field | Value |
|---|---|
| Category | API / release claim |
| Severity | High |
| Release impact | Must be reconciled before the tag: narrow the claim in the release notes, or move the glue into engine crates |
| Confidence | confirmed |
| Kind | scope gap against the stated release bar |

**Evidence**

- The stated bar (`docs/roadmap/v0.1.0-plan.md:5-7`): a competent developer can write a real small game "without bypassing the engine or implementing fundamental engine systems themselves".
- `examples/collectathon/src/scene.rs:207` defines `ScenePipeline` (the file is 500 lines); `shader.rs` (38 lines) compiles WGSL with `naga`; `hud.rs` is 192 lines; the windowed `bin/collectathon.rs` is 505 lines. `examples/ui-game/src/scene.rs:75` defines a second `ScenePipeline`.
- The engine crates contain no scene pipeline, no application or loop runner, and no shader compile path; `docs/release-notes/v0.1.0.md` (line 56) states there is no facade or prelude crate.
- The RHI has no depth attachment, one texture binding and no mip chain (`engine/canary-render/src/types.rs:43`, `docs/architecture/rendering.md:193`), and the perspective path uses a fixed virtual camera (`engine/canary-render-ecs/src/textured_renderable.rs:37`).

**Current behavior.** A new developer can build the sample, but only by copying its renderer pipeline, shader compilation, resize handling, offscreen target and loop. Those are engine fundamentals by most definitions. The documentation is honest about the missing facade, but not about how much of a game's rendering is the consumer's job.

**Expected behavior and impact.** Either the release claim states precisely what the consumer supplies, or the engine supplies it. Impact: expectation mismatch for the first external consumers; every game repeats the same 1,200 lines.

**Reproduction.** `wc -l examples/collectathon/src/scene.rs examples/collectathon/src/shader.rs examples/collectathon/src/hud.rs examples/collectathon/src/bin/collectathon.rs`.

**Recommended resolution.** For `v0.1.0`: state in the release notes that the renderer pipeline, shader compilation and loop are reference code in `examples/` that consumers copy, and list what that code does. For `v0.2.0`: roadmap `V2-01` (engine-owned loop and facade) and `V2-03` (engine-owned 2D pipeline).

**Regression coverage.** A CI check (or review checklist item) that `examples/*` define no render pipelines once `V2-03` lands; the facade acceptance in `V2-01` (a `main` of 200 lines or fewer).

**Dependencies and trade-offs.** `012`, `027`, roadmap `V2-01`, `V2-03`, `V2-08`.

### CANARY-REL-006

**The release workflow publishes on any `v*` tag with no approval or evidence gate**

| Field | Value |
|---|---|
| Category | release process |
| Severity | Medium |
| Release impact | Should be fixed before the first real release; the stable-ancestry check is the only implicit human step |
| Confidence | confirmed |
| Kind | design gap |

**Evidence**

- `.github/workflows/release.yml:19-20` triggers on `tags: v*`; the publish step sets `draft: false` (`:251`); no job declares an `environment:` with a required reviewer.
- `verify-tag` checks the tag/version match, the existence of `docs/release-notes/<tag>.md` and stable ancestry; it never reads the notes' content or the checklist state, so unchecked manual gates or stale evidence do not stop a publish.
- The `stable` ruleset requires zero approving reviews.

**Current behavior.** Once a maintainer pushes a `vX.Y.Z` tag on a commit reachable from `stable` and the build and integration gates pass, a public release is created automatically. Manual live-device evidence is recorded in documents but not enforced.

**Expected behavior and impact.** Publication requires an explicit approval and a machine-checked evidence record. Impact: an accidental or premature tag publishes a release.

**Reproduction.** Read `release.yml`; confirm there is no `environment:` key and that `draft: false` is set.

**Recommended resolution.** Smallest sound change: publish as a draft by default and add a GitHub Environment with a required reviewer to the publish job; add an evidence-validation step (cited SHA and tree match the tag, required checklist boxes ticked).

**Regression coverage.** A `workflow_dispatch` dry run on a throwaway pre-release tag (roadmap `V2-02`) that exercises every step except publication.

**Dependencies and trade-offs.** `001`, `005`, `007`.

### CANARY-REL-008

**The Tier A (WASM) budget bounds each memory, not the guest; tables and instance counts are unlimited**

| Field | Value |
|---|---|
| Category | security / sandboxing |
| Severity | Medium |
| Release impact | Fix or document before Tier A is described as resource-safe for untrusted guests |
| Confidence | confirmed |
| Kind | observed defect |

**Evidence**

- `engine/canary-plugin-api/src/tier_a/wasm_loader.rs:362` builds `StoreLimitsBuilder` with `memory_size(max_memory_bytes)` only (default 64 MiB). That caps each linear memory; table growth, memory count and instance count keep wasmtime's permissive defaults.
- Fuel metering is in place (10,000,000 units, rearmed per call), which bounds instruction count but not the memory one `table.grow` or several memories can commit.
- No test exercises aggregate memory or table growth (the existing fixture checks a single memory).

**Current behavior.** Reproduced with the proposed tests: (1) eight memories of 32 MiB each, every one under the per-memory cap, gave the guest 256 MiB against a 64 MiB budget; (2) forty `on-load` calls, each growing one funcref table by 2,000,000 slots and each inside its own fuel allowance, reached 80,000,001 elements (about 610 MiB). A single 20,000,000-slot `table.grow` committed about 125 MB of host memory (resident set 70 to 196 MB) and then trapped, so per-call fuel limits how much one call can add, but nothing bounds the total.

**Expected behavior and impact.** The configured budget bounds what a guest can consume in total. Impact: a malicious or buggy Tier A guest can commit far more host memory than the documented budget.

**Reproduction.** `cargo test -p canary-plugin-api --lib audit_budget -- --ignored` after registering the proposed `audit_budget_tests` module.

**Recommended resolution.** Implement `ResourceLimiter` accounting across the store (sum of memories), set `table_elements`, `memories`, `tables` and `instances` limits, and consider epoch interruption for wall-clock bounds.

**Regression coverage.** `engine/canary-plugin-api/src/tier_a/audit_budget_tests.rs` (proposed); extend with the malicious-guest corpus in roadmap `V2-14`.

**Dependencies and trade-offs.** `V2-14`.

### CANARY-REL-009

**Project and snapshot loading has no size budget**

| Field | Value |
|---|---|
| Category | security / robustness |
| Severity | Medium |
| Release impact | Should be fixed before untrusted project files are supported |
| Confidence | confirmed |
| Kind | observed defect |

**Evidence**

- `engine/canary-state/src/authored.rs:147` reads the whole file with `std::fs::read_to_string` and no length check; `snapshot::decode_snapshot` (`snapshot.rs:199`) accepts a slice of any length.
- Contrast: `canary-assets` caps files at 64 MiB and decoded textures by byte budget, and `canary-loc` budgets every `.ftl` file.

**Current behavior.** Reproduced with the proposed test: `AuthoredDocument::load` on a 67,108,864-byte (64 MiB) sparse file allocated 67,108,904 bytes before returning an error.

**Expected behavior and impact.** Every file read has a documented budget enforced before allocation. Impact: a hostile or corrupt project file can force an allocation as large as the file.

**Reproduction.** `cargo test -p canary-state --test audit_unbounded_load -- --ignored` (proposed; loads a 64 MiB sparse file and measures peak allocation).

**Recommended resolution.** Check `metadata().len()` (and the read itself with `take(limit + 1)`) against a documented default budget, with an override; return a typed `OverBudget` error. Apply the same to snapshot loading in `canary-runtime` and the sample's save/load.

**Regression coverage.** `engine/canary-state/tests/audit_unbounded_load.rs` (proposed).

**Dependencies and trade-offs.** `003`, roadmap `V2-10`.
