# Canary Engine `v0.0.6` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.6-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.6` has a
single focus — the RHI trait (`canary-render`) and its first backend
(`canary-render-vulkan`, via `ash`) — deliberately bounded to an
offscreen hello triangle rather than a render graph or a live window.

## What `v0.0.6` is

`v0.0.6` is where Canary's rendering stops being an abstraction-strategy
document and becomes a real GPU pipeline producing real pixels:

- **The RHI trait itself.** `canary-render`'s `RenderDevice`/
  `CommandEncoder`, deliberately minimal for this release's actual
  milestone — devices, buffers, a minimal pipeline, command encoding —
  not a speculatively complete GPU abstraction.
- **A first native backend, not a `wgpu` bootstrap.**
  `canary-render-vulkan` implements the trait via `ash` (compiling clean
  under the `rustc` 1.75 floor with zero pins), with real resource
  cleanup — an `Rc<ash::Device>` shared across every resource type's own
  `Drop` impl, not deferred to process exit — per ADR 0016, which
  supersedes ADR 0004's original backend choice per direct project
  direction.
- **The real milestone: a hard-coded triangle, rendered and read back.**
  One WGSL shader cross-compiled to SPIR-V through standalone `naga`,
  drawn to a real offscreen color target on this environment's real
  `llvmpipe` Vulkan device, read back and asserted on specific pixel
  values — not "it compiled" or "it didn't panic."
- **Backend opt-in-ness proven, not just described.**
  `canary-render` has zero dependencies at all — checked mechanically
  (`cargo tree -p canary-render` shows nothing, not even transitively).
  Building this also caught a real error in ADR 0016's first draft
  ("a Cargo feature on `canary-render`"), which is structurally
  impossible — a feature flowing from `canary-render-vulkan` back to the
  trait crate it depends on would be a literal dependency cycle — and
  corrected it in the ADR, `rendering.md`, and the roadmap.
- **Offscreen by design, not blocked on windowing.** Correctness is
  proven by pixel readback with no display surface needed — the same
  "prove the subsystem correct in isolation" pattern `v0.0.5` used for
  missing consumers — so this release never waited on `v0.0.4`; wiring
  swapchain-to-window presentation is real, near-term follow-on work.
- **`docs/architecture/rendering.md` and the ADRs' status updated to
  match**, with `cargo build`/`fmt --check`/`test`/`doc` clean and
  `clippy` clean (`-D warnings`, matching CI exactly) across the full
  workspace with both new crates added as members.

## What this release deliberately is not

- **Not the render graph.** Pass declaration, resource-dependency
  tracking, transient pooling, and the ECS extract step are all real,
  described, future work.
- **Not a materials/shader-variant system.** One hard-coded shader,
  compiled once, for the hello-triangle proof.
- **Not live window presentation (swapchain-to-window).** Deferred until
  real windowing is wired up to it — the RHI surface is designed so that
  addition needs no redesign.
- **Not `canary-render-metal`/`canary-render-dx12`/`canary-render-gl`.**
  Real, intended, explicitly unsequenced — see ADR 0016 for why Vulkan
  went first.
- **Not 2D-specific rendering, textures, depth testing, blending,
  multiple draw calls, or multi-pass rendering.** One triangle, one
  pass, one target.
- **Not real GPU hardware validation.** Automated coverage is
  `llvmpipe`-only; real-driver validation is real, necessary, separate
  work.

## What's next: goals for `v0.0.7`

Per [`docs/roadmap/status.md`](docs/roadmap/status.md) and the September
2026 external review triage
([`docs/decisions/2026-09-review-triage.md`](docs/decisions/2026-09-review-triage.md)),
the open "what comes next" question is resolved: two independent reviews
converged on the same gap — the ECS needs a real data-access
architecture (multi-component queries, typed resources, a formal access
model) before a scheduler can be built on it — so the ECS execution
model is next, not the render graph, physics, UI, or state options that
were previously open.
