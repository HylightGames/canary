## What `v0.1.0` is

The integration proof: one small documented game — the `collectathon`
sample in `examples/collectathon/` — played directly against Canary's
documented public APIs, proving the subsystems work as a usable whole
rather than only in isolation.

- **The game.** A one-room 2D collectathon: one physics-driven player
  moves on mapped digital actions (WASD/arrows + Space/collect, R/reset),
  collects three authored shards, reaches the goal, and shows
  score/goal status in a `CanaryUI` HUD. One HUD button sends game
  intent through the documented simulation boundary (never a direct
  `World` mutation from a widget callback); pickup state triggers a
  sound loaded from disk (`pickup.wav`).
- **The runtime path.** On-disk mesh/texture/audio assets load through
  the public asset APIs; the authored `room.json` spawns through the
  authored-state seam (`AuthoredSpawner` + `CollectathonDecoder`);
  physics + transform propagation + gameplay + audio trigger run on the
  scheduled simulation; a live window presents game output and HUD
  while a headless twin (`collectathon_headless`) runs the same
  schema/bindings/systems with scripted input for CI-friendly checks.
- **The integration boundaries.** From the same project data: one
  authoritative replication server/client exercises `.15` replication
  and frame-tagged input; two collaboration clients exercise the `.16`
  authored-transform operation, revision conflict, and reconnect history
  path; a Tier A guest probe runs inside its documented
  `on_load`/`on_unload`-only lifecycle boundary against the game world.
- **Save/reload.** The room uses authored stable IDs and can be saved
  and reloaded; a simulation snapshot separately proves deterministic
  capture and restore (byte-stable capture → restore → recapture).

## What this release deliberately is not

- **Not an editor, marketplace, console support, AI/ML integration,
  client prediction/rollback netcode, a full asset-cooking pipeline
  with hot reload, or beginner tooling** — all real, intended, and
  explicitly deferred per the plan.
- **Not a crates.io consumer release.** `canary-runtime` is
  `publish = false`, so `cargo add canary-runtime` does not resolve.
  The supported consumer route is a `git` (or local `path`) dependency
  pinned to a tested commit — see
  `examples/collectathon/README.md` ("Depending on Canary from your
  own crate"). There is no facade or prelude crate; each `canary-*`
  dependency is selected explicitly.
- **Not peer-to-peer, offline-queue, or per-frame-plugin proof.**
  Replication stays server-authoritative without prediction/rollback
  (ADR 0027); collaboration stays one-operation authoritative
  (ADR 0028); the guest exercises `OnLoad`/`OnUnload` only.

## What the consumer supplies

There is no facade, prelude, or application crate. The engine crates
compose into `canary-runtime`, but they do not own a general-purpose
game loop or a scene render pipeline, so a consumer assembling a game
from them supplies (or replaces) that glue itself. In `v0.1.0` the
reference for that work is the collectathon sample, which owns about
1,200 lines of it:

- `examples/collectathon/src/scene.rs` (500 lines) — `ScenePipeline`:
  scene shader pipelines, scene vertex baking, and draw recording into
  the caller's open color pass (no depth attachment).
- `examples/collectathon/src/shader.rs` (38 lines) — WGSL compilation via
  `naga`; the engine crates provide no shader compile path.
- `examples/collectathon/src/hud.rs` (192 lines) — the `CanaryUI` HUD
  layout and the bridge from a button event to simulation intent.
- `examples/collectathon/src/bin/collectathon.rs` (505 lines) — the
  windowed binary: offscreen color target, resize handling, render-pass
  opening, event loop, frame pacing, presentation, and window/audio
  bring-up around the engine schedule.

The remaining sample files (`game.rs`, `state.rs`, `assets.rs`, and the
networking/collaboration/plugin harnesses) are game-specific reference
code, not required glue. Copy or replace the four files above; an
engine-owned loop and 2D pipeline are `v0.2.0` roadmap items
(`V2-01`/`V2-03`), not `v0.1.0` deliverables. See
[`examples/collectathon/README.md`](../../examples/collectathon/README.md),
[`docs/architecture/engine-overview.md`](../architecture/engine-overview.md),
and [`docs/architecture/rendering.md`](../architecture/rendering.md) for
where the subsystem boundary sits.

## Try it

```sh
git clone <this repository>
cd canary
# On Linux, install the native build libraries first (see
# examples/collectathon/README.md "Linux native packages"):
# sudo apt-get install -y libwayland-dev libxkbcommon-dev libxrandr-dev \
#   libxi-dev libxcursor-dev pkg-config libasound2-dev

cargo run -p collectathon --bin collectathon        # windowed game
cargo run -p collectathon --bin collectathon_headless  # deterministic twin
```

the live-evidence checklist.

## Robustness bounds

Three robustness gaps reproduced by the final review are fixed, so the
bounds below are enforced rather than aspirational:

- **Snapshot nesting.** Decoding a `SnapshotValue` is bounded at
  `MAX_SNAPSHOT_VALUE_DEPTH` (64 levels, counting the value itself). A
  crafted 20 KB save can no longer abort the process; it fails with a
  typed `StateError::NestingTooDeep`.
- **File budgets.** `AuthoredDocument::load` is bounded by
  `MAX_PROJECT_BYTES`, and `load_snapshot`/`decode_snapshot` by
  `MAX_SNAPSHOT_BYTES` (16 MiB each). Oversized input is refused from a
  metadata pre-check (`StateError::InputTooLarge`) before it is read,
  not after it has been allocated.
- **Tier A resource budgets.** `ResourceBudget::max_memory_bytes` is a
  store-wide total shared by every linear memory and table a guest
  creates, not a per-memory ceiling; memory, table and instance counts
  are capped as well. Several memories can no longer multiply the
  budget.

Untrusted project and save files, and untrusted Tier A plugins, are
supported within those bounds. The bounds are denial-of-service
ceilings, not a trust or authentication boundary.

**Dependency baseline.** `cargo audit --deny warnings` reports no
vulnerabilities: wasmtime 49.0.5 closes RUSTSEC-2026-0422/0423/0424 and
rustix 1.1.6 closes RUSTSEC-2026-0486. The one accepted warning is
`ttf-parser` unmaintained (RUSTSEC-2026-0192) reached through winit's
`ab_glyph`/`sctk-adwaita` chain; it is not a vulnerability and is not
manifest-actionable from this workspace.

## Known limitations

`v0.1.0` is a foundation proof, not a production multiplayer stack. The
networking limits that matter to a consumer are:

- **Loopback and one session.** The QUIC transport refuses any
  non-loopback bind address (`NetError::NonLoopbackBind`; no opt-out),
  and the sample server rejects one at its CLI before any socket work.
  The sample server serves exactly one session, then exits; reconnect is
  new-session-only and never resumes an old session.
- **Server certificate pinning only.** The implemented trust is the
  client pinning the server's certificate. It authenticates the server,
  not the client.
- **No client authentication.** An authoritative server cannot identify
  or authorize a client, which is why it is restricted to loopback. Do
  not expose it to another machine or a public network without a
  separate authentication and abuse review.

See
[`docs/architecture/networking.md`](../architecture/networking.md#known-limitations-v010)
for the architectural detail. No prediction, reconciliation, or rollback
is implemented either (see "What this release deliberately is not" and
ADR 0027).

## What's next

Per [`docs/roadmap/status.md`](../roadmap/status.md) and the
post-`v0.1.0` roadmap: the editor, marketplace, console support, and
the deferred hardening items above. `v0.1.0` closes the
foundation-to-game arc. It adds one public-surface field in this pass —
`AudioSource::positional` (default `true`, but source-breaking for
external struct literals, which pre-1.0 policy allows) — and otherwise
does not open new API surface.
