# Canary Engine `v0.1.0` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`;
this note records the release scope for the future tag, it does not
claim a release happened. `v0.1.0` itself is NOT released.
**Scope source:** `docs/roadmap/v0.1.0-plan.md` (`v0.1.0` — integration proof)
**Branch/tag policy:** work happens on `dev`; `stable` only receives
reviewed release merges (`feature/<name> --PR--> dev --release-->
stable`), per `docs/development/git-workflow.md`. Tags (`vX.Y.Z`) mark
the release commit and trigger publication of this file via
`.github/workflows/release.yml`. No `v0.1.0` tag exists yet; this
document states the policy without resolving any `stable`/tag drift.

## What `v0.1.0` is

The integration proof: one small documented game — the `collectathon`
sample in `examples/collectathon/` — played directly against Canary's
documented public APIs, proving the subsystems work as a usable whole
rather than only in isolation.

- **The game.** A one-room 2D collectathon: one physics-driven player
  moves on mapped digital actions (WASD/arrows + Space/collect, R/reset),
  collects three authored shards, reaches the goal, and shows
  score/goal status in a `CanaryUI` HUD. One HUD button sends game
  intent through the documented simulation boundary (never a direct
  `World` mutation from a widget callback); pickup state triggers a
  sound loaded from disk (`pickup.wav`).
- **The runtime path.** On-disk mesh/texture/audio assets load through
  the public asset APIs; the authored `room.json` spawns through the
  authored-state seam (`AuthoredSpawner` + `CollectathonDecoder`);
  physics + transform propagation + gameplay + audio trigger run on the
  scheduled simulation; a live window presents game output and HUD
  while a headless twin (`collectathon_headless`) runs the same
  schema/bindings/systems with scripted input for CI-friendly checks.
- **The integration boundaries.** From the same project data: one
  authoritative replication server/client exercises `.15` replication
  and frame-tagged input; two collaboration clients exercise the `.16`
  authored-transform operation, revision conflict, and reconnect history
  path; a Tier A guest probe runs inside its documented
  `on_load`/`on_unload`-only lifecycle boundary against the game world.
- **Save/reload.** The room uses authored stable IDs and can be saved
  and reloaded; a simulation snapshot separately proves deterministic
  capture and restore (byte-stable capture → restore → recapture).

## What this release deliberately is not

- **Not an editor, marketplace, console support, AI/ML integration,
  client prediction/rollback netcode, a full asset-cooking pipeline
  with hot reload, or beginner tooling** — all real, intended, and
  explicitly deferred per the plan.
- **Not a crates.io consumer release.** `canary-runtime` is
  `publish = false`, so `cargo add canary-runtime` does not resolve.
  The supported consumer route is a `git` (or local `path`) dependency
  pinned to a tested commit — see
  `examples/collectathon/README.md` ("Depending on Canary from your
  own crate"). There is no facade or prelude crate; each `canary-*`
  dependency is selected explicitly.
- **Not peer-to-peer, offline-queue, or per-frame-plugin proof.**
  Replication stays server-authoritative without prediction/rollback
  (ADR 0027); collaboration stays one-operation authoritative
  (ADR 0028); the guest exercises `OnLoad`/`OnUnload` only.

## Try it

```sh
git clone <this repository>
cd canary
# On Linux, install the native build libraries first (see
# examples/collectathon/README.md "Linux native packages"):
# sudo apt-get install -y libwayland-dev libxkbcommon-dev libxrandr-dev \
#   libxi-dev libxcursor-dev pkg-config libasound2-dev
git checkout dev
cargo build -p collectathon
cargo run -p collectathon --bin collectathon        # windowed game
cargo run -p collectathon --bin collectathon_headless  # deterministic twin
```

See [`examples/collectathon/README.md`](../../examples/collectathon/README.md)
for setup, launch, controls, the first-game guide (dependency selection
+ boot order: assets → room → world → schedule → presentation), and
the live-evidence checklist.

## Evidence checklist (per WP4: automated vs live-device)

Automated rows run in CI or as deterministic local commands; manual
rows require a real machine with a display and/or audio device and are
**left unchecked** until that run is recorded (platform / command /
result). CI plus this table is the WP4 exit-evidence split — no
unsupported platform or backend is implied verified.

### Automated (CI / deterministic local)

| Check | Where | Command | Result |
| --- | --- | --- | --- |

| Headless deterministic run (90 scripted frames; hold-left frame 0, collect edge 33, release 60; decode-only audio) | CI-capable, local | `cargo run -p collectathon --bin collectathon_headless` | `collectathon_headless: score … collected …/… player (…)` |

## What's next

Per [`docs/roadmap/status.md`](../roadmap/status.md) and the
post-`v0.1.0` roadmap: the editor, marketplace, console support, and
the deferred hardening items above. `v0.1.0` closes the
foundation-to-game arc. It adds one public-surface field in this pass —
`AudioSource::positional` (default `true`, but source-breaking for
external struct literals, which pre-1.0 policy allows) — and otherwise
does not open new API surface.
