# Canary Engine `v0.0.5` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.5-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.5` has a
single focus — `canary-loc`, `LocKey` + Fluent (`.ftl`) resolution per
ADR 0015 (now `Accepted`) — deliberately moved ahead of rendering since
it's a founding constraint that gets cheaper the earlier it's
load-bearing.

## What `v0.0.5` is

`v0.0.5` is where "no user-facing text is hardcoded, anywhere" stops
being a documented principle and starts being load-bearing code:

- **`LocKey` + the `key!` macro.** A newtype wrapping a validated key
  string, with compile-time validation of Fluent's identifier grammar —
  confirmed against `fluent-syntax`'s own parser source, not assumed
  from the spec — and a real `compile_fail` doctest proving an invalid
  key genuinely fails to build.
- **`LocaleBundle` with real fallback resolution.** Keys resolve against
  a fallback chain computed via `fluent-langneg`, proven against real
  `.ftl` content rather than mocked: a plain message, a pluralized
  message correctly branching between CLDR categories, string
  interpolation, an unavailable requested locale falling back to the
  configured default, and a real edge case (default locale configured
  but with zero actually-loadable content) degrading gracefully rather
  than panicking.
- **Missing-key/fallback events verified to actually fire.** The
  `tracing::warn!`/`tracing::debug!` events are checked with a real
  capturing `tracing` layer built specifically for it — which caught two
  genuine bugs in the test harness itself before either test could
  honestly pass.
- **A deliberately temporary placeholder loader.**
  `discover_available_locales`/`load_locale_resources` reads via
  `std::fs`, doc-commented as temporary and naming `canary-assets` as
  its intended replacement, decoupled from `LocaleBundle` (which takes
  any loader closure) so the replacement won't touch `LocaleBundle`'s
  own logic.
- **Toolchain pins re-verified at implementation time, not trusted from
  scoping.** Genuinely incomplete as scoped: two more pins needed
  (`unic-langid-macros`, `unic-langid-macros-impl`, both `=0.9.5`)
  beyond what scoping found, since `canary-loc` uses `unic-langid`'s
  `macros` feature — which the scoping-phase spike never exercised.
- **`docs/architecture/localization.md`'s "Status in this foundation"
  rewritten to match**, and `cargo build`/`fmt --check`/`test`/`doc`
  clean with `clippy` clean (`-D warnings`, matching CI exactly) across
  the full workspace with `canary-loc` added as a new member.

## What this release deliberately is not

- **Not `CanaryUI` integration.** No widget API exists yet to integrate
  with; `canary-loc` is proven standalone.
- **Not compile-time validation that a key resolves against real `.ftl`
  content.** Only key *syntax* is checked at compile time — see ADR 0015.
- **Not `fluent-templates`/`fluent-fallback`/`i18n-embed` or any
  compile-time asset embedding.** See ADR 0015's "Alternatives
  considered."
- **Not translator tooling or a Weblate integration.** Worth real locale
  content existing first.
- **Not non-Fluent formats as a runtime option.** One format, per
  ADR 0015 — no runtime format negotiation is planned.

## Try it

```sh
git clone <this repository>
cd canary
git checkout dev
cargo build --workspace
cargo test --workspace
cargo run -p canary-runtime
```

## What's next: goals for `v0.0.6`

Per [`docs/roadmap/v0.0.6-roadmap.md`](../roadmap/v0.0.6-roadmap.md#why-rendering-and-why-bounded-this-way),
rendering is the next large, real piece of engine surface — the RHI
trait and its first concrete backend — now that the localization
redirect's "cheap now, expensive later" reasoning no longer applies the
same way.

## Thanks

Built and reviewed as a single continuous effort, picking up cleanly
from `v0.0.4`'s windowing work via the documented architecture and ADRs
rather than from memory of how it was built — including proving
`canary-loc`'s core correct now, by direct real tests against the crate
itself, instead of waiting on `CanaryUI` or `canary-assets` to exist.
