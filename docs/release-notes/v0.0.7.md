# Canary Engine `v0.0.7` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.7-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.7` has a
single focus — the ECS data-access architecture a scheduler needs
(queries, resources, `Tick` width) — decided by the September 2026
external review triage rather than picked from the previously-open
render-graph/physics/UI/state options.

## What `v0.0.7` is

`v0.0.7` is where the ECS gains the data-access architecture the
reviews found missing — locked contracts, only what the next milestone
needs:

- **`Tick(u32)` → `Tick(u64)`.** A plain `Ord`-derived `tick > since`
  comparison is only correct if `Tick` never wraps during a `World`'s
  lifetime; at `u32`, a long-lived server ticking once per frame at 60Hz
  wraps in about 2.3 years of continuous uptime — mirroring the
  reasoning already applied to `Entity::generation`.
- **Typed resource storage.** `World::insert_resource`/`resource`/
  `resource_mut`/`remove_resource`/`contains_resource`/
  `resource_changed_since` — globally-unique, engine-owned state
  addressed by type, with the same `Tick`-based change detection every
  component column already has.
- **Multi-component queries.** `World::query2`/`query3` (read-only
  archetype-set intersection across 2–3 component types) and
  `World::query2_mut` (one mutable, one shared — the "update `A` based
  on `B`" shape) — deliberately narrow, hand-written methods rather
  than a fully generic `Query<D>`, mirroring this crate's established
  "manual impl before derive macro" precedent from ADR 0010.
- **`docs/architecture/execution-model.md`.** The design document these
  implement a first cut of, including the "five invariants" (ownership,
  access, time, identity, side-effects) adopted from the second review's
  closing argument.
- **The crate's first `unsafe`, reasoned explicitly.** `Archetype::
  column_pair_mut` enables `query2_mut`'s simultaneous mutable+shared
  column access, carries a `// SAFETY:` invariant comment, and is
  flagged prominently in `execution-model.md` ("On `unsafe`") — since
  the coding standards name `canary-ecs` as outside the two boundaries
  where `unsafe` is expected; the safe-storage-restructure alternative
  was considered and deferred as larger and riskier than this scope
  justifies.
- **Full-workspace hygiene.** `cargo build`/`fmt --check`/`test`/
  `clippy -D warnings` clean, with and without `winit-backend`,
  re-verified against this environment's `rustc`/`cargo` 1.91 after
  every change.

## What this release deliberately is not

- **Not the scheduler/job-stealing system itself.** The entire point of
  this release is the prerequisite, not the thing itself.
- **Not command buffers or events.** Nothing runs concurrently yet to
  need either.
- **Not first-class time types** (`WallClock`/`FrameTime`/
  `SimulationTime`) — no frame loop sophisticated enough to need them
  yet.
- **Not a fully generic `Query<D>` trait or query-composed filters.**
  `query2`/`query3`/`query2_mut` are the narrow, real second consumer
  that should exist before generalizing.
- **Not mechanical enforcement of the five invariants** — real,
  accepted, scoped as its own future CI/`xtask` work.
- **Not mixed-mutability query shapes beyond `query2_mut`'s
  one-mutable-one-shared.**

## What's next: goals for `v0.0.8`

Per [`docs/roadmap/v0.0.8-roadmap.md`](../roadmap/v0.0.8-roadmap.md#why-this-and-why-bounded-this-way),
the scheduler is this release's direct, intended payoff: the
access-model work would otherwise sit unused for a release, so
`canary-scheduler` comes now — picked over the render graph/physics/
`CanaryUI`/`canary-state` options left open after `v0.0.7`.
