# Canary Engine `v0.0.8` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.8-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.8` has a
single focus — the scheduler `v0.0.7`'s access-model work was explicitly
the prerequisite for — bounded to what's actually safe to parallelize
now rather than blocking the whole release on concurrent writes.

## What `v0.0.8` is

`v0.0.8` is where `v0.0.7`'s access model pays off as a real, working,
measurably parallel scheduler:

- **New crate `canary-scheduler`.** Depending only on `canary-ecs`'s
  public API — no privileged access to `World`'s internals.
- **`SystemAccess`.** A system's declared reads/writes, component and
  resource types tracked separately, built as an explicit chainable
  declaration rather than inferred from a system function's signature —
  matching this project's existing "manual before macro" precedent from
  ADR 0010.
- **`Schedule`.** Greedily batches systems, in registration order, into
  stages — one or more read-only systems, or exactly one system that
  writes anything — and runs each stage, joining any spawned threads
  before the next starts.
- **Real, measured concurrent execution for read-only stages.** Via
  `std::thread::scope` — no external thread-pool dependency for this
  first cut — proven with a real timing-based test (two 120ms sleeping
  systems completing well under their sum) and a concurrency counter,
  not just exercised; and a write system is proven by test to never
  overlap a concurrently-running read.
- **Correctness at the boundaries.** Stage computation checked directly
  against `compute_stages` for every documented rule; a system observes
  an earlier order-dependent system's effect end-to-end through
  `Schedule::run` against a real `World`; `add_read_system` panics on a
  not-actually-read-only declaration rather than silently trusting the
  mismatch.
- **`docs/architecture/execution-model.md` updated in place** ("The
  scheduler" section) rather than a new document, per its own stated
  intent from `v0.0.7` — with `cargo build`/`clippy -D warnings`/`test`/
  `fmt --check` clean across the full workspace, with and without
  `winit-backend`, after adding the new crate.

## What this release deliberately is not

- **Not concurrent execution of two write systems, even with
  provably-disjoint access.** Found during implementation to need a
  substantially larger `unsafe` undertaking (closer to Bevy's
  `UnsafeWorldCell`/`SystemParam` machinery) than this scope justifies —
  the reason this release is bounded the way it is.
- **Not automatic access inference from a system's signature.** Declared
  explicitly, per the "manual before macro" precedent.
- **Not wiring `Schedule` into `canary-core`'s `App`/`Subsystem` tick
  loop.** `Schedule` is usable standalone; integration is real next work
  once a second subsystem beyond the ECS has systems worth scheduling.
- **Not a persistent work-stealing thread pool.** Threads spawn fresh
  per parallel stage — real overhead, documented, not optimized without
  evidence it matters yet.
- **Not command buffers or events.** Still correctly deferred: with
  concurrent systems always all-read and writes always solo, neither has
  a live race to prevent yet.

## What's next: goals for `v0.0.9`

Per [`docs/roadmap/v0.1.0-plan.md`](docs/roadmap/v0.1.0-plan.md#why-this-order-dependency-reasoning-not-preference),
`v0.0.9` starts the `v0.1.0` integration sequence directly on top of
this scheduler: a real-time `App`/`Subsystem` loop with real delta-time,
`Transform`/`GlobalTransform` hierarchy in a new crate, and ECS-driven
rendering — the bar shifting from "the crate exists" to "another real
part of Canary uses it."

where it's safe to be, with the write-concurrency gap named precisely
