# Canary Engine `v0.0.4` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.4-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.4` has a
single focus — a real `winit`-backed implementation of
`canary-platform`'s `Window`/`InputSource` traits — rather than
spreading effort across several half-finished pieces.

## What `v0.0.4` is

`v0.0.4` is where Canary stops being headless-only and gets a real
window, proven against a real display server rather than mocked:

- **Real `winit`-backed windowing.** `WinitWindow`/`WinitInput` exist
  alongside (not replacing) `HeadlessWindow`/`HeadlessInput` — headless
  remains the right choice for dedicated servers and most tests — behind
  a `winit-backend` Cargo feature off by default, with mechanically
  confirmed (`cargo tree`) zero `winit`/Wayland leakage into builds
  without it.
- **An honest pull/push bridge.** `Window::poll_events()` drives modern
  `winit` 0.30's `ApplicationHandler` model via `pump_app_events` with a
  zero timeout, buffering close/input events into fields the trait impl
  reads — documented as a real, acknowledged tension with `winit`'s
  recommended ownership-of-the-main-loop model, not a frictionless fit.
- **`Key` expanded to a realistic keyboard.** Letters, digits, function
  keys, modifiers, navigation, editing keys, and punctuation, modeled on
  physical position — up from two named keys plus an `Other(u32)` escape
  hatch — since a windowing backend nobody can type into isn't a
  meaningfully complete one.
- **A real running-window integration test.** Against a live `Xvfb`
  display: window creation, several `poll_events()` cycles, a real
  keyboard press synthesized via the X11 XTEST extension (observed as
  `InputEvent::KeyPressed(Key::W)`), and a real ICCCM
  `WM_DELETE_WINDOW` close signal — `#[ignore]`d by default, run
  automatically in CI's dedicated `windowing-integration` job.
- **Two genuine `winit` constraints found by testing, not assumed, and
  worked around.** `EventLoop::new()` panics off the main thread (where
  `cargo test` runs), and only one `EventLoop` can exist per process,
  ever — handled with a Linux-only, explicitly test-only
  `WinitWindow::new_for_testing` constructor and a consolidated test —
  plus the `winit`/Wayland pin set re-verified at implementation time
  (it had drifted; two more pins beyond scoping's three).
- **Docs and hygiene.** `docs/architecture/platform-abstraction.md`'s
  "Status in this foundation" rewritten to match, and `clippy` became
  reachable in this sandbox for the first time this release — used to
  confirm the new code clean and, in a separate commit, to clear the
  small number of pre-existing warnings in older code.

## What this release deliberately is not

- **Not rendering.** A window with nothing drawn into it — see `v0.0.6`.
- **Not gamepad/joystick input, IME, or any input beyond keyboard.**
  More keys, not more event kinds.
- **Not multi-window support.** One window — matching both the existing
  trait's implicit single-window shape and a real `winit` constraint
  found while implementing (one `EventLoop` per process, ever).
- **Not mobile or console windowing backends.** Desktop
  (Windows/macOS/Linux) `winit` support only.
- **Not a macOS/Windows equivalent of the integration test.**
  Linux/`Xvfb`/XTEST only for now.

## Try it

```sh
git clone <this repository>
cd canary
git checkout dev
cargo build --workspace
cargo test --workspace
cargo run -p canary-runtime
```

Windowing itself lives behind the opt-in feature (`winit-backend`, off
by default); the headless path above stays the default. See
[`README.md`](../../README.md) for the full picture and
[`CONTRIBUTING.md`](../../CONTRIBUTING.md) to get involved.

## What's next: goals for `v0.0.5`

Per [`docs/roadmap/v0.0.5-roadmap.md`](../roadmap/v0.0.5-roadmap.md#why-this-replaces-what-was-pencilled-in-as-v005),
localization (`canary-loc`) moved ahead of rendering: "no user-facing
text is hardcoded, anywhere" is a founding constraint that gets cheaper
the earlier it's load-bearing, while rendering — still real, still
scoped — simply isn't next.

## Thanks

Built and reviewed as a single continuous effort, picking up cleanly

rather than from memory of how it was built — including overturning, by
direct verification instead of inheritance, the old assumption that real
windowing couldn't be built or tested in this environment.
