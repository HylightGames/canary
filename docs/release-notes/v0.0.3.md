# Canary Engine `v0.0.3` — Release Notes

**Status:** implemented on `dev`, not yet tagged — `harden then cut`; this note records the release scope for the future tag, it does not claim a release happened.
**Scope source:** `docs/roadmap/v0.0.3-roadmap.md`
**Nature of this release:** one subsystem, done properly. `v0.0.3` has a
single focus — Tier A (sandboxed WASM Component Model) plugin loading,
described since `v0.0.1` but never implemented — rather than spreading
effort across several half-finished pieces.

## What `v0.0.3` is

`v0.0.3` is where "any language with a Component Model toolchain can
author a plugin" stops being aspirational and becomes real, working,
tested code:

- **A working Tier A loader in `canary-plugin-api`.** `WasmPluginLoader`/
  `WasmComponentPlugin` (in `engine/canary-plugin-api/src/tier_a.rs`),
  backed by Wasmtime `21.0.2` — confirmed empirically to compile under
  this sandbox's `rustc` 1.75 floor, with five transitive-dependency pins
  recorded in `docs/development/build-system.md` — loads a `.wasm`
  component, instantiates it with an explicit per-instance capability
  grant, and exposes it through the same `Plugin` trait Tier B already
  implements, covering the `on_load`/`on_unload` lifecycle end to end.
- **Structural capability enforcement, proven independently for each
  interface.** A component granted a capability can use it; a component
  without it has no reachable way to even attempt it — a grant decides
  what gets linked in at instantiation time, not an `if` inside an
  always-reachable host function. Proven separately for `ecs-read`/
  `ReadEcsWorld` and `ecs-write`/`WriteEcsWorld`: a component granted
  read but not write still fails to instantiate if it imports
  `ecs-write`.
- **A baseline resource budget on every Tier A instance.** A default
  memory limit and an execution (fuel) budget, proven by a real
  fuel-exhaustion trap test and a real over-budget `memory.grow` failure
  test — not merely wired through unverified.
- **The full first-cut ECS data ABI.** `get`/`set`/`has-component`/
  `is-valid-entity` over a deliberately small, explicit set of
  schema-safe value types (`ComponentValue`/`PrimitiveValue` via
  `ComponentValueCodec`/`CodecRegistry`), `SCHEMA_ID`-addressed through
  the `v0.0.2` identity registry (`World::type_id_for_schema`, then
  codec, then `World::get_erased`/`set_erased`) — identity and
  representation as two composed mechanisms, not one conflated API.
- **A proven AOT-compilation path.** `Engine::precompile_component` output
  loads via `Component::deserialize` and runs identically to a freshly
  compiled component — a working native-code execution path, not a
  performance claim.
- **Docs updated to match.** `docs/architecture/plugin-system.md` no
  longer carries Tier A's not-yet-implemented note, and ADR 0003 records
  both tiers as implemented; 15 unit + 2 integration tests in
  `canary-plugin-api` (up from 8), plus 5 new `canary-ecs` tests for the
  type-erased host-adapter half.

## What this release deliberately is not

- **Not a plugin manifest format, marketplace tooling, or capability
  review UX** (R-08; Era 6) — there is no marketplace to serve yet.
- **Not Tier B signing/provenance** (R-09) — unrelated to Tier A's trust
  model.
- **Not safe hot-unloading with full resource reclamation.**
  `Plugin::on_unload` being *called* is in scope; guaranteeing every
  resource gets reclaimed and the instance cleanly reinstantiated is a
  much bigger problem and isn't solved here.
- **Not scoped `World` access for a Tier A instance while that `World`
  is in use elsewhere** (R-34).
- **Not a scripting language layered on Tier A** — ADR 0003 leaves that
  as a possible future addition *once Tier A exists*.
- **Not real windowing, the change-detection unification work of ADR
  0014, or the parallel job-stealing scheduler** — each its own
  separately scoped piece.

## Try it

```sh
git clone <this repository>
cd canary
git checkout dev
cargo build --workspace
cargo test --workspace
cargo run -p canary-runtime
```

## What's next: goals for `v0.0.4`

Per the sequencing already recorded in
[`docs/roadmap/v0.0.3-roadmap.md`](../roadmap/v0.0.3-roadmap.md#explicitly-not-in-v003),
real `winit`-backed windowing (`canary-platform`) is next in sequence
after this release — deliberately not bundled with it, since a
non-headless environment isn't needed to validate a plugin loader.
